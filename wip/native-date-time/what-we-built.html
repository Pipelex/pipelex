Date and Time natives: one ISO 8601 contract

Two pinned MTHDS natives could not be produced by the primary operator. They validated, they dry-ran green, and then they failed on every paid call. Here is what broke, why it hid so well, and what we changed.

PR #1089 → dev branch fix/Native-date-time ~430 lines, 8 files

TL;DR

  • A PipeLLM with output = "Date", Date[] or "Time" failed 100% of live runs. The model answered "2025-03-12" — the only thing JSON can carry — and pydantic refused it with date_type.
  • Cause: a mode="before" validator silently forfeits pydantic's strict-JSON acceptance of ISO strings. Instructor validates every structured response with strict=True; whatever a before-validator returns is re-validated as Python input, where a str is refused outright. YesNo survived only because bool is a JSON type.
  • Fix: the validators now parse the ISO string themselves and return a real date/time, so strict-JSON, strict-Python and lax all agree.
  • Then the review found the natives had two contracts — authored inputs were pinned to extended ISO, model output was not. A new iso_temporal.py now owns what these natives accept, and both paths parse through it.
  • Three silent-corruption bugs fell out of that unification, including one that only appears on Python 3.14: "24:00:00" parsed as this day's midnight instead of the next day's.
  • Breaking Non-extended spellings authors could previously write ("15:40:00+0200", "2026-07-07T154000", "24:00:00", padded strings) are now refused.

1. The symptom

Reported from mthds-ui while adding native-concept fixture coverage. Deterministic, on every repeat, on the gateway backend:

Error generating single object with direct method in pipe 'read_one_time':
  1 validation error for TimeContent
  time
    Input should be a valid time [type=time_type, input_value='14:00:00+00:00', input_type=str]

Error generating list of objects with direct method in pipe 'read_dates':
  2 validation errors for ListOfDateContent
  items.0.date
    Input should be a valid date [type=date_type, input_value='2025-03-12', input_type=str]

Two things made this worth a careful look rather than a quick patch.

The input was correct. A JSON document has no date type, so "2025-03-12" is the only representation a model can produce — and the field's own description tells it to answer exactly that. And the same string worked from inputs.json. Identical value, identical field, opposite outcome depending on which door it came through.

The error code was the tell. Pydantic emits date_parsing when a lax coercion fails on a malformed string, and date_type when strict mode refuses a string outright. We were getting date_type on well-formed input, so something upstream was validating in strict mode.

Why nothing caught it. --mock-inputs fabricates real datetime objects, which sail past the broken path. So the method validated, dry-ran green, and failed on the first real call — the dry-run/live gap at its worst.

2. Root cause

Three facts had to line up.

  1. Instructor validates structured outputs strictly. Every create/create_with_completion signature defaults to strict: bool = True, and our workers never pass strict — so every provider's response is validated with model_validate_json(..., strict=True).
  2. Strict JSON mode would have been fine. Pydantic knowingly accepts ISO strings for date/time fields when the input is JSON, precisely because JSON has no temporal type. Plain datetime.date fields in user structures survive strict validation for this reason.
  3. A mode="before" validator destroys that acceptance. Its return value is re-validated as Python input — where strict refuses a str. The two temporal natives were the only ones carrying a before-validator on a non-JSON-native field.

We verified the mechanism in isolation, with no pipelex involved: a bare class Plain(BaseModel): date: datetime.date passes model_validate_json('{"date":"2025-03-12"}', strict=True); adding a no-op before-validator to the same field makes the identical call fail.

Why we did not just pass strict=False to instructor

It was the obvious one-liner and it was the wrong call. The blast radius is every provider and every user structure, not just these two classes — it would re-open the silent lax coercions that strict currently blocks on all LLM output, and weaken instructor's re-ask signal. Strict stays the inference-path policy; the natives were the smallest correct surface.

We also checked whether field-level Field(strict=False) could opt out locally. It cannot — the call-level strict=True wins.

3. The fix

Have the before-validators finish the job: after the existing guards, parse the string into a real object, so the inner validation always receives something already correct. That satisfies strict-JSON, strict-Python and lax alike.

     @field_validator("time", mode="before")
     @classmethod
-    def _reject_lax_temporal(cls, value: Any) -> Any:
+    def _validate_temporal(cls, value: Any) -> Any:
         ...guards: no bare number, no datetime...
+        # Returning a real object is what keeps this model valid under the strict validation
+        # instructor applies to every LLM response. Non-str values — real time objects, e.g.
+        # from `--mock-inputs` — pass through.
+        if isinstance(value, str):
+            return parse_iso_time(value)
         return value

That is the whole behavioural fix: about ten lines across the two validators. Everything below is what the review turned up once we started looking.

4. One contract, not two

The first review round asked a sharp question: the model path now parses ISO strings — which ISO strings? Because StuffContentFactory, which handles authored inputs, had already pinned itself to extended ISO for a documented reason, and the new model path had inherited none of it.

That mattered because fromisoformat is far more permissive than people expect. It accepts the basic spellings ("20260707", "154000") and the week and ordinal calendars ("2026-W27-2", "2026-189"). None of those corrupt a value, but all of them restate it in a calendar the source never used — and the all-digit ones collide with the epoch guard the natives depend on.

# pipelex/core/stuffs/iso_temporal.py
_EXTENDED_DATE_PATTERN = re.compile(r"\d{4}-\d{2}-\d{2}")
_EXTENDED_TIME_PATTERN = re.compile(r"(?P<hour>\d{2}):\d{2}(:\d{2}([.,]\d+)?)?([Zz]|[+-]\d{2}(:[0-5]\d)?)?")

Every character of that time pattern was argued for. Fractional seconds take . or , because ISO 8601 permits both. The offset takes Z, ±hh or ±hh:mm — but not ±hhmm, which is the basic spelling. And the offset minutes are range-checked in the pattern, for a reason worth its own section.

5. What the unification uncovered

Three of these were silent-corruption bugs. None was hypothetical — each was reproduced before we touched anything.

InputBecameShould beWhere
"24:00:00" 00:00 same day next day's midnight Python 3.14 only
"15:40:00+02:60" +03:00 rejected all versions
"2026-W27-2" 2026-07-07 rejected (right date, wrong calendar) model path only
"2026-07-07T154000" accepted rejected (model path already refused it) author path only

ISO 8601's 24:00 names the end of a day — that is, the next day's midnight. Python disagrees with itself about it:

# Python 3.13.9
>>> datetime.time.fromisoformat("24:00:00")
ValueError: hour must be in 0..23

# Python 3.14.0
>>> datetime.time.fromisoformat("24:00:00")
datetime.time(0, 0)          ← silently this day's midnight

Our requires-python is >=3.11,<3.15, so 3.14 is squarely in range. A Date carrying {"date": "2025-03-12", "time": "24:00:00"} would land on March 12th midnight instead of the 13th — a full day early, silently, on some of our supported interpreters and not others.

We reject it rather than rolling the date forward: a Time has no date to roll, and fixing only Date would make the two natives disagree. The error message names what the form means so an author can fix it. We verified the guard by loading the new module under both 3.13 and 3.14 — identical behaviour.

Worth noting what is not affected: datetime.fromisoformat("2026-07-07T24:00:00") rolls correctly to the 8th on 3.14. Two review bots claimed corruption there; the probe says otherwise. Only the bare time-of-day parse was at risk.

An offset's components are summed into a timedelta, so nothing range-checks the minutes:

>>> datetime.time.fromisoformat("15:40:00+02:60")
datetime.time(15, 40, tzinfo=timezone(timedelta(seconds=10800)))
                                                      ↑ +03:00

A stated offset silently becoming a different offset is precisely the fidelity loss these natives exist to prevent. What makes it easy to miss is that every neighbouring check works: an out-of-range offset hour raises, and the time's own minute and second raise. Only the offset minutes slip through, so the pattern pins them to [0-5]\d.

Round one routed the factory's bare-time path through the shared parser and declared the contract unified. It wasn't. _parse_iso_temporal still handed the whole string to datetime.fromisoformat, so the time half never reached the pin:

-        if not re.fullmatch(r"\d{4}-\d{2}-\d{2}([Tt ].*)?", value.strip()):
                                                  ↑ ".*" — anything goes after the T
-        parsed = datetime.datetime.fromisoformat(value)
-        return parsed.date(), parsed.timetz()
+        match = re.fullmatch(r"(?P<date>\d{4}-\d{2}-\d{2})(?:[Tt ](?P<time>.+))?", value)
+        the_date = parse_iso_date(match.group("date"))
+        the_time = parse_iso_time(time_text) if time_text is not None else None

So "2026-07-07T154000" was accepted from an author while {"date": …, "time": "154000"} was refused from a model. Splitting the string first — rather than delegating to datetime.fromisoformat — is what makes the time half reachable at all.

6. What we deliberately did not do

Three reported issues were declined. Recording them matters as much as the fixes, because each is the kind of thing that gets re-reported later.

Sub-microsecond precision is truncated

"15:40:00.1234567" becomes …123456. True — but datetime.time cannot represent more, so the only alternative is failing a live run over precision no real source states. Truncating to what the type holds is what every Python consumer of that string does. The natives' fidelity rules are about not inventing or shifting a value; sub-microsecond rounding is a different thing.

The numeric guard also matches nan / inf

is_numeric_string uses float(), which parses those tokens. They get the "no epoch-seconds" message rather than the malformed-ISO one. Both are rejected either way, no model emits them, and the proposed remedy — switch to int() — would make the accurate epoch message stop covering 8.64e4 and 86400.0, since int() raises on both.

Worth flagging honestly: the first version of this rationale claimed the swap would "reopen an epoch hole" and fail the suite. A reviewer challenged it and was right — with the extended pin in front of the parse, anything int() declines is rejected by the parser anyway. The decision held; the reasoning did not, and was corrected on the record.

The numeric-string guard itself, now that the pin exists

Nearly cut. The extended-form pattern rejects every all-digit spelling before fromisoformat is reached, so the string arm of that guard is no longer load-bearing — it only buys a better message ("never a number (no epoch-seconds)") in place of a generic one. We kept it and pinned the wording in a test, because a branch justified solely by its message and not asserting that message is a branch that can be deleted with the suite still green.

The int/float arm beside it is load-bearing: pydantic will happily coerce a bare 86400 into a date.

7. What changes for you

Breaking for authored inputs. These parsed on dev and are refused now. All four are non-extended spellings; if you have any in a bundle or an inputs.json, they will fail loudly with a message naming the expected shape.
No longer acceptedWrite insteadWhy
"15:40:00+0200""15:40:00+02:00"basic offset spelling
"2026-07-07T154000""2026-07-07T15:40:00"basic time spelling
"24:00:00"next day + "00:00:00"end-of-day form, ambiguous across Python versions
" 15:40:00""15:40:00"padding is not part of the value

Everything ISO calls extended still works, including the shapes a model plausibly answers: Z and lowercase z, +02 and +02:00, both fraction separators, and HH:MM without seconds.

Nothing changes for Python callers holding real date/time objects — they pass through the validators untouched, which is also why the --mock-inputs path was unaffected throughout. kajson round-trips were verified to still rebuild typed objects, so distributed execution is unaffected.

8. Testing

Both strict-mode test modules were written red-first and reproduce the reported failure verbatim before the fix. They cover the exact reported payloads under strict JSON, strict Python mode, the generated ListOf… wrapper, offset fidelity, real objects still accepted, and every rejection firing in both validation modes.

The independent final review mutation-tested them rather than trusting them: removing the parse call and flipping the 24:00 sentinel turned 23 tests red across the two modules. It also swept the time pattern's whole language — 560 pattern-admitted strings, zero of which fromisoformat then refused — confirming the round-4 bug class (pattern and parser disagreeing) is closed.
