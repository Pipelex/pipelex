## 1. The one-TestClass-per-module rule against the narrative multi-class layout

**Reporter:** Codex (`tests/unit/pipelex/cli/test_doctor_config_checks.py`, and by extension `test_doctor_display_report.py`, `core/test_validation_report.py`, `system/telemetry/test_telemetry_stale_remedy.py`) — [thread](https://github.com/Pipelex/pipelex/pull/1115#discussion_r3792986025).

`AGENTS.md` says one TestClass per module, and this PR broke it in four modules. Two of them (`test_doctor_config_checks.py`, `test_doctor_display_report.py`) had one class before the PR, and the branch folded the new tests back into it. The other two — `tests/unit/pipelex/core/test_validation_report.py` and `tests/unit/pipelex/system/telemetry/test_telemetry_stale_remedy.py` — were already multi-class before this PR, laid out as one class per concern with a narrative name (`TestNoValueFromAUsersFileIsEverRendered`, `TestTheRemedyIsNamedOnlyWhereItWouldWrite`), and the PR's added class followed each file's own layout. Dozens of modules across `tests/` are laid out the same way.

**Why deferred:** reworking modules whose layout predates the PR is not a review fix, and the two directions are genuinely different decisions. Either the rule holds — and those modules are split into one file per class (a mechanical sweep, but a large diff touching many modules the migrator work never opened) — or the narrative one-class-per-concern layout is accepted for a module that tests one seam from several angles, and `AGENTS.md` (which is generated — edit the source, not the file) is relaxed to say so.

**Recommendation:** decide once, repo-wide, rather than per PR. If the rule holds, sweep the two migrator modules first since they are the ones this branch touched, then the rest in a `chore/` PR of its own. Until then, a new test in an already multi-class module should follow that module's layout — mixing both styles in one file is the worst outcome.
