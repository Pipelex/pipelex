Killing documentation drift

The Drift Hunt campaign & the drift-contracts system — a recap for the team · July 2026

TL;DR

  • We did two complementary things about code↔doc drift. campaignA one-off Drift Hunt swept every hand-written docs page against the current code and fixed everything that had drifted — 104 pages, 1,439 claims checked, ~140 confirmed defects fixed, landed on dev through five reviewed PRs. systemA standing drift-contracts gate now prevents new drift: declared code→doc review obligations, mechanically enforced in make check and CI.
  • What changes for you day-to-day: if you touch a trigger file (the config model, CLI code, the keyword-only guard), make check fails with an open contract. Run make drift-plan, actually review the named doc pages, fix what's stale, git add your changes, then make drift-ack CONTRACT=… RATIONALE="…" and commit. There is deliberately no bypass flag — but “reviewed, no doc change needed” is a perfectly legitimate rationale and takes one minute.
  • Trust level of the docs today: every fix was re-verified against the code by an independent adversarial agent before being applied, every changed example re-validated against the real parser, and each fix batch survived a blind no-context review. Honest caveat: the cookbook pages were deliberately not swept (deferred).

The problem, in one sentence

Documentation rots silently: the code renames a method, a default flips, a CLI grows a flag — and the page that explains it keeps teaching the old world, with no error anywhere. The worst finding of the campaign made the cost concrete: a guide told users to implement observer hooks under names the protocol no longer has, so a user following it to the letter got a silent no-op — their monitoring code simply never ran, no exception, nothing.

Think of it as a stock-and-flow problem. The stock is the drift already accumulated in the pages; the flow is the new drift every future code change can introduce. The campaign drained the stock; the contracts throttle the flow.

campaignPart 1 — the Drift Hunt

A campaign, not a feature: sweep every hand-written page under docs/ (plus CONTRIBUTING.md, the agent instruction files, and friends) for statements the code can contradict — commands, flags, config keys, defaults, paths, API names, behaviors, and code snippets that should run. Editorial quality, tone, and structure were explicitly out of scope: a drift hunt, not a rewrite.

What actually drifts — the top defect classes
  1. Renamed Python API never propagated into docs — the #1 class across all sections, and the source of the worst silent failures (mis-named observer hooks, renamed execute/run methods, renamed factory functions).
  2. Doc bundle examples that fail real validation — examples that parse as TOML but fail semantic validation (missing required fields, illegal inline sigils, operator constraints). Dominant in the language guide.
  3. Stale closed enumerations — a list written once (native concepts, the operator roster, model handles), the registry grows, the list is never revisited. One stale operator roster was copied on three pages, including the docs landing page.
  4. Wrong defaults / behavioral claims — flipped defaults, wrong fallback directories, wrong indexing bases, invented behaviors.
  5. Keyword-only convention drift in snippets — docs showing positional calls that now raise TypeError under the repo's keyword-only convention.
  6. Repo-tooling drift — the distinctive class of the contributor pages: not one phantom make target, but targets whose behavior changed under a stable name (e.g. a test target that grew heartbeat output weeks after a page was written on the premise it was silent).
  7. False prose beside a correct snippet — the most uncomfortable class: a tutorial whose examples all validate and dry-run, while the sentence explaining them teaches a false rule. A snippet checker returns green here; only an adversarial reader catches it.
How we kept ourselves honest (the part worth stealing)
  • Adversarial verification before any action: no finding was acted on until a second, independent agent — prompted to refute it — confirmed it against the code with file:line evidence. Result: zero findings ever rejected downstream, so the pipeline's precision held.
  • False-negative spot-checks: since nothing was ever refuted, the real risk was under-reporting. So on every part, the "clean" verdicts on high-risk pages were hand-verified — and once, that check broke a clean verdict both the reviewer and the verifier had passed (the false-prose-beside-correct-snippet case). It became a standing step.
  • Blind post-fix reviews: after each fix batch, two reviewers with no context — just the commit SHA — re-reviewed the changes. They caught defects in three of the five reviewed batches, including one where the Stage-1 finding's own "correct" text was wrong. Rule learned: the code is the authority, even over the finding that points at it.
  • Run it, don't guess: live execution twice reversed a conclusion reached by reading — a CLI form "confirmed dead" from --help that a shortcut layer actually forwards, and a TOML construct "invalid" under a generic parser that the shipped loader accepts. Every changed example was re-validated against the real parser, load-bearing ones executed in dry-run.
  • Validate the whole snippet, not just the fixed clause: a finding scoped to one kwarg masked a surrounding example that never ran at all. After that lesson, every touched snippet was import-checked or executed end to end.
The headline lesson: drift follows audience, not complexity

The strongest pattern in the data is not what a page is about but who it is for. Pages whose author is also their reader — the maintainer-facing convention docs, the reliability pages written against the code — came back clean. Pages that explain something to someone else — onboarding, contributor setup, internals guides — drifted at up to 2 findings per page. And pages edited in the same commit as their code did not drift at all, which is precisely the behavior the contracts system forces. That correlation is where contract budget should go: reader-facing pages, not maintainer-facing ones.

systemPart 2 — drift contracts, the standing gate

Shipped just before the campaign, then hardened. A drift contract declares: when these trigger files change, these doc pages must be re-examined against the change, and the examination must be recorded. The tool can't judge whether prose is still true — that takes a human or an agent — but it can prove, deterministically, that someone looked at this exact content and said so on the record.

Three tiers — contracts are only the last resort

TierMechanismJudgment needed
DerivedRegenerate and diff (config sync, schema, gateway models, error pages)None — output is a pure function of sources
LinkageReferential integrity of declared cross-references (spec ↔ conformance links)None — links resolve or they don't
ReviewDrift contracts: "this changed → that must be looked at, and the look recorded"Yes — someone must judge whether the prose still holds

Standing rule: anything mechanizable gets demoted into a derived check. The best review contract is one you eventually mechanize out of existence.

The one rule everything hangs on

A contract is fulfilled iff the stored ack digest equals the digest recomputed from the current tree. Otherwise it is open.

No base ref, no git diff, no timestamps — pure content equality. The digest covers the (path, blob OID) of every tracked file matching the contract's triggers, plus the contract's own definition. Edit a trigger file, add or delete a matched file, or edit the contract itself — it opens. And the digest reads the git index, not the working tree, which is what lets the ack land in the same commit as the change it certifies.

The lifecycle, end to end

Where it acts, surface by surface

SurfaceWhat happens there
Make targetsmake drift-check (dc) is the pass/fail gate; make drift-plan (dp) prints one packet per open contract — what changed, what to review, the previous reviewer's rationale; make drift-ack CONTRACT=… RATIONALE="…" (da) records the review, running the contract's verify_commands first.
Quality checksdrift-check runs inside the make check aggregate — a full local check cannot pass with an open contract. It also hard-fails on manifest rot (dead globs, orphan acks, shadowed triggers), so a rename that kills a trigger pattern is caught on the same PR.
Commitsdrift ack writes the ack file and stages it, into the same index the check reads — so the code change, the doc fix, and the ack land in one commit, reviewed as one diff. If staging fails, the ack is rolled back rather than left as a false green.
Branches / mergesTwo branches re-acking the same contract may or may not conflict textually — irrelevant either way, because after the merge the digest is recomputed over the merged tree, and a spliced or stale ack simply fails until re-acked.
PRs / CIA lint-drift CI job runs the check on every PR — currently advisory (visible, not merge-blocking; promotion to a required check is planned once the open-PR backlog lands). The committed ack appears in the PR diff, so the reviewer sees the rationale right next to the change it covers.

The pieces on disk

  • drift.toml (repo root, human-authored) — the manifest. Each contract: triggers (globs), optional exclude, review targets, optional verify_commands. Live today: config-docs (config model + shipped defaults → configuration docs, verified by a boot test), cli-docs (CLI source → CLI docs + the agent-CLI contract doc), keyword-only-convention (the guard's source → its specification page).
  • .drift/acks/<contract-id>.toml (tool-written, committed) — the last fulfilled review: digest, reviewer, timestamp, rationale, per-file trigger snapshot.
  • pipelex-dev drift plan|check|ack — the engine the make targets wrap.
Why there is deliberately no bypass

drift ack has no --skip-verify and drift check has no override label. Every escape hatch is a rubber-stamp invitation — and the legitimate escape already exists: acking with a rationale that says “reviewed, no doc change needed” is cheap, honest, and auditable. If a contract opens so often that acking feels like ceremony, the contract is mis-scoped: narrow its triggers, or mechanize it into a derived check. The manifest is kept deliberately small — contracts are added where staleness has actually hurt, and the campaign's density data is exactly the evidence for where that is.

One hardening detail worth knowing: for a contract with verify_commands, an unstaged edit or untracked file matching the triggers is a hard error, not a warning — the verify commands run on the working tree, so they would otherwise certify content the digest doesn't cover. The check runs both before the verify commands (fail fast) and after them (catching files the verify commands themselves regenerate).

How the two halves reinforce each other

The campaign wasn't just cleanup — it was an evidence-gathering run for the contract system. Every finding logged an observation about whether a contract or a derived check would have caught it. The resulting shortlist feeds the system's pilot verdict:

  • Best derived-check candidates: diff documented closed enumerations against the code's registries; validate doc bundle examples against the real parser (with placeholder scaffolding injected); import-and-check every Python symbol a doc references.
  • Best contract candidate: make-targets-and-tooling — every documented target exists, so no script scores a single point; what drifts is behavior under a stable name. Un-mechanizable, judgment-only: exactly what a review contract is for.
  • Known limit of any snippet checker (proven the hard way): it verifies the snippet, never the sentence beside it. A green check must not be read as a clean page.
Open follow-ups after this recap
  • Pilot verdict per contract (keep / narrow / mechanize / drop), fed by the campaign's shortlist and the per-ack dogfood log.
  • Promote the CI job from advisory to required, once the open-PR backlog has landed (a required check would instantly fail every PR predating its acks).
  • Deferred code-side findings — the hunt surfaced defects whose fix belongs in code, not docs (e.g. an error message whose remediation names config fields that don't exist; a dependency floor that admits a parser too old for the documented syntax). They're recorded with evidence and candidate fixes, to be picked up as ordinary follow-ups.
  • The cookbook sweep, if ever revived — the reusable review harness (rules, carve-outs, verification pipeline) is archived and ready.
