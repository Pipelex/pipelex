> **A different page shape, so a different hunt.** Parts 1–2 were snippet-dense (bundle examples, Python API calls). These are short capability / landing pages — 20–130 lines, almost no code fences — whose claims are *prose*: capability assertions, closed enumerations of operators / providers / commands, and config keys with default values. Stage 0's mechanical pre-screen found **zero** suspect rows in both sections, so every page started seedless; the seeds were hand-built from the Part 1/2 defect classes instead.
>
> **Two new review rules were needed** (baked into both the review and verify prompts, alongside the blessed FP list and the D11 carve-out):
> - **Exhaustive vs illustrative lists.** For a closed list ("the six operators are …"), a *shipped member missing from it* is drift — the sentence is factually false. For a hedged list ("such as", "and more"), only a *named member that doesn't exist* is drift; an omission is a completeness wish, which is out of scope. Ambiguous ⇒ treat as illustrative. This rule is what separates the real findings below from editorial noise, and it is directly responsible for F2 / F8 / F9.
> - **Floor counts.** "60+ models" is a floor, not an exact count — false only if the real deck is *below* it. (It isn't; `gateway.md` is clean.)
>
> **Cross-repo and product guardrails** (to prevent false positives, all held): `plxt` and the Claude Code skills plugin are documented here but ship from sibling repos (`vscode-pipelex`, `mthds-plugins`) — reviewers ran the real `plxt` binary and read the real plugin repo rather than declaring them phantom. The distributed/durable-execution pages got the settled rulings: orchestrator plugins are private and deliberately not on PyPI (so "no install instructions" is not drift), and Temporal wire-format/version-skew is out of bounds.

> **False-negative spot-checks (hand-verified after the run, because a clean sweep is the suspicious result here).** The pages I had seeded as *highest* carry-in risk all came back clean, so I re-checked them by hand: `automatic-retries.md`'s three config claims match the shipped config exactly (`[cogt] transport_max_retries = 2`, `[cogt.llm_config] schema_reask_max_attempts = 3`, `[pipelex.pipeline_execution_config] max_concurrency = 8` — `pipelex/pipelex.toml:136,147,301`); `telemetry.md` never mentions the fabricated `telemetry_mode` (Part-2 F24) — it names Langfuse / OTLP / PostHog, all real; `cost-tracking.md`'s Python snippet imports cleanly (`render_cost_report_for_output`), i.e. it does *not* carry the `set_reporting_delegate` rename (Part-2 F37); `deepseek-ocr` in the `index.md` extract list is a real gateway extract protocol (`pipelex/plugins/gateway/gateway_protocols.py:9`). **The low density is real, not guardrail suppression.**

## Findings by page (worst-first)

### `features/configuration.md` — 3 finding(s)

**F3 · 🔴 breaks-a-user**
- **Doc:** `docs/features/configuration.md:26` (the `## Environment Variables` section, directly after the `## Configuration Levels` list)
- **Claim:** Use `${VAR_NAME}` syntax **in TOML files** for dynamic config from env vars and secrets — `${env:VAR}`, `${secret:VAR}`, and fallback chains like `${env:VAR|secret:VAR}`.
- **Reality:** That substitution is wired into exactly **two** config files — `telemetry.toml` and `inference/backends.toml` — and **nowhere else**. It does *not* apply to the `pipelex.toml` / `pipelex_local.toml` / `pipelex_{env}.toml` layering chain the page itself just described one section earlier. A reader who puts `${env:VAR}` in their `.pipelex/pipelex.toml` gets the **literal placeholder string**, unresolved.
- **Code evidence:** `pipelex/tools/secrets/secrets_utils.py:22` defines `substitute_vars()`; its only call sites are `pipelex/system/telemetry/telemetry_config.py:282-284` and `pipelex/cogt/model_backends/backend_library.py:90-105`. Nothing under `pipelex/system/configuration/` calls it. **Reproduced live:** a scratch `.pipelex/pipelex.toml` with `bucket_name = "${env:MY_TEST_BUCKET_ENV}"` (env var set) loaded via `ConfigLoader().load_config()` returned the literal `'${env:MY_TEST_BUCKET_ENV}'`.
- *The page's placement is what makes this breaks-a-user: the syntax is presented as a general property of "TOML files" immediately below the list of config files it does not work in.*

**F4 · 🟠 wrong**
- **Doc:** `docs/features/configuration.md:20`
- **Claim:** Environment / run-mode-specific files — `pipelex_dev.toml`, `pipelex_prod.toml`, **`pipelex_testing.toml`**, etc.
- **Reality:** `pipelex_testing.toml` is not a filename the loader ever reads. "testing" is neither a `RunEnvironment` (`local`/`dev`/`staging`/`prod`) nor a `RunMode` (`normal`/`unit_test`/`ci_test`/`codex_cloud`/`codex_cloud_test`), so such a file is **silently ignored**.
- **Code evidence:** `pipelex/system/runtime.py:67-71` (RunEnvironment) and `:43-48` (RunMode); the loader builds `pipelex_{environment}.toml` / `pipelex_{run_mode}.toml` at `pipelex/system/configuration/config_loader.py:190-194`. `grep -rn "pipelex_testing"` across the repo returns **only this doc line**.

**F5 · 🟡 misleading**
- **Doc:** `docs/features/configuration.md:16-20`
- **Claim:** A numbered precedence ladder: 1 base defaults → 2 global overrides (`~/.pipelex/pipelex.toml`) → 3 project overrides (`{project_root}/.pipelex/pipelex.toml`) → 4 local overrides (`pipelex_local.toml`) → 5 environment/run-mode-specific.
- **Reality:** The ladder implies `pipelex_local.toml` and the env-specific files *always* outrank a project's own `pipelex.toml`. In truth the split is **global tier vs project tier**, not base-vs-override: the *entire* global tier (including a global `pipelex_local.toml`) is merged **before** the project tier, so a plain project `pipelex.toml` **overrides a global `pipelex_local.toml`**. Only a *project-scoped* local/env file outranks the project base.
- **Code evidence:** `pipelex/system/configuration/config_loader.py:280-295` (docstring) + `:311-337` (implementation). **Reproduced live:** global `~/.pipelex/pipelex_local.toml` (`GLOBAL_LOCAL_OVERRIDE`) vs project `.pipelex/pipelex.toml` (`PROJECT_BASE`) → merged result was `PROJECT_BASE`.

### `features/plxt.md` — 1 finding

**F10 · 🟠 wrong**

## Dogfood observations (feed the drift-contracts Phase 3 verdict, per D5)

1. **Stale closed enumerations are this part's dominant class** — 4 of 10 findings (F2 native concepts 11/15; F8 + F9 operators 6/7; F7 a retired model still listed). Every one is **mechanically detectable**: the doc's list is a closed set, and the truth is a registry/StrEnum/deck file in the tree. This is the strongest new drift-contract candidate of the campaign so far → **`doc-enumerations-vs-registry`**: diff documented closed lists against `NativeConceptCode`, the `pipe_operators/` package (blueprints with `pipe_category="PipeOperator"`), the pipe *controllers*, and the shipped model deck. The check's hard part is not the diff, it is **deciding which lists are closed** — the exhaustive-vs-illustrative rule this part had to invent would have to be encoded (e.g. only lists without a "such as"/"including"/"and more" hedge are checked).
2. **Capability pages drift *less* than internals pages** — density 0.40 vs 1.26 / 1.62. Worth stating plainly in the close-out: the sections that most look like marketing surface are the *least* drifted, and the deep technical pages are the worst. A contract budget should follow the defect density, not the page's visibility.
3. **The reliability section is the campaign's clean-room** — 44 claims, 0 findings, including a page (`automatic-retries.md`) that hard-codes three config keys *with their default values* and a list of which SDK clients receive the retry budget. It is the strongest evidence yet that a page written *against the code*, recently, stays true — and a good candidate to hold up as the model when writing the close-out.
4. **A "clean" wave is the result that most needs adversarial follow-up.** The false-negative spot-checks (see the header note) were the right instinct: 0 findings on the highest-risk seeded pages would have been the campaign's most likely place to have fooled itself. They held — but the protocol should be explicit for Part 4: *when a page you seeded as high-risk comes back clean, hand-verify at least one of its load-bearing claims before believing it.*
