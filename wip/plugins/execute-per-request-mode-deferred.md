# Deferred / flagged items — `/execute` honors per-request `execution_mode`

Companion to `execute-per-request-execution-mode.md` (the plan). Captures findings surfaced while implementing **Phase E0** that were deliberately **not** acted on, plus pre-existing drift that the implementation absorbed. None block the feature.

## 1. DIRECT dispatch does a serialize→rehydrate round-trip (accepted tradeoff, not a bug)

`/execute` now dispatches every mode — including `direct` — through the `OrchestratorRegistry`. The orchestrator answers with the JSON-safe `PipelexPipeRunOutput` (the same shape that crosses the Temporal worker boundary, via `serialize_completed_output`), so the synchronous `/execute` path rehydrates it back into a rich `PipeOutput` (`_pipe_output_from_run_output` in `api/routes/pipelex/pipeline.py`). For `direct` this means the working memory is `dump_for_temporal()`'d and then `hydrate_working_memory()`'d **in-process** — one redundant re-serialization the old boot-slot path didn't pay.

**Why accepted:** it keeps `/execute` on the *same* per-call dispatch seam as `/start` and `/validate` (no per-mode branch), which is the whole point of the locked decision. The cost is bounded (one extra round-trip of a working memory that `/execute` already serializes once for the HTTP response).

**If it ever matters:** the clean fix is at the *contract* layer, not here — e.g. let `OrchestratorProtocol.run` optionally hand back the rich `PipeOutput` for the in-process arm so the DIRECT path skips the round-trip. That's a core (`pipelex`) change to a shared SPI, out of scope for this single-repo plan. Don't special-case DIRECT inside `pipelex-api` (that reintroduces the per-mode branch the seam removed).

## 2. `graph_spec` / `tokens_usages` reconstruction needs `strict=False` (correct, worth knowing)

`serialize_completed_output` dumps `graph_spec` / `tokens_usages` with `model_dump(mode="json")`, and those models are `strict=True` (e.g. `GraphSpec.created_at: datetime`). A strict re-validation of the JSON dump fails (str→datetime is rejected in strict mode — confirmed empirically). `_pipe_output_from_run_output` therefore validates with `strict=False`, which is the correct tool for reversing our *own* trusted JSON dump (a round-trip, not untrusted ingest). Nothing else in the tree rehydrates these dump fields today, so there was no prior precedent to copy — flagged here so a future reader doesn't "tighten" it back to strict.

## 3. Pre-existing `/start` DIRECT-path resource leak (flagged, NOT fixed — out of scope)

While mirroring `start`, noticed that `ApiRunner.start` calls `pipeline_run_setup(...)` then the orchestrator, with **no** teardown on the success path. `pipeline_run_setup` only tears the run library / pipeline-manager entry down on its *error* path; `PipeRun.run` closes the tracer but not the library or the pipeline-manager registration. The base `PipelexMTHDSProtocol.execute` does that teardown in its `finally`. So on the **DIRECT** `/start` success path (reachable on the agnostic base, where `start` runs in-process and blocks), the run library and its pipeline-manager entry appear to leak per request.

`/execute` does **not** have this problem: this change delegates to the base `execute`, inheriting its full teardown. The finding is purely about `/start`.

**Not fixed here** because it touches `/start` (a different surface) and the plan is scoped to `/execute`. Worth a small follow-up: give `ApiRunner.start` the same lifecycle guarantees (or factor the base `execute`'s setup+teardown into a shared context manager both `execute` and `start` use). Verify first that it is a genuine leak and not cleaned up elsewhere before changing `/start`.

## 4. Absorbed pre-existing drift from the `/validate` work (informational)

The committed `docs/openapi/pipelex-api.openapi.yaml` and `docs/configuration.md` at the validate tip (`72c0efc`) were **stale** w.r.t. the `/validate`-by-`execution_mode` work: the OpenAPI artifact lacked the `PipelexExecutionMode` component + the validate request's `execution_mode` field, and `configuration.md` still said `/validate` "always runs in-process and ignores this setting." Both are regenerated/corrected in this change (the OpenAPI artifact is generated, so it must match the current app exactly; the config doc was rewritten holistically for `/execute` + `/start` + `/validate`). Mentioned so the diff's validate-flavored hunks aren't mistaken for execute-scope creep — they are pre-existing drift this change necessarily resolves.

## 5. Reverse helper location — altitude (independent review, deferred)

`_pipe_output_from_run_output` is the exact inverse of `serialize_completed_output` (which lives in `pipelex/runtime_bridge/serialization.py`), but the reverse currently lives as a private function in the `pipelex-api` route module. If `PipelexPipeRunOutput` gains/renames a field, forward (pipelex) and reverse (pipelex-api) could drift independently. **Deferred:** single consumer; moving it crosses a repo boundary; and the reverse must run *inside* the still-open run-library scope (a precondition naturally satisfied at this call site). Confirmed no existing reverse helper is being reinvented (`rehydrate_pipe_output_with_crate` operates on a `PipeOutput.working_memory_raw`, not a `PipelexPipeRunOutput`; the new helper correctly reuses `hydrate_working_memory`). Promote to a `deserialize_completed_output` in `serialization.py` only if `pipelex-temporal`'s blocking path ever needs the same reverse.

## 6. OpenAPI request schema doesn't advertise the `execution_mode` body extra

`/execute`, `/start`, and `/validate` all honor a per-request `execution_mode` override, but the override is parsed from the raw kajson body as a `PipelineApiExtras` extra, so the *generated* OpenAPI request schema only lists it where the route uses a typed body model.

**`/execute` half — RESOLVED (PR #27 review fix).** `/execute`'s `openapi_extra` now documents a new `PipelexApiExecuteRequest(RunRequest)` schema (mirroring the existing `PipelexApiStartRequest` pattern) that declares `execution_mode`, reusing the shared `_EXECUTION_MODE_DESCRIPTION` already on `PipelineApiExtras.execution_mode` (factored to a module constant so the two can't drift). The committed OpenAPI artifact was regenerated; the drift check (`scripts/export_openapi.py --check`) is green. Greptile (P1) / Codex (P2) flagged exactly this gap on `/execute` — the route reads `extras.execution_mode` and honors it, but the published schema (`RunRequest.model_json_schema()`) omitted the field.

**Dangling `#/$defs/` ref for the advertised enum — DEFERRED (pre-existing artifact-generation pattern).** A follow-up Codex pass (P2) noted that `/execute`'s newly-advertised `execution_mode` references `#/$defs/PipelexExecutionMode`, which a root-based OpenAPI resolver can't dereference (the document has no top-level `$defs`; the enum also exists at `#/components/schemas/PipelexExecutionMode`). This is a **pre-existing pattern**, not introduced here: both `/execute` and `/start` already emit dangling `#/$defs/StuffContentAbstract` and `#/$defs/WorkingMemoryAbstract_Any_` refs, because both parse the body through the raw `Request` and supply their schema via `openapi_extra: <Model>.model_json_schema()` — FastAPI hoists nested defs into `components/schemas` only for *typed-body* routes (like `/validate`), not for a manually-supplied schema dict. My `execution_mode` ref is consistent with the existing dangling refs on the same endpoint. Fixing only `execution_mode` would leave it inconsistent with its siblings and still not make the endpoint's schema resolvable; the clean fix is a cross-endpoint OpenAPI-generation improvement (hoist each `openapi_extra` schema's `$defs` into `components/schemas` and rewrite the refs, or move `/execute` + `/start` to typed bodies) — a separate change spanning both endpoints, out of scope for this PR. Tracked here.

**`/start` half — STILL DEFERRED (scope).** `/start`'s `PipelexApiStartRequest` schema *also* omits `execution_mode` (it extends `RunRequest` and only redeclares `callback_urls`; the field lives on `PipelineApiExtras`). That gap is **pre-existing** — `/start`'s `execution_mode` consumption was introduced by the F1 work, not by PR #27, whose diff touches only `/execute`. Not fixed here to honor scope discipline. The clean fix is the same one-liner pattern: have `PipelexApiStartRequest` redeclare `execution_mode = Field(default=None, description=_EXECUTION_MODE_DESCRIPTION)`, then regenerate the artifact. Note: the published `make openapi-export` target does not exist in `pipelex-api`'s Makefile; regenerate by running `.venv/bin/python scripts/export_openapi.py docs/openapi/pipelex-api.openapi.yaml` (write) and `--check` to verify. Never hand-edit the yaml.

## 7. `is_completed` invariant the synchronous path relies on (independent review, rejected-as-fix)

`_pipe_output_from_run_output` unconditionally builds a completed `PipeOutput` without checking `run_output.is_completed`. **Rejected as a fix** (not a bug): `/execute` refuses fire-and-forget upfront with a 400, and every non-f&f orchestrator today (`DirectOrchestrator`, `TemporalBlockingOrchestrator`) returns `is_completed=True`, so a `False` here is unreachable — guarding it is a defensive check for an impossible-today scenario. Recorded only so a future orchestrator author knows the invariant the synchronous path assumes.

## 8. Worker-dispatched (`temporal_blocking`) rehydration is unexercised here (pre-landing review, INVESTIGATE — out of scope)

The adversarial pre-landing review traced the `temporal_blocking` arm: a worker runs the pipe and returns a `PipelexPipeRunOutput` whose `output_dict` carries `__pipelex_class__` markers for any dynamic concept classes registered **on the worker**. `_pipe_output_from_run_output` then calls `hydrate_working_memory` against the **API-side** run library's class registry. This resolves correctly *because* `pipeline_run_setup` already loaded the same bundle API-side (the rich `PipeJob` is built locally before dispatch, registering the same dynamic concept classes) — the same property `/start` and `/validate` already rely on for their worker-dispatched arms. So `/execute` introduces **no new** boundary risk: it reuses the shared `PipelexPipeRunOutput` contract and the same `hydrate_working_memory` round-trip.

**INVESTIGATE, not fixed:** this path cannot be exercised on the orchestrator-agnostic base (no `pipelex-temporal` installed; `test_execute_dispatch.py` covers DIRECT only, with a stub orchestrator that round-trips through the real `serialize_completed_output` → `hydrate_working_memory`). End-to-end coverage of the `temporal_blocking` `/execute` rehydration belongs in `pipelex-temporal`'s own test suite (where the blocking orchestrator and a real worker exist), alongside the analogous `/start` / `/validate` worker-path tests. Out of scope for this single-repo `pipelex-api` PR. Verify there when the hosted-Temporal flavor lands; reinforced by the runtime constraint in `validate-dispatch-requires-boot-active.md` (a `temporal_*` `/execute` on a runner not booted under Temporal fails the same way a temporal-mode `/start`/`/validate` does).

## 9. Failing-pipe `/execute` now yields a double-wrapped error message + unwound `pipe_stack` (pre-landing review, DEFERRED — seam tradeoff, cross-endpoint)

The adversarial pre-landing review traced how a *failing* pipe surfaces differently after the dispatch change. Verified against source:

- **Old `/execute`** ran the pipe through the boot slot (`get_pipe_run()` → `PipeRun.run`), which observe-and-reraises the original `PipeRouterError` (`runner.py` core, `pipe_run.py: raise execution_error`). The base `execute`'s `except PipeRouterError` arm then built `PipelineExecutionError(message=exc.message, pipe_stack=exc.pipe_stack)` — the raw router message and the **failure-site** pipe-stack snapshot.
- **New `/execute`** runs through `DirectOrchestrator.run`, which catches `PIPE_DISPATCH_ERRORS` and re-raises `PipelexBridgeDispatchError("Pipe execution failed in DIRECT mode for pipe 'X': <original>")` (`direct_orchestrator.py`). That no longer matches `except PipeRouterError`, so it falls to the base's `except PipelexError` arm → `PipelineExecutionError(message=exc.message, pipe_stack=pipe_job.pipe_run_params.pipe_stack)`. Net: the operator-facing **message gains the "in DIRECT mode" wrapper** and the **`pipe_stack` is the unwound live stack**, not the failure-site snapshot.

**Not a wire-status / classification regression.** `error_domain` / `http_status` / `error_category` survive because `PipelexBridgeDispatchError.to_error_report()` enriches from the full `__cause__` chain, and `pipe_stack` is not an `ErrorReport` wire field. So a machine consumer sees the same `is_valid`/status/error-domain; only the human-readable `message` wording and log-stack fidelity change.

**DEFERRED, not fixed** — it is a property of the **orchestrator seam, not of `/execute`**: the seam deliberately funnels every mode's pipe failure through the single `PipelexBridgeDispatchError` type so a host catches one error regardless of backend. `/start` (also routed through `DirectOrchestrator`) and the dispatched `/validate` already exhibit the identical wrapping (the agent's symmetric finding: `/start` and `/execute` now render different `message`/`title` for the same underlying pipe failure than the legacy boot-slot path did). Harmonizing the wording — or restoring the failure-site `pipe_stack` for the DIRECT arm — is a change to the **shared seam spanning all three surfaces** (e.g. have `DirectOrchestrator` re-raise the original `PipeRouterError` so the base's precise arm still fires, or teach the base `except` to unwrap a `PipelexBridgeDispatchError` cause), not a `pipelex-api`-local `/execute` edit. Out of scope for this PR; no shipped Temporal flavor means no prod error-shape contract is at risk. Worth a small follow-up if product wants byte-identical error bodies across `/execute` / `/start` and parity with the legacy message.
