Pipelex Plugin System & Temporal Externalization

What we built, why, and where it stands — a guide for co-developers · branch refactor/Plugins-3

TL;DR

We turned Pipelex's two families of optional integrations — inference backends (Anthropic, OpenAI, Mistral, Google, Bedrock, FAL, …) and execution orchestrators (Direct, Temporal, Mistral Workflows) — into a real plugin system, so that core names no integration anywhere: not by import, not by a match string. Every backend and orchestrator now registers itself into a hub registry through one tiny contract.

  • The mechanism: a PipelexPlugin contract + a PluginRegistrar menu + build_registrar() discovery over built-ins and pipelex.plugins entry points. Core looks plugins up in registries on the hub; it never branches on a vendor name.
  • The payoff: Temporal became its own distribution, pipelex-temporal, discovered purely via an entry point. Core has no temporal extra and imports no temporalio at boot.
  • Status: Phases 0–5 are done, committed, and pushed on both repos; all gates green. What remains is downstream wiring. pipelex-temporal is a private dist (not on PyPI): our hosted infra pins it via git+ssh, and the public packages drop the temporal coupling. Gated on the hosted-Temporal rollout, not a package publish.

1 · The problem we set out to kill

Pipelex core used to hard-code every optional integration behind a match statement. Adding a backend meant editing core; an optional SDK could be imported at the wrong time; and Temporal — a heavy, optional dependency — was woven through the core runtime. The coupling lived in a handful of seams:

Seam (where core named an integration)File(s)How it's resolved now
Inference dispatch — 4 families (LLM, image-gen, extract, search)cogt/{llm,img_gen,extract,search}/*_worker_factory.pyInferenceBackendRegistry.lookup(family, sdk)
Model listing (the show models path)cogt/model_backends/model_lists.pyModelListerRegistry.get_optional(sdk)
Orchestrator dispatch (Direct / Temporal / Mistral)runtime_bridge/bridge.pyOrchestratorRegistry.get_optional(mode)
Boot / teardown hub-swap (Temporal runtime)pipelex.pyhub-slot claims + LIFO teardown callbacks
Config schema + CLI commandsconfigs.py, cli/_cli.pyschema relocated to core; ops commands → console script

Every row above used to contain a vendor or temporalio name. After the refactor, the only place an integration name appears in core is typed config and prose comments.

2 · The design — one contract, one registrar, one discovery pass

A plugin is a tiny object with a register method. Discovery hands it a registrar (a menu of "I provide X" methods); the registrar accumulates contributions into registries that get installed on the hub at boot. That's the whole machinery.

The contract

# pipelex/plugins/contract.py
PLUGIN_API_VERSION: int = 1

@runtime_checkable
class PipelexPlugin(Protocol):
    name: str
    targets_api: int
    def register(self, registrar: "PluginRegistrar") -> None: ...
    # INVARIANT: register is side-effect-free — it may ONLY call registrar
    # menu methods. No hub access, no I/O, no SDK/client construction.
    # Heavy work happens lazily inside the closures register hands over.

The discovery → boot flow

What the registrar offers

Menu methodContribution
add_inference_backend(family, sdk, make_worker)a backend driver, keyed by (family, sdk)
add_orchestrator(mode, orchestrator)an execution strategy, keyed by execution_mode
add_model_lister(sdk, lister)an optional model-listing capability
claim_content_generator / pipe_router / pipe_run / task_manager(factory)a hub-slot claim — a deferred thunk, run only if the slot is taken
add_teardown(callback)a teardown hook, run LIFO at shutdown

plugins/anthropic/anthropic_plugin.py — a whole backend in one small file. register is trivial and import-light; the closure does the heavy lifting lazily.

def _make_anthropic_worker(*, inference_model, backend, sdk_clients, reporting_delegate):
    require_sdk(spec="anthropic", extra="anthropic", msg=_ANTHROPIC_MISSING_MSG)
    from ...anthropic_factory import AnthropicFactory   # lazy: no SDK at boot
    from ...anthropic_llm_worker import AnthropicLLMWorker
    model_handle = ModelHandle.make_for_inference_model(inference_model=inference_model)
    sdk_instance = sdk_clients.get_or_create(handle=model_handle,
        build=lambda: AnthropicFactory.make_anthropic_client(model_handle=model_handle, backend=backend))
    return AnthropicLLMWorker(sdk_instance=sdk_instance, ...)

class AnthropicPlugin:
    name = "anthropic"
    targets_api = PLUGIN_API_VERSION
    def register(self, registrar):
        registrar.add_inference_backend(family=InferenceFamily.LLM, sdk="anthropic",         make_worker=_make_anthropic_worker)
        registrar.add_inference_backend(family=InferenceFamily.LLM, sdk="bedrock_anthropic", make_worker=_make_anthropic_worker)
        registrar.add_model_lister(sdk="anthropic", lister=_list_anthropic_models)

One plugin can serve several (family, sdk) keys and several families at once (Mistral registers into both LLM and Extract; Linkup into both Extract and Search).

4 · What ships in core today

Core ships a list of built-in plugins. Importing this module imports no backend SDK — the SDKs load lazily inside the make_worker closures.

# pipelex/plugins/builtins.py
BUILTIN_PLUGINS: list[PipelexPlugin] = [
    DirectOrchestratorPlugin(),                                  # core orchestrator
    OpenAIPlugin(), GatewayPlugin(), PortkeyPlugin(), AnthropicPlugin(),
    MistralPlugin(), BedrockPlugin(), GooglePlugin(), FalPlugin(),
    HuggingFacePlugin(), BlackboxaiPlugin(), OpenRouterPlugin(),
    AzureRestPlugin(), DoclingPlugin(), Pypdfium2Plugin(), LinkupPlugin(),
]
# Naming one of these in plugins.disabled is a config error, not a no-op:
CORE_UNCONDITIONAL_PLUGIN_NAMES = frozenset({"direct", "openai"})

Between them these built-ins register every (family, sdk) inference backend across the four families. direct owns the in-process execution mode; openai is the always-on default driver. Observability: pipelex plugins list shows what's discovered, what each registered, and the denylist state.

5 · Temporal as an external plugin

Phase 5 lifted pipelex/temporal/ into a sibling distribution, pipelex-temporal (top-level package pipelex_temporal). It depends on core; core depends on nothing Temporal. Installing the dist makes the TEMPORAL_* orchestrators appear by discovery — no core change, no config.

The key prerequisite (Step 0b): why the config schema had to move first

Core config (configs.py) imported the Temporal config schema, which lived under pipelex.temporal. You cannot "keep config in core, move temporal/ out" while core config imports from temporal/. So the schema (config_temporal.py) and the two exceptions it raises were relocated into core (pipelex/system/configuration/{config_temporal,exceptions}.py), re-based on PipelexError. After this, the last hard pipelex.temporal import in core was gone — and the move became pure packaging. The RetryPolicy field aliases to Any at runtime so the schema validates without importing temporalio.

A latent bug surfaced and was fixed along the way: a (ValueError, PipelexError) MRO meant ValueError.__init__ won and .message was never set. Bases were reordered to (PipelexError, ValueError), with a regression test sweeping every PipelexError subclass.

"Option A": why operational commands are a console script, not a plugin contribution

An earlier design harvested plugin-contributed CLI commands by running discovery at CLI-build time, on every pipelex invocation. A review found this brittle: one broken or colliding external plugin (or an unreadable user config) could brick every command — including the --help/doctor/plugins recovery commands. We removed the surface instead of hardening it. Temporal's worker and setup-namespace now ship as a standalone pipelex-temporal console script ([project.scripts]), so pipelex --help no longer loads config or scans entry points, and a third party can't shadow a core command.

6 · The invariants that hold every phase

Import-light boot. Booting with built-ins registered imports no optional SDK (anthropic, mistralai, boto3, fal_client, …) and no temporalio. Enforced by a subprocess test with a sys.meta_path finder that raises on those modules — boot must not trip it.
Side-effect-free register. A plugin's register may only call registrar menu methods — no hub access, no I/O, no client construction. This is what makes discovery a pure, repeatable function.
Fail loud. Duplicate (family, sdk) / duplicate mode / a double-claimed slot / an API-version mismatch / a broken entry point each raise a named, contextual error. A missing backend says "install X" — it never dereferences None.

Presence vs activation (so you don't add a flag that shouldn't exist)

QuestionAnswer
Is a plugin present?It's in BUILTIN_PLUGINS or an installed dist exposes the pipelex.plugins entry point. Zero config.
When does an inference backend activate?By data — a model names its sdk; the registry resolves it.
When does an orchestrator activate?Per call — the request's execution_mode selects it.
When does the Temporal runtime boot?Only when temporal.is_enabled — a per-process "boot as a Temporal worker" gate, not a generic on/off toggle.
Can I turn a plugin off?A narrow plugins.disabled denylist (can't disable a core-unconditional plugin). There is deliberately no redundant allowlist.

What's left — downstream wiring (private dist; gated on the hosted-Temporal rollout)

pipelex-temporal is private / not open-source, so it is not published to PyPI. It travels by a pinned git+ssh reference — exactly how this workspace already pins pipelex-shared (… @ git+ssh://git@github.com/Pipelex/infra-python-tools.git@<ref>).

  1. Tag a release in the private pipelex-temporal repo (e.g. v0.1.0).
  2. Private infra installs it via git+ssh: pipelex-worker (pipelex[dynamodb,s3]==X + pipelex-temporal @ git+ssh://…@v0.1.0, plus the Dockerfile/Makefile pipelex worker → pipelex-temporal worker flip) and pipelex-api-hosted's child image (the hosted runner enqueues Temporal workflows, so it needs the client too).
  3. Public packages drop temporal (a public MIT dist can't depend on a private repo): remove the temporal extra from pipelex-api and from pipelex-mistralai-workflows (its temporal tests become an internal git+ssh dev dep, or move out).
  4. Cut the public pipelex release (its temporal extra is already removed) and open the PR refactor/Plugins-3 → dev (no PR for -3 yet; PR #997 is the earlier Phases-0–2 snapshot).
  5. Run the consumer suites against the new pins before deploying the hosted worker.

One known follow-up: the Temporal dev make targets removed from core were not added to pipelex-temporal's Makefile (they need a running Temporal server to verify, so they weren't shipped unverified). A shipped-module → tests/ back-import in pipelex-temporal is deferred (pre-existing, dormant in production).
