# Review findings — orchestrator-dispatched `/validate` (PR #998)

Captured from a pre-landing `/review` (gstack) of the `feature/Orchestrator-dispatched-validate` feature across all three repos (`pipelex` core = PR #998 vs `refactor/Plugins-4`; `pipelex-temporal` vs `refactor/own-temporal-config`; `pipelex-api` vs `refactor/orchestrator-agnostic-base`). Verdict: **landable.** No critical findings. Greptile P1 (verdict alias bound under `TYPE_CHECKING`) already fixed by `34a33633d`. The items below were surfaced by the testing + adversarial passes and are deferred (none is a clear, unambiguous win; the brief was clean-solid, no speculative guards). ## 1. MISTRAL_NATIVE `/validate` is unserviceable; its "missing" error names an already-installed package (deferred — out of scope by plan)

**Observation (adversarial, conf 8).** `pipelex-mistralai-workflows`'s plugin (`mistral_plugin.py:31`) registers only the MISTRAL_NATIVE *orchestrator*, never a bundle validator. So a deployment configured `execution_mode = mistral_native` (plugin installed, `/start` working) would fail every `/validate` with `MissingBundleValidatorError` → 5xx — and that error's MISTRAL_NATIVE branch (`pipelex/runtime_bridge/exceptions.py`) tells the operator to `pip install pipelex-mistralai-workflows`, a package that is already installed in that scenario. `/start` and `/validate` are asymmetric for the one orchestrator whose error message specifically promises serviceability.

**Why deferred, not fixed.** This is the **explicitly deferred Mistral arm**, not a regression this PR introduces:

- The plan (`orchestrator-dispatched-validate.md`) defers Mistral in three places: START-HERE ("Mistral is a gated follow-up — do **not** build it"), decision **C** ("Mistral deferred… gated on its own `mistralai-2.x` work"), and Phase **V-Mistral — DEFERRED** ("Add a `MistralBundleValidator` later… The generic seam means this lands without touching core or the API").
- `pipelex-mistralai-workflows` is itself gated from publish (HOLD on `mistralai-2.x` / instructor #2298), so `mistral_native` is not a shippable `/validate` config on any deployment that ships today. The dead path is unreachable in production.
- The error-message wording mirrors the parallel `MissingOrchestratorError` MISTRAL_NATIVE branch verbatim; once the Mistral validator lands, the install hint becomes directionally correct again. Touching only the message now (to soften the "install X" claim) is a judgment call, not a mechanical win, and would desync the two parallel error classes.

**When the Mistral validator lands (Phase V-Mistral):** register a `MistralBundleValidator` under MISTRAL_NATIVE (genuine dispatch, or an in-process passthrough — validation is backend-independent pure analysis). At that point `MissingBundleValidatorError`'s MISTRAL_NATIVE branch is reachable only as a true "plugin not installed" signal and its message is correct. If Mistral is *intentionally* never going to serve `/validate`, revisit the message then (e.g. point MISTRAL_NATIVE `/validate` at the DIRECT in-process validator as a fallback) — but that is a Phase-D/V-Mistral decision, not this PR's.

## 2. The `cast` at the verdict narrowing point launders a non-`PipelexValidationReport` valid arm (deferred — latent, loud-fail, future-plugin guard)

**Observation (adversarial, conf 6).** The seam's valid arm is typed at the protocol-level `ValidationReport` (a leaf type, to stay import-acyclic in core — see §9 divergence in the plan). `ApiRunner.validate_verdict` ends with `return cast("PipelexValidationReport | ErrorReport", verdict)`, and the route discriminates with `if not isinstance(verdict, PipelexValidationReport): return _invalid_report_response(verdict, ...)`. The protocol `ValidationReport` valid arm has neither `validation_errors` nor `message` (confirmed in `mthds/protocol/models.py`), and `_invalid_report_response` accesses `error_report.validation_errors` / `error_report.message`. So a *future* validator whose valid arm returned a bare `ValidationReport` (not the `PipelexValidationReport` subtype) would fail the `isinstance`, be routed to the invalid-arm handler, and crash on attribute access.

**Why not a bug today, why deferred.**

- Both shipped validators (`DirectBundleValidator`, `TemporalBundleValidator`) are annotated `-> PipelexValidationReport | ErrorReport` and in fact return the concrete envelope; the type checker enforces this for every in-tree validator. The `cast` is the single documented narrowing point the plan's §9 acceptance note already calls out.
- The failure mode for a hypothetical non-conforming external plugin is **loud (5xx crash), not silent data corruption** — the worst-case is an obvious server error, not a wrong verdict.
- Adding a runtime guard ("validator returned a non-Pipelex report → raise a clear fault") would broaden the seam's surface to defend a scenario no in-tree code can reach — exactly the speculative guarding the review brief excludes ("no guarding impossible scenarios, no broadening surface area").

**If revisited:** if external/third-party bundle validators ever become a supported extension point (not just core + the two first-party plugins), add a single explicit guard at the narrowing point in `ApiRunner.validate_verdict` — `if isinstance(verdict, ErrorReport) or isinstance(verdict, PipelexValidationReport): ...` else raise a clear "validator must produce a PipelexValidationReport" fault — so a misbehaving plugin gets a precise diagnostic instead of an `AttributeError` deep in the route. Until then the `cast` + the type-checked first-party validators are sufficient.

## 3. Test-coverage symmetry gaps (deferred — covered transitively / by convention)

Testing pass, all INFORMATIONAL, none a correctness gap:

- **Dispatched-*valid* arm has no ungated fast-suite test (conf 6).** `pipelex-api/tests/unit/test_validate_dispatch.py` exercises the non-direct *invalid* (`ErrorReport` → 200) and *fault* (→ 5xx) arms with a stub validator, but not the non-direct *valid* (`PipelexValidationReport` → 200 `is_valid: true`) arm. That valid dispatched path is covered by `pipelex-temporal/tests/integration/test_temporal_bundle_validator_in_memory.py`, which is `@pytest.mark.temporal`-gated (needs `temporalio` + an in-memory server) and excluded from the default fast `agent-test` run. The route mapping is backend-independent and the DIRECT valid arm is covered ungated by the existing `/validate` suite, so risk is low. This matches the plan's §7 V2 acceptance bar, which deliberately scoped the stub tests to invalid/fault/missing/403 and relied on V1 for the valid path. **If desired:** add a `TestValidateDispatch` case with a stub validator returning a real `PipelexValidationReport` for a temporal mode, asserting 200 + `is_valid: true` — proves the valid dispatched arm with no `temporalio` import. Nice-to-have symmetry, not a bug.
- **`DirectOrchestratorPlugin.register` validator line untested in core (conf 5)** and **`TemporalBundleValidator._require_temporal_extra` guard untested (conf 4).** Both are zero-coverage lines, but each is consistent with the pre-existing untested-by-convention sibling (the DIRECT *orchestrator* registration is likewise not directly asserted in core; the orchestrator's own `_require_temporal_extra` is likewise untested). Wiring is covered transitively by the cross-repo boot/envelope tests. Flagging only for the record; not worth a new test against the existing convention.

## Passes with no findings

- **Maintainability:** clean — no dead code/imports, F2 "always DIRECT" prose thoroughly reversed across docstrings + `docs/pipe-validate.md` + CHANGELOG + trackers, no DRY violation worth extracting (the `start`/`validate_verdict` duplication is the separately-noted deliberate mirror; the two `Missing*Error` classes are parallel-by-design), no module-boundary violation (the protocol-level typing is a *deliberate* import-cycle avoidance).
- **API contract:** verified byte-equivalent for the direct path; `execution_mode` field is backward-compatible (optional, default None → deployment default); the 200-always-for-verdict / non-2xx-for-no-verdict contract is preserved including the new forbidden-override 403; `isinstance(verdict, PipelexValidationReport)` is provably correct (disjoint MROs — neither `ErrorReport` nor `PipelexValidationReport` subclasses the other).
- **Enum completeness:** `MissingBundleValidatorError._build_message`'s `match` over `PipelexExecutionMode` is exhaustive (all four members, `-> str`, no `case _`); a 5th member would be caught by the linter. Mirrors the existing pattern in `execution_mode.py`.
- **Boot wiring:** `set_bundle_validator_registry` is called in the single boot block (`pipelex.py`) immediately after `set_orchestrator_registry`; identical lifetime guarantees to the already-production orchestrator registry — no partial-boot gap introduced.
