## High — deferred by design, but the error message actively misleads

- **`MISTRAL_NATIVE` is currently a dead execution mode.** `runtime_bridge/bridge.py` deleted `_run_mistral_native` and flipped to registry discovery, but **no plugin contributes a `MISTRAL_NATIVE` orchestrator** — `pipelex-mistralai-workflows` has no `pipelex.plugins` entry point / `add_orchestrator` call (it exposes only `register_pipelex_primitives` + a `make_mistral_workflows_pipe_run` factory the *old* bridge imported directly). This is expected per the Phase-3 goal ("core names no integration — not by import, not by string"), and landing the MISTRAL_NATIVE plugin onto `dev` is tracked as its own sub-track ([../distributed-execution/mistral-workflows/](../distributed-execution/mistral-workflows/)). The deferred *defect* is the user-facing message: a consumer who **already has** `pipelex-mistralai-workflows` installed and submits `execution_mode=MISTRAL_NATIVE` now gets `MissingOrchestratorError` telling them to `pip install pipelex-mistralai-workflows` — a package they have. Until the plugin grows an entry point, MISTRAL_NATIVE is wholly unusable and the hint points at the wrong remedy. Secondary: the old arm returned `workflow_id=pipe_output.pipeline_run_id`; the seam provides no orchestrator preserving that non-null `workflow_id` contract.

## Medium — error-contract & teardown fragility at the new seam

- **The bridge no longer wraps orchestrator errors; the single-error-type contract now rests on each orchestrator's discipline.** `runtime_bridge/bridge.py` calls `orchestrator.run()` with no surrounding `try`/`except` — error-wrapping into `PipelexBridgeDispatchError` moved *into* each orchestrator. The in-tree DIRECT/TEMPORAL orchestrators kept their wrapping, but an **external** orchestrator (the future MISTRAL_NATIVE plugin) must now wrap its own pipe-execution errors; the old `_run_mistral_native` did that wrapping at the bridge. If an external orchestrator raises a raw `PipeRunError`/`PipeJobError`/`PipeExecutionError`, it propagates unwrapped through the bridge, and a host catching only the documented `PipelexBridgeDispatchError` fails to catch it. Decide whether the SPI documents "orchestrators MUST raise `PipelexBridgeDispatchError`" as a hard contract (with a conformance test), or whether the bridge keeps a thin outer wrap as a safety net.

- **`teardown()` runs plugin callbacks with no `try`/`finally`; one raising callback aborts all core teardown.** `pipelex/pipelex.py:teardown()` (~`:494`) iterates `reversed(self._plugin_registrar.teardown_callbacks)` and *then* runs core teardown (pipeline/telemetry/inference/reporting/sdk-client managers). If a plugin teardown callback raises — e.g. a Temporal worker's `task_manager.teardown()` or `temporal_hub.reset()` throwing during an unclean shutdown — the exception propagates out of the loop and **none** of the subsequent core teardown runs, leaking those resources/handles. The old code had this same shape for the single inlined Temporal block, so this is a pre-existing fragility now generalized across N callbacks — flagged per the "flag and fix pre-existing bugs" convention. Cleanup that must run on the error path belongs in `try`/`finally` (per the error-handling standard).

- **`_teardown_temporal` re-fetches the task manager from the global hub instead of the instance it built.** `pipelex/temporal/temporal_plugin.py` (~`:63`): `_setup_temporal_task_manager()` constructs a `TemporalTaskManager`, sets it on the module-global `temporal_hub`, and discards the local reference; `_teardown_temporal()` re-fetches via `temporal_hub.get_optional_task_manager()`. If any path between setup and teardown resets `temporal_hub` (a nested/aborted second boot, or a reentrant `TemporalPlugin` register that fails after claiming), the fetch returns `None`, teardown silently skips `task_manager.teardown()`, and `TemporalManager` session/sandbox state + the in-workflow content generator leak into the next worker boot. Holding the constructed instance and tearing it down directly (instead of round-tripping through the global) would forward the call unconditionally.

## Low — cleanup, non-blocking

- **Enum identity comparison instead of the property.** `runtime_bridge/bridge.py` `_validate_input` (~`:165`) singles out fire-and-forget via `input_payload.execution_mode is PipelexExecutionMode.TEMPORAL_FIRE_AND_FORGET` instead of the existing `PipelexExecutionMode.is_fire_and_forget` property added for exactly this case. Violates the python-standards rule "never test equality to an enum value; add an `@property` so the linter complains when a new value is added." A future fire-and-forget-like mode would silently miss this validation guard. Pre-existing (untouched by the diff but in the reshaped file) — flagged per "flag and fix pre-existing."

- ✅ **RESOLVED (Option A).** The import-time CLI harvest is gone, so the second discovery, the per-invocation config load (deep-merge + full `PipelexConfig` validation), and the `entry_points(group=…)` metadata scan no longer run on any `pipelex` invocation (including `--help` and shell tab-completion) — only boot discovers now. Original finding retained below. **Double discovery + import-time cost on every invocation.** On any boot-requiring command (`run`/`validate`/`build`), plugin discovery + config load runs **twice**: once in the import-time CLI harvest (`_cli.py:~280`), once again at boot (`pipelex.py:~390`, `build_registrar(config=get_config())`), with the harvest registrar discarded except for command names. Separately, the harvest adds a full config load (deep-merge of multiple TOML overrides + full `PipelexConfig` validation) **plus** an `importlib.metadata.entry_points(group=...)` metadata scan to **every** `pipelex` invocation — including `--help` and shell tab-completion, which did none of this pre-Phase-3. Both stem from the harvest running fully, at import, on every call. **Coupled to the critical finding:** any redesign that defers/memoizes the harvest (see [phase-3-critical-cli-harvest-fragility.md](phase-3-critical-cli-harvest-fragility.md) "Solution space → Single vs. double discovery") should resolve this for free — solve them together, don't apply a narrow perf patch here in isolation.

- **Dead `serialize_pipe_output` re-export.** `runtime_bridge/bridge.py` (~`:43`) keeps a `serialize_pipe_output` re-export commented "for host-runtime back-compat," but the real definition + every internal use moved to `serialization.py`, and grep across `pipelex/`, `tests/`, and the sibling runner repos (`pipelex-api` / `pipelex-worker` / `pipelex-mistralai-workflows`) finds **zero** importers of it from `bridge`. Under the workspace "No backward compatibility" policy this is unjustified duplicated surface that keeps `bridge.py` importing `serialization.py` purely to re-export, and silently rots. Drop it; in-tree callers and the orchestrator SPI already import from `serialization.py` directly.

- **Hardcoded count in a docstring.** `pipelex/temporal/temporal_plugin.py` (~`:11`) says the plugin "claims the **four** process-global hub slots," violating the workspace "never hardcode counts" rule. The next phase (Phase 4, the `model_lists` 5th seam) is precisely the kind of change that makes "four" go stale while the `claim_*` calls below it claim a different number. Write "the process-global hub slots" with no count.
