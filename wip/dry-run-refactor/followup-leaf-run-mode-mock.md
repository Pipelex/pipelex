## Still relevant — a distinct dry-run mode (do NOT drop this file)

This describes a **different** dry-run mode from the in-memory in-process activity ([`followup-temporal-validation-activity.md`](./followup-temporal-validation-activity.md)). Both are wanted; they're orthogonal `run_mode × backend` combinations of one foundation (mock at the leaf; the backend decides where the leaf runs — D-plan §3.5):

- **This file (req 1) — full distribution, leaf-only mocks.** A DRY run goes through the **real** Temporal path (`WfPipeRouter` → child workflows → `act_llm_gen_*` activities) and the **leaf inside each activity** mocks instead of calling the model. Purpose: **test the distribution machinery** (dispatch, scheduling, serialization, routing, cross-worker propagation) without AI cost or latency.
- **The other file (req 2) — one in-process activity, in-memory tracing.** The whole dry-run + validation runs **in-process inside a single activity** (nothing nested is dispatched), tracing the graph in memory. Purpose: offload validate+graph to a worker cheaply.

**Already partly shipped:** `is_mock_inference` (the registry branch's interim trigger) **is** the LLM slice of this mode — `run_mode` stays LIVE so operators dispatch `act_llm_gen_*` normally, but the leaf fakes the call (`JobMetadata.is_mock_inference` → the `llm_generate.py` leaf branch). So req-1 behavior already coexists, today, alongside the pipe-level DRY path — concrete proof the two modes don't conflict. B1/B2 generalize it from LLM-only + `is_mock_inference` to all leaves + `run_mode=DRY`.

**Shared seam with the in-memory activity — `scoped_content_generator` (RESOLVED: it exists, consume it).** B2 routes the DRY mock through `get_content_generator()` at the leaf. Under a Temporal-enabled hub that returns `ContentGeneratorInWorkflow` **globally** (boot-time, `pipelex.py:370-385`). The in-process activity (req 2) landed first and **built the inline-content-generator scope** — `scoped_content_generator` is live (`bundle_validator.py:260` uses it, see `TODOS.md` Phase 2). This follow-up consumes it: B2's Mode-1 scopes (`validate_pipes`, `dry_run_pipe_in_process`) swap `ContentGeneratorDry()` for an inline `ContentGenerator` inside the existing scope.

## Deferred items from the B1 code review (2026-06-10)

Findings from the post-B1 review round that were verified real but deliberately NOT fixed in B1 — each is a design tradeoff or a later-phase concern, not a silent bug in shipped behavior:

- **Storing activities resolve `get_storage_provider()` before the leaf's DRY branch** (`act_img_gen_generate.py`, `act_extract_generate.py`, `act_render_page_views.py`): D10's "no storage credentials under DRY" holds only because boot always constructs a provider from config (provider construction needs no credentials; only real IO does). If B3's Tier 17 no-keys arm ever boots a worker without a storage provider, move acquisition inside the leaf's LIVE arm. Verify in B3.
- **Sequential page-view storage uploads** in `render_page_views_and_store` (pre-existing behavior, relocated): each rendered page is stored one `await` at a time; a large PDF pays serialized upload latency inside the activity. Candidate `asyncio.gather` with a bound — perf-only, touch when a real workload hurts.
- **Ambient `dry_run_config.nb_extract_pages` read at two leaves** (`dry_extract_page_contents`, `dry_render_page_views`): under Temporal these run in different activities, so heterogeneous worker configs could mismatch page counts and trip the generator's length check on a dry run. D11-style fix = carry the resolved count on the assignments. Revisit in B3 (Tier 17 would surface it).
- **No cross-call memoization of `DryRunFactory.make_dry_run_factory`**: list mocks now build the factory once per call (`build_mock_objects`), but repeated leaf calls for the same class still rebuild it. An lru-cache keyed by class adds lifetime/invalidation surface for dynamically-created classes — skipped as over-engineering until dry-run profiling says otherwise.
- **Schema-reconstruction failures stay untyped** (`_reconstruct_object_class` → `SchemaToModelFactory`): D7 wrapped the polyfactory build; codegen failures (ValueError / datamodel-code-generator errors) share their surface with the LIVE leaf path (same function, same schema), so typing them only on the mock path would add asymmetry. Belongs to the broader "retry-forever on unconverted exceptions" hardening family already tracked.

Additional deferred items from the B2 code review (2026-06-10):

- **`PIPELEX_FORCE_DRY_RUN_MODE` env var vs the hub forced-DRY flag**: two run-mode-forcing mechanisms now coexist — the env var (resolved in `pipeline_run_setup`, only a *default* despite its name: an explicit run mode wins, per its own `# TODO: rethink this, it's not forcing`) and the hub flag (genuinely forcing, resolved at `make_run_params`). Nothing in the repo sets the env var; folding it into the hub flag (or deleting it) is a user-facing-surface decision — defer.
- **Mock-input list factory not hoisted** (`working_memory_factory.make_mock_inputs` builds a `DryRunFactory` per item): NOT a pure hoist — `_get_mockable_class` picks a *random concrete subclass per item*, so hoisting would change mock diversity. Left as is.
- **`ContentGeneratorInWorkflowFactory` is now a param-less wrapper**: kept as the deliberate lazy-import construction seam (boot imports it deferred); revisit if it never grows params.
- **Mock-inference guard not consolidated**: the `MockInferenceUnsupportedError` guards at the img/extract/search leaves stay inline (3 small sites with distinct operation labels); consolidation would save little.
