PR 1028 explainer

Smart Inputs: from protocol envelopes to plain business values.

Before this PR, users had to feed Pipelex inputs in Pipelex's internal shape. After this PR, they provide the values they already have, and the pipe signature turns those values into typed working memory.

Branch: feature/Smart-inputs Base: dev Scope: native concepts + runner/CLI/API input seam Generated: 2026-07-08

TL;DR

Before Smart Inputs: a caller had to know the ceremony: concept envelopes, content field names, file wrappers, and list shapes. After Smart Inputs: a caller gives Pipelex ordinary values like "contract.pdf", true, 2026-07-07, or rows from people.csv; Pipelex reads the declared signature, builds the right typed data, and fails loudly when the value cannot match the contract.

Plain callers now provide business values, not Pipelex protocol envelopes
1 shared Smart Inputs seam across CLI, Python API, and hosted runner
Typed values become declared concepts such as Question, YesNo, Date, Document, and structured rows
Safer unknown names, bad scalar kinds, wrong list counts, nulls, and incompatible envelopes are typed errors

Before / After For Executives

The business change is simple: users now fill in the values they actually have. Pipelex owns the typing, validation, file resolution, and exact rendering.

Before protocol-shaped

  • Users had to understand Pipelex envelopes: {"concept", "content"}.
  • A yes/no judgment could come back as text that callers had to parse.
  • A calendar date could be forced into a datetime, quietly inventing midnight.
  • Input names not declared by the pipe could be ignored silently.
  • Generated templates did not look like the values accepted by pipelex run.
{
  "question": {
    "concept": "legal.Question",
    "content": { "text": "Does this contract include a penalty clause?" }
  },
  "verdict": {
    "concept": "YesNo",
    "content": { "yes_no": true }
  },
  "signed_on": {
    "concept": "Date",
    "content": { "date": "2026-07-07" }
  }
}

After JSON value-shaped

  • Users provide plain values; the pipe signature supplies the meaning.
  • YesNo is a real boolean concept with prompt rendering as yes or no.
  • Date stores a date and only stores time when the source states one.
  • Unknown inputs, incompatible envelopes, nulls, wrong scalar kinds, and bad list counts fail with typed errors.
  • The generated light template is the template you can fill and run.
{
  "question": "Does this contract include a penalty clause?",
  "verdict": true,
  "signed_on": "2026-07-07",
  "contract": "contract.pdf"
}

After TOML value-shaped

  • Same Smart Inputs model as JSON.
  • TOML keeps the shape compact for editable input files.
  • Date literals can stay native TOML dates.
  • The file path stays a plain string.
question = "Does this contract include a penalty clause?"
verdict = true
signed_on = 2026-07-07
contract = "contract.pdf"

What We Built

Native YesNo

A built-in native concept backed by YesNoContent. It carries one strict boolean, renders as yes/no, and supports refinements like any other native concept.

Native Date

A built-in native concept backed by DateContent. It preserves source precision: date-only stays date-only; time and offset appear only when the source states them.

Smart Inputs

A new InputShaper interprets caller input from the declared pipe signature, not from raw value shape alone. One seam covers CLI files, inline inputs, Python callers, and hosted runs.

Architecture

The key decision: shaping is a runtime boundary concern, not a CLI feature. The CLI passes the inputs file base directory when it has one; the shared shaper decides how each value maps to the declared concept.

Developer Impact

Area What changed Why co-developers should care
Native data NativeConceptCode now includes YesNo and Date, with corresponding content classes and rendering. No more local string conventions for two common extraction/judgment outputs.
Input shaping InputShaper maps bare values to the declared concept, checks envelopes, applies multiplicity rules, and raises typed errors. Every surface gets the same behavior. A CLI fix is not stranded in the CLI.
Files and tables Relative file-ish strings resolve against the inputs file directory; declared structured lists can accept a CSV path by signature. Common user artifacts, like contract.pdf and people.csv, become first-class inputs without wrappers.
Templates build inputs and pipelex-agent inputs default to the light shape; --explicit keeps the old envelope. Generated examples now teach the recommended model and round-trip into run.
Breaking edge YesNo and Date are reserved native concept codes; unknown inputs and top-level nulls are hard errors. Breakage is intentional: it removes silent wrong work and makes author mistakes visible at the boundary.

One Seam, All Surfaces

The implementation deliberately routes the behavior through working-memory construction. That keeps CLI, Python, agent CLI, and hosted runner behavior aligned.

The old bottom-up path remains when no signature is available. When a signature exists, Smart Inputs is opt-in by data: pass input_specs and the same PipelineInputs are shaped top-down. 

caller values + entry pipe signature
  -> WorkingMemoryFactory.make_from_pipeline_inputs(..., input_specs=...)
  -> InputShaper.shape(...)
  -> WorkingMemory full of typed Stuff
  -> normal pipe execution

Migration Notes

These breaking changes are the cost of making wrong inputs visible instead of silently tolerated.

  • YesNo and Date are now reserved native concept codes. Bundles declaring concepts with those exact codes now error.
  • Unknown input names are hard errors with the declared names listed.
  • Top-level null is rejected. Omit the key to express absence.
  • TOML date and datetime literals now map to Date; bare time-of-day values remain invalid.
  • Structure field type = "date" now means datetime.date. Use type = "datetime" for a timestamp.
  • build inputs defaults to the light template. Use --explicit when you want the old envelope form.
