## 1. Wire-cost / CLI-total parity — fixture-coverage gap (cubic P2)

- **Reporter:** cubic (thread `PRRT_kwDOOwmMFc6SEzQN`), `pipelex/cogt/usage/cost_registry.py` (`compute_tokens_usage_cost`).
- **Verdict:** false positive *as filed*, with a narrow real residual. The finding claims `compute_tokens_usage_cost` "duplicates the logic in `CostRegistry.complete_cost_report`" and can diverge. In fact the two paths already share the pieces that carry the cost *policy* — the rate lookup + cached-discount fallback (`model_cost_per_token`) and the total formula (`compute_total_cost`). Only the structural component derivation is duplicated. Parity is **explicitly asserted**: `tests/unit/pipelex/cogt/usage/test_usage_cost.py:37-46` compares the summed wire `cost` against `CostRegistry.aggregate_costs(...).total_cost` — the actual number the CLI cost table prints — plus per-record parity across all four usage variants.
- **Why deferred:** the only divergence that escapes the parity test is *widening which token categories count toward the table total* (e.g. starting to charge reasoning/audio), because the parity fixture `RATED_NB_TOKENS` (`tests/unit/pipelex/cogt/usage/test_data.py`) only carries `INPUT`/`INPUT_CACHED`/`OUTPUT`. That is a fixture-coverage hole, not the architectural drift the finding describes — and closing it by folding `compute_tokens_usage_cost` into `complete_cost_report` reshapes a client-facing response path, which is not worth destabilizing a release branch for.
- **Recommendation:** cheap, test-only follow-up — add a *dedicated* single-record parity test for an excluded category, not a new entry in `all_variants()`. Add a `UsageFixtures` method (e.g. `reasoning_usage()`) carrying an `OUTPUT_REASONING` (and/or `INPUT_AUDIO`) token count plus a matching rate, then assert that both `compute_tokens_usage_cost(reasoning_usage())` and `CostRegistry.aggregate_costs([reasoning_usage()]).total_cost` equal the three-component total (the excluded category contributing 0 to both) — so a future change that starts counting the extra category in one path but not the other breaks the test. Two footguns to avoid, both verified against the current tests: (1) do **not** mutate the shared `RATED_NB_TOKENS` constant (`tests/unit/pipelex/cogt/usage/test_data.py`) in place — `tests/unit/pipelex/reporting/test_usage_records.py` hard-asserts the exact `{"input":1000,"input_cached":400,"output":250}` dict, so mutating it breaks those; (2) do **not** fold the new heterogeneous variant into `all_variants()` — `test_parity_with_aggregate_run_total` asserts exact-float `==` and holds only because all four current variants are token-identical, so a heterogeneous variant risks an ULP mismatch from float-summation order. The delegation refactor (make parity structural instead of asserted) is optional and belongs off a release branch.

## 2. Transported PipeFunc failures lose traceback source-line text (cubic P2)

- **Reporter:** cubic (thread `PRRT_kwDOOwmMFc6SEzQb`), `pipelex/pipe_operators/func/direct_pipe_func_executor.py` (`run_pipe_func_transported`, `finally` cleanup).
- **Verdict:** confirmed as a code fact, and PR-introduced. The new deterministic cleanup (`shutil.rmtree` of the materialized workdir in the `finally`, on every path) runs *during exception unwinding*, before the default excepthook formats the traceback. Because Python resolves frame source *text* lazily via `linecache` at format time (and the `SourceFileLoader` fallback also reads from the now-deleted path), the customer-code frames in the stderr diagnostic show `file:line:function` **without the source-line text**. Verified empirically: the subprocess entrypoint (`pipe_func_transported_entrypoint.py`) does not capture `traceback.format_exc()` into a shipped-back string, so nothing materializes the source before cleanup. Before this PR there was no cleanup at all (the workdir leaked), so those source lines used to survive — this is a genuine diagnostics regression traded for deterministic cleanup + `sys.path` pruning.
- **Why deferred:** what is lost is only the source-line *text* of customer frames — the exception *type*, *message*, and every frame's *file + line-number + function* all survive, and the filename was a throwaway temp path anyway. The reviewer's "retain the workdir until diagnostics are captured" directly conflicts with the PR's goal (clean up on every path, which is needed for long-lived reuse — in-process sandbox / Temporal worker). The correct fix (eagerly materialize `traceback.TracebackException.from_exception(exc, lookup_lines=True)` before `rmtree`, then surface that captured text since the excepthook would re-look-up and fail again) is a non-trivial change to error-path behavior with excepthook interplay.
- **Recommendation:** implement the eager-capture fix on a follow-up branch off `dev`, with a regression test (a crate whose `@pipe_func` raises at a known line; run transported; assert the emitted traceback contains the source-line text). Not worth landing on the release branch — it only affects failure-diagnostic richness, not correctness.

## 3. `finally` teardown in the workdir test (cubic P2)

- **Reporter:** cubic (thread `PRRT_kwDOOwmMFc6SEzQa`), `tests/unit/pipelex/pipe_operators/pipe_func/test_direct_executor_workdir.py` (`finally: get_library_manager().teardown(...)`).
- **Verdict:** false positive on the concrete claim, minor latent nit. The finding says the unconditional teardown can raise `LibraryError` ("library not found") and mask the original test exception. Traced against the flow, that cannot happen: rehydration calls `open_fresh_library(library_id=_TRANSPORTED_LIBRARY_ID)` → `open_library` (which **registers** the library in `_libraries`) at step 2 of `rehydrate_library_and_memory`, *before* crate load, working-memory hydration, and the function lookup where a failure could occur. The test's trivial crate (`{"funcs.py": "x = 1\n"}`) cannot fail during source-materialization/import/registration, so every reachable failure point is *after* registration — teardown always finds the library and succeeds. The reviewer's suggested "just rely on `scoped_current_library`" is not viable alone: that context manager only restores the `_library_id` ContextVar, it does **not** unregister the process-global library, so some teardown is genuinely required to avoid leaking `_TRANSPORTED_LIBRARY_ID` into later tests.
- **Why deferred:** the teardown is coupled to rehydration's internal ordering. A *future* change that made the transported run fail before `open_fresh_library` (e.g. an import-time error in the crate) would let the `finally` raise `LibraryError` that supersedes (chains over) the real failure — a latent robustness nit, not a current bug.
- **Recommendation:** when convenient, make the teardown best-effort (guard on membership, or `try/except LibraryError: pass`) or move library lifecycle into a dedicated autouse fixture. Test-only and safe to land any time; no urgency.
