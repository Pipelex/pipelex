Per-activity, per-handle Temporal queue routing

Shipped v1 branch: feature/Per-activity-queue 4 commits since 0a273cad

TL;DR

  • Killed the binary inference_task_queue split. Replaced with a per-activity, per-handle routing table.
  • One resolver: WorkerConfig.resolve_queue(activity_name, routing_key). Three layers: per-handle → activity default → worker default.
  • Every workflow.execute_activity(...) call site now passes task_queue=resolved — no more asymmetric kwargs.
  • Deployments can now scale OpenAI vs Anthropic separately, isolate image-gen onto heavy pools, or pin an OCR backend to its own queue. All via TOML, zero code change.
  • Default config ships with empty activity_queues — existing single-queue deployments unaffected.

Why this change

The predecessor PR introduced inference_task_queue as a quick "LLM goes here, everything else goes to the workflow's own queue" split. It served the immediate split-worker test but had no answer to real deployment questions:

  • Scale OpenAI workers independently from Anthropic workers?
  • Pin image generation (slow, heavy payloads) to its own pool?
  • Route Mistral OCR to a dedicated backend pool?

None of those were expressible in the old two-queue model. v1 solves it with one config table, one resolver, and no special cases.

The resolver, visually

┌─────────────────────────────────────────────────────────┐ │ worker_config.resolve_queue(activity_name, routing_key) │ └─────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────┐ layer 1 → │ activity_queues[activity_name]? │ │ └─ no ──────────────────────────┐ │ └─────────────────────────────────────────────────────┘ │ │ yes │ │ ▼ │ ┌─────────────────────────────────────────────────────┐ layer 2 → │ routing_key is not None AND │ │ activity_route.by_handle[routing_key]? │ │ └─ yes ─→ return per-handle queue │ │ └─ no ──────────────────────────┐ │ └─────────────────────────────────────────────────────┘ │ │ ▼ │ layer 3 → return activity_route.default │ │ ▼ return worker_config.task_queue

Before vs after, at a glance

Before — asymmetric kwarg

await workflow.execute_activity(
    act_llm_gen_text,
    arg=llm_assignment,
    ...,
    **_inference_dispatch_kwargs(worker_config),
)

await workflow.execute_activity(
    act_img_gen_images,
    arg=img_gen_assignment,
    # no task_queue kwarg → workflow's own queue
    ...,
)

LLM-text had a magic helper. img-gen, extract, jinja2, render — silently fell to the workflow's queue. Copy-pasting the kwarg to img-gen would break runners that don't register img-gen activities.

After — uniform dispatch

await workflow.execute_activity(
    act_llm_gen_text,
    arg=llm_assignment,
    task_queue=worker_config.resolve_queue(
        act_llm_gen_text.__name__,
        llm_assignment.llm_handle,
    ),
    ...,
)

await workflow.execute_activity(
    act_img_gen_images,
    arg=img_gen_assignment,
    task_queue=worker_config.resolve_queue(
        act_img_gen_images.__name__,
        img_gen_assignment.img_gen_handle,
    ),
    ...,
)

Every call site looks the same. Activities without a routing dimension (jinja2, render-page-views) pass routing_key=None and resolve to the worker default.

Schema change — WorkerConfig

class ActivityRouteConfig(ConfigModel):
    default: str
    by_handle: dict[str, str] = Field(default_factory=dict)

class WorkerConfig(ConfigModel):
    task_queue: str
-   inference_task_queue: str | None = None
+   activity_queues: dict[str, ActivityRouteConfig] = Field(default_factory=dict)
    workflow_execution_timeout: timedelta = Field(strict=False)
    ...

    def resolve_queue(self, activity_name: str, routing_key: str | None = None) -> str:
        activity_route = self.activity_queues.get(activity_name)
        if activity_route is None:
            return self.task_queue
        if routing_key is not None:
            per_handle = activity_route.by_handle.get(routing_key)
            if per_handle is not None:
                return per_handle
        return activity_route.default

The route_activities_to helper — why it exists

Integration tests that spin up an in-process worker on a UUID-scoped task queue and substitute activities on it would silently break under v1: the dispatcher resolves to worker_config.task_queue (the production default), where nothing is listening. The activity hangs until pytest-timeout fires. This context manager patches activity_queues for the duration of the test and restores prior entries on exit. 

with route_activities_to(task_queue, [act_llm_gen_object.__name__, act_llm_gen_object_list.__name__]):
    async with get_task_manager().make_worker(
        temporal_client,
        task_queue=task_queue,
        substitute_activities={
            act_llm_gen_object: _stub_act_llm_gen_object,
            act_llm_gen_object_list: _stub_act_llm_gen_object_list,
        },
    ):
        await temporal_client.execute_workflow(...)

Decisions taken (open questions resolved)

  • Field name: kept task_queue (worker-wide default) — no rename to default_task_queue.
  • Resolver lives where: method on WorkerConfig — discoverable, no separate module.
  • Migration: hard delete inference_task_queue. No shim. CHANGELOG note only (per project's "no backward compatibility" rule).
