Runtime bridge — extracting runtime-agnostic tools out of the Temporal subpackage

A lot of what we built for Temporal isn't actually Temporal-specific. This PR pulls that logic into a neutral home so it can be shared across runtimes — used by Temporal today, by the Mistral Workflows plugin when it ships.

PR #969 branch feature/Runtime-bridge-extraction base dev new package pipelex/runtime_bridge/

TL;DR

We're going to support more than one execution runtime. Today Pipelex runs pipes durably on Temporal; next we'll run them on Mistral Workflows. While building the Temporal integration, several pieces turned out not to be Temporal-specific at all: delivering results (storage + webhook), flushing trace events, hydrating working memory, rehydrating a library crate, classifying a pipe as controller-vs-leaf.

This PR lifts that runtime-agnostic logic out of the pipelex.temporal subpackage into a new neutral home — pipelex/runtime_bridge/primitives/ — and turns the Temporal activities into thin wrappers over it. Nothing about behaviour changes; only the home of the logic does.

  • Used by Temporal today now — the act_*.py activities are now thin @activity.defn wrappers that delegate to the shared primitives; even core delivery_executor consumes one. One copy, instead of logic that would get re-implemented per runtime.
  • Used by Mistral Workflows next later — the same primitives are what the pipelex-mistralai-workflows plugin will consume when we ship it (currently preview).
  • Also lands a forward-looking dispatch surface — run_pipe_via_bridge() + a PipelexExecutionMode enum + JSON-safe boundary types — designed and tested now as the door the Mistral plugin will enter through. It has no in-tree caller yet; Temporal keeps its existing entry points and just consumes the lifted primitives.

The diff looks large, but the code core is small and concentrated in pipelex/runtime_bridge/. Most of the line count is a vendored skill + triage notes that are not review material (see What's not part of this work).

A note on two words used throughout this doc. The relocation came in two flavours — the distinction matters when reading the diff:

  • moved — the module already stood on its own; it just changed directory, byte-for-byte. Git records it as a rename (high similarity), so the diff shows no real content change — only a new path. Example: hydration.py, pipe_run_arg.py, submitter_hydration.py.
  • lifted — the logic was welded inside a Temporal activity's function body. It was extracted into its own standalone, runtime-agnostic function, leaving a thin @activity.defn wrapper behind that just calls it. This is an extraction / refactor, so the diff shows code leaving one file and a new file appearing — not a clean rename. Example: delivery.py, trace_flush.py.

In short: moved = same code, new home; lifted = code pulled out of a Temporal wrapper into a reusable home, wrapper kept thin. Both are behaviour-neutral.

What a Temporal activity looks like now

The activity keeps only its Temporal-specific shell — the @activity.defn decorator and arg decode — and delegates the body to the shared primitive:

# act_deliver.py — Temporal shell only; the body now lives in the runtime-agnostic primitive.
from pipelex.runtime_bridge.primitives.delivery import execute_delivery

@activity.defn(name="act_deliver")
@convert_pipelex_errors
async def act_deliver(arg: DeliveryActivityArg) -> None:
    await execute_delivery(...)   # the lifted, host-agnostic body

Two robustness fixes also rode along on live code: tracing now degrades gracefully when the event-log backend can't even be constructed (new EventLogSetupError), not only when a read fails; and hub.py gains scoped_pipe_router, a contextvar router override that restores the prior value on exit.

The forward-looking dispatch surface

Designed, not yet wired in. run_pipe_via_bridge() + a PipelexExecutionMode enum + JSON-safe (extra="forbid") boundary types are the door the Mistral plugin will enter through. They're built, unit-tested, and hardened — but have no in-tree caller yet. Temporal keeps its own entry points and just consumes the lifted primitives. Skim to know it's there; no need to review as live code.

The four execution modes (reference)
ModeWhat it doesNeeds
DIRECT (default)In-process, no Temporal. Forces local execution even inside a Temporal-enabled worker.nothing
TEMPORAL_BLOCKINGDispatch as a Pipelex Temporal workflow and await it.pipelex[temporal]
TEMPORAL_FIRE_AND_FORGETDispatch and return the workflow_id; completion arrives via the DeliveryAssignment (required here).pipelex[temporal] + delivery target
MISTRAL_NATIVEDecompose into native Mistral Workflows primitives (controllers → child workflows, leaves → activities).pipelex-mistralai-workflows (preview)

Optional deps stay optional — temporalio / the Mistral plugin are lazy-imported only inside the matching branch; a missing extra raises a precise install-hint error. The surface is already covered by unit tests (dispatch, validation, idempotent boot-race, DIRECT router scoping, trace-context isolation), so it's ready the day the consumer lands.

Why this is the right shape

The lift earns its keep now

It's not abstraction-for-later: the primitives are consumed in-tree today by Temporal (and core delivery_executor). Moving them just stops the logic from being duplicated when Mistral arrives.

Right home, no host coupling

runtime_bridge/primitives/ imports only Pipelex core types — no temporalio, no mistralai. "Temporal SDK glue" stays in pipelex.temporal; the reusable bodies don't.

Not over-engineered

The dispatch surface is a flat enum, not a plugin registry; __init__.py is empty (no re-export indirection, per project convention). No speculative interfaces beyond the one real upcoming consumer.

What's not part of this work

The diff looks large, but a vendored /workflows skill under .claude/skills/ accounts for most of the line count and is not part of this PR — it was adapted from Mistral's own Workflows skill and rode along on this branch for convenience. Internal triage notes under wip/ are likewise not review material. A couple of unrelated review-driven fixes also rode along (e.g. honoring transport_max_retries on the gateway LLM client factories).
