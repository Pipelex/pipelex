Refactor · pipe taxonomy

PipeSignature is a contract, not an executable pipe type

We evicted PipeSignature from the PipeType / PipeCategory taxonomy. A signature stays a PipeAbstract (so the dry-run engine can still mock it), but it is no longer pretending to be a sibling of PipeLLM or PipeSequence.

Landed make tb · agent-check · agent-test green MTHDS schema: no diff Breaking: PipeCategory.PIPE_SIGNATURE removed

TL;DR

A pipe has a signature (its contract). A PipeSignature is that contract alone — no body. It was a member of PipeType/PipeCategory, which framed it as a way of running next to PipeLLM/PipeSequence. It isn't one. We pulled it out of the executable taxonomy.

  • Removed PipeType.PIPE_SIGNATURE and PipeCategory.PIPE_SIGNATURE. The two enums now describe only things that execute (operator vs controller).
  • Identity by class, not enum. is_signature is now a class fact — base returns False, PipeSignature / PipeSignatureBlueprint override to True — instead of reading an enum field. Every existing call site keeps working unchanged.
  • It stays a PipeAbstract. The dry-run engine dispatches over PipeAbstract, and a signature must be dry-runnable (verify inputs, mock output). A signature carries type = "PipeSignature" with pipe_category = None.
  • One honest allowlist. A new PIPE_SIGNATURE_TYPE_TAG + valid_pipe_type_tags() expresses "legal type = executable kinds ∪ the signature tag" as the single source of truth for the three validators that gate it.
  • Breaking but tiny. Anything matching on PipeCategory.PIPE_SIGNATURE must drop that arm. signature_for is kept (mthds-plugins depends on it); its two guard validators are deleted because the rejection is now structural.
  • Invisible to the wire. The blueprint union discriminates on type (unchanged), so the generated MTHDS JSON Schema produced no diff.

1The diagnosis

PipeType and PipeCategory were each doing two jobs:

  • Job 1 — parse-time allowlist. "Is this type legal under [pipe.X]?" (value in PipeType.value_list(), in three validators.)
  • Job 2 — executable taxonomy. PipeType.category → operator vs controller; the orchestration role.

A signature only needs Job 1 — type = "PipeSignature" is a real thing you write. But the only way to clear the allowlist was to join the enum, which forced a .category and dragged it into Job 2 as a peer of the real kinds. PipeCategory.PIPE_SIGNATURE was the scar.

The fix separates the two jobs: the allowlist becomes "executable kinds ∪ the signature tag"; the enums shrink back to executable kinds only. As a bonus, PipeType.category is a total function again — its match is cleanly exhaustive over {OPERATOR, CONTROLLER}.

2The principle

PipeSignature stays a PipeAbstract subclass (the dry-run engine dispatches over PipeAbstract, and a signature must be dry-runnable) — but it leaves the executable taxonomy.

The four rules

  • PipeAbstract = the substrate. A contract-bearing graph node: inputs / output / description, dry-runnable. A PipeSignature is that substrate with nothing added. It stays here.
  • PipeType / PipeCategory = the executable taxonomy. How a pipe runs and whether it orchestrates. A signature does not run → it is in neither.
  • Identity by class, not by enum field. is_signature is the keystone — it stops reading pipe_category and becomes a class fact.
  • The runtime PipeSignature is a dry-run shim of a blueprint-layer contract. Live-run always errors; dry-run mocks the declared output, and only under --allow-signatures.

4The keystone: identity by class

Everything hinges on one property moving from "read an enum field" to "ask the class." Because every existing call site already calls is_signature, swapping its implementation propagates the new model everywhere for free.

7Scope: the spec layer stays put

The taxonomy correction lands at the blueprint + runtime layers. ../mthds-plugins authors against the spec layer (PipeSignatureSpec), so that surface is left stable: it keeps its type / pipe_category = "PipeSignature" string literals as display tags (not typed as PipeCategory, and to_blueprint() never propagates them). The only spec edit was widening PipeSpec.validate_pipe_type via the same valid_pipe_type_tags() and dropping the broken signature_for guard.

Why the spec can keep a tag the blueprint drops

Blueprints are the MTHDS language reference (what .mthds parses into); specs are an authoring format for agents, each with a to_blueprint(). Spec fields may legitimately differ from blueprint fields — so a cosmetic pipe_category string on the spec is fine.

Why is_controller was not converted to a class fact (deliberate)

We left is_controller reading the enum — it's cleanliness, not correctness, and converting it would do more harm:

  • It already returns the right answer for a signature: pipe_category is None, PipeCategory(None) raises ValueError, and is_controller_by_str's except → False handles it.
  • A class-based override would orphan PipeCategory.is_controller / is_controller_by_str into dead code (their only caller is PipeAbstract.is_controller).

Revisit only if is_controller ever needs to stop touching pipe_category for another reason.
