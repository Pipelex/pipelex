## Deferred from the review rounds

Findings of the round-1 `/rev` pass at profile 4 and the round-2 pass at profile 5 (both 2026-09-07) that are real but not this campaign's to fix. Each is a candidate for its own item once a consumer asks for it.

Round 2 fixed three things and deferred the rest: the agent CLI now settles its graph inclusion before the run (the build gate and the render gate read different configs, so `graphspec_json = false` in the user's config produced a graphspec with no companions); the stale-companion removal logs a warning per file, since the agent CLI's directory is the user's own bundle directory; and the build's catch is blind again, so a builder bug cannot skip the delivery of a completed run.

- **The artifacts cover the whole run library, and the cost follows.** `get_own_pipes()` is every non-aliased pipe of the run library, so `library_dirs` and `PIPELEXPATH` bundles are described too, at the end of every graph-enabled run, synchronously on the event loop, with an uncached JSON-Schema render per pipe input and output; the form deriver's cycle guards are path-scoped, so a DAG of repeated concept references expands exponentially (a reviewer's probe: a dozen chained concepts each referencing its predecessor twice gave a descriptor near 300 KB). All of it pre-exists in `build_input_form` and `/validate`; the branch moves it onto the run's hot path and into the SPI payload beside `graph_spec_dump`, where the direct orchestrator dumps the same artifacts a second time for the response. On a host serving a caller-supplied `library_id`, the delivered artifacts describe every method in that library, not only the one that ran. One measurement on a realistic library decides between narrowing the scope to the executed bundle (which changes what a viewer can resolve for a cross-bundle call), an expansion budget reported on `pipe_io_artifacts_error`, and leaving it. This absorbs the "Payload growth" entry below.
- **Key order and parity.** The run side's key order is the library's insertion order and validate's is `result.pipes`; nothing sorts either, and the parity test asserts byte identity only while the two key sets match. Sorting would break byte identity with the corpus already committed downstream, so this waits for the spec item L-260907-f6fd8d to say whether order is part of the contract.
- **`pipe_io_artifacts_error` is read by no local surface either.** The hosted half is the entry below; locally, a build failure leaves a complete-looking graph output (viewer, graphspec, `graph_files`) with the companions absent and one warning in the log. Surfacing it in the agent CLI's envelope and the human CLI's summary is the same contract question as the hosted marker.
- **Storage redelivery to a reused scope.** The delivery executor never removes a previous delivery's companions from a storage prefix; the scope identifies the run by contract and no optional result file (`tokens_usages.json`, the viewer) is invalidated there today, so this is the storage layout's property, not the companions'.
- **The removal sweep propagates `PermissionError` or `IsADirectoryError`** from a companion path that is not a plain writable file, before the agent CLI writes `live_run.json`; and `write_text` follows a symlinked companion to its target. A guard costs a try block; it waits for a report of the shape occurring.
- **Windows line endings.** Every byte-discipline write goes through `write_text` without `newline="\n"`, so a run's files and a regenerated corpus come out CRLF on Windows while the committed corpus is LF. Pre-existing in the corpus generator; `newline="\n"` on those writes is the fix.
- **Tests not written.** The agent CLI's `graph_files` companion keys have no test; the `PipeIOArtifacts` fixture in `tests/unit/pipelex/core/pipes/test_pipe_io_artifacts.py` duplicates `tests/helpers/pipe_io_artifacts.py`; the three-site retyping of the companion names (the writer, the delivery executor, the agent CLI) has no single list to drift from.

- **`pipe_io_artifacts_error` never reaches a delivered results prefix.** The delivery executor writes the three companions when the output carries them and nothing when it does not, so a hosted consumer cannot tell "graph tracing off" from "build failed" the way `tokens_usages.json` lets it tell for usage. The ratification rationale for the field was hosted visibility. The fix is a small marker beside the graphspec carrying the error, but its name is a new contract for the readers (`vscode-pipelex`, `pipelex-app`), so it waits for the spec item L-260907-f6fd8d to name it.
- **The agent CLI's live and dry runs share one companion set.** `live_run_graph.json` and `graphspec.json` sit in the same directory with one `input_form.json`; editing the bundle between a live run and a dry run leaves the older graph described by the newer declarations, exactly as `live_run.json` itself goes stale. Per-graph snapshots are a change to the agent CLI's file layout, not to this feature.
- **The artifacts describe declared output, not a step's effective `output_multiplicity`.** A `PipeLLM` declared `Text` and run with `output_multiplicity=2` returns a list while its contract says single. The validate report has the same property, and the graph viewer already lives with it; describing effective invocations is a change to the contracts themselves.
- **Describing dependency pipes.** Left out of the key set (design §4). Doing it needs the dependency's own qualified crate and alias-aware keys in the three artifacts, which is a protocol question before it is a runtime one.
- **Payload growth.** `pipe_io_artifacts` rides `PipeOutput` across the Temporal activity boundary and `pipe_io_artifacts_dump` rides the SPI payload for every graphspec-writing run. Measure a serialized `PipeOutput` on a large real method before the `pipelex-server` pin moves; Temporal's payload limit does not fail cleanly.
