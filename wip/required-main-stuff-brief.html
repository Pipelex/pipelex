Pipelex runtime · design note

A pipeline must always deliver its main output

Why reading a pipeline's result is uglier than it should be, the rule we adopted to fix it, and the API shape divergence we're tracking separately.

Branch feature/Required-main-stuff Full design: wip/required-main-stuff.md

TL;DR

  • Problem. A pipeline doesn't always deliver a main_stuff. One construct — PipeParallel with only add_each_output — never stamps it, so callers get a stale value, nothing at all, or (hosted) an empty result envelope. Every consumer pays with defensive code.
  • Decision. Every pipe run now delivers a main stuff. PipeParallel always combines its branch outputs into its declared output concept. The redundant combined_output field is deleted, and a new native.Composite concept covers the "just give me the named results" case.
  • Payoff. main_stuff stops being optional across the runtime, the wire, and the SDKs — a stale-output bug disappears and a pile of defensive branches gets deleted.
  • Side track. The two execution surfaces return the same data in different shapes: blocking POST /v1/execute nests everything under pipe_output (working memory in its transport encoding, main stuff reached via the main_stuff_name pointer), while POST /v1/start → delivery relays flat artifacts via GET /v1/runs/{id}/results — main_stuff (content pre-extracted), graph_spec, and working_memory too, as a clean render. Same information, two encodings — every client normalizes. Unifying them is a companion track, designed separately.

The symptom

Reading a result takes a page of guesswork

Our own starter project needs a normalizer just to get a pipeline's output. It checks whether main_stuff exists, falls back to walking the serialized working memory, and picks "the first entry whose content is a dict" — a heuristic, in code we hand to every new user:

# pipelex-starter-python/my_project/run_output.py (abridged)
def find_main_content(results: RunResults) -> dict[str, Any] | None:
    if isinstance(results.main_stuff, dict):      # /start → delivery shape…
        return results.main_stuff
    working_memory = results.pipe_output.get("working_memory")  # …or /execute blocking shape
    for entry in working_memory["root"].values(): # heuristic: first dict wins
        ...

Two distinct flaws feed this: main_stuff is optional, and the two execution paths return different shapes. This note covers the fix for the first and the plan for the second.

Root cause

One pipe doesn't stamp the main stuff

Every operator (PipeLLM, PipeExtract, PipeCompose, …) stamps its result as the working memory's main_stuff. So do PipeBatch and PipeCondition. The single exception: PipeParallel without combined_output. It drops each branch result into memory by name and leaves the main_stuff pointer untouched — and the language explicitly allows that as a pipeline's last step.

Failure modeWhen it happensWhat the caller sees
Stale The parallel ends a PipeSequence — the shared memory keeps the previous step's stamp The wrong output, silently
Missing The parallel is the main pipe, inputs came through the API path (no input alias) main_stuff_name = null; typed accessors raise
Empty envelope The /start → delivery path — delivery always writes working_memory.json, but the main_stuff.* artifacts are only written when a stamp exists A "successful" run with main_stuff: null — clients dig through the raw memory dump

Decision

PipeParallel always combines — and combined_output dies

The rule: a pipe run always delivers a main stuff. We enforce it at the one leaf that breaks it — PipeParallel now always combines its branch results into its declared output concept and stamps that as main stuff. Sequences, conditions, and nesting then deliver the invariant for free, and the stale pointer is always overwritten.

This also kills a redundant field. Today a combining parallel declares the same concept twice (output and combined_output), while a non-combining one declares an output that is a lie — it never produces it. After the change, output is the single, truthful declaration:

Before — output is a lie

[pipe.parallel_summarize]
type = "PipeParallel"
inputs = { input_text = "Text" }
output = "Text"   # never produced
add_each_output = true
branches = [
  { pipe = "sum_short", result = "short_summary" },
  { pipe = "sum_long",  result = "detailed_summary" },
]

After — combines into what it declares

[pipe.parallel_summarize]
type = "PipeParallel"
inputs = { input_text = "Text" }
output = "Composite"  # named combination
add_each_output = true
branches = [
  { pipe = "sum_short", result = "short_summary" },
  { pipe = "sum_long",  result = "detailed_summary" },
]

Declare a bespoke structured concept and the combination is fully typed (today's combined_output behavior, minus the duplicate line). Don't want to declare one? The new native.Composite concept holds the branch results under their names — the "dict of results" experience — while staying a first-class stuff that renders, serializes, and travels like any other. And a new static validation checks branch names against the declared structure at authoring time, so today's runtime combine error becomes a /validate error.

Side track

/execute and /start → delivery speak different shapes

The second flaw behind the ugly starter code: the two execution surfaces carry the same information in structurally different results. POST /v1/execute blocks until the run completes and responds with the runner's native envelope: everything nested under pipe_output, the working memory in its cross-process transport encoding (type-metadata keys, lists flattened — built for rehydration, not reading), and the main stuff not extracted — you follow the main_stuff_name pointer into root and unwrap .content yourself.

POST /v1/start returns immediately; the run then goes through delivery, which writes a folder of result artifacts to storage — working_memory.json, main_stuff.{json,md,html}, main_stuff_viewer.html, graphspec.json, mermaid/reactflow views — and GET /v1/runs/{id}/results relays three of them as flat fields: main_stuff (the output content, pre-extracted), graph_spec, and working_memory (a clean render). So it's not that one path lacks the memory — both carry it. What differs is the envelope, the main-stuff addressing, and the memory encoding — and the SDK only names a subset (working_memory rides along as an unnamed extra field). Every client normalizes.

Rollout

Three phases, breaking by design

No backward compatibility, per house policy — combined_output disappears and existing .mthds files migrate (mechanically: delete the redundant line, or make the declared output truthful).

  1. Runtime + language surface (pipelex repo): always-combine, delete the field, add native.Composite and the static branch-name check, migrate fixtures, regenerate the MTHDS schema.
  2. Enforce the invariant: tighten the defensive optional_main_stuff branches (delivery, graph tracer, CLI, telemetry) and make main_stuff_name non-optional on the wire models.
  3. Cross-repo sweep (gated on a pipelex release): MTHDS spec + JSON schema, plxt pinned schema, conformance, plugin skills, app/UI TypeScript types, cocode pipelines, docs sites, SDKs + starter.
