pipelex · v0.46.0

Configuration migration: repairing a user's file instead of throwing it away

We changed the shape of every configuration file pipelex reads — and built the machinery that makes that survivable on a machine that already has one. Migration is now recorded as data, replayed over real files, and enforced by gates that refuse a schema change nobody accounted for.

Release v0.46.0 9 merged PRs · #1117 cuts the release Author-facing doc — for co-developers

TL;DR

The problem: a schema change used to be a landmine. pipelex init never overwrites, so every machine in the field kept its old file, and the next boot died on extra="forbid" naming a key the user never chose to have. The only remedy we could offer was pipelex init — which resets the file and discards their API keys, buckets and log levels.

What we built: every configuration surface now carries a checked-in ledger recording each shape change as data. pipelex migrate replays it over a user's real files, in place, keeping their values and taking a timestamped backup. A stale-but-explainable config no longer stops the boot — it warns. Three gates make it impossible to land a schema change without the entry that repairs it.

What you need to do: after pulling, run pipelex migrate once. If you touch a config model and make cmig refuses, invoke the add-migration skill — never regenerate the goldens to silence it.

Why a "just edit the model" change was never just that

Three of the four surfaces below changed shape in this release, and each change was, by itself, reasonable. The reshape gave pipelex.toml a scheme. Retiring prompting_target made templating an authoring decision. Neither is controversial. What made them dangerous is that configuration files are the user's: we ship defaults, they edit and keep them, and we never overwrite. So a field we delete lives on in their file forever, and the strict loader that protects them from typos is exactly what turns our cleanup into their broken boot.

The failure had a particularly bad shape. The error named a key — but not which file put it there, and certainly not whether that key was correct last month. A user reading Extra inputs are not permitted: prompting_target has no way to tell a typo from a field that we removed.

The ledger: a migration is data, not code

The core move is that a shape change is recorded, in a checked-in TOML file, as a list of structural operations. Not a Python function — data. That is what lets the same record be replayed by the command, rehearsed by the boot, verified by a gate, and read by a human.

The reshape entry, as it actually ships 
[[migration]]
id = "pipelex-config@3"

The walk is deliberately narrow: the global ~/.pipelex/ and the project .pipelex/, those two only, one level deep, and into a subdirectory only when a configuration family owns it. inference/backends/ is such a directory; inference/deck/ is not and is never entered. A file is claimed by the pair (directory, name) — which is what stops inference/backends/pipelex_gateway.toml, a pipelex_*.toml match by name, from being rewritten under the main config's ledger.

Boot tolerance: a stale file warns, it does not stop the world

The command alone would not have been enough. A user upgrades, boots, and dies before they ever see a message telling them to run it. So when a surface fails to validate, its ledger is replayed over the same files in memory and the result re-validated.

Critical diff — the retry seam (config_surface.py)

Two things in here are load-bearing and easy to break. The import is deferred for an architectural reason, not for speed; and a file that cannot be read abandons the whole retry rather than being skipped. 

+ # Imported here rather than at module level, and the reason is architectural: the
+ # engine's applier lives under an interpreter package, while this module sits in
+ # runtime_hub's import closure — the kernel layer, which loads zero interpreter modules.
+ from pipelex.migration.engine import replay_ledger_over_text  # noqa: PLC0415
+
+ for path in paths:
+     try:
+         text = path.read_text(encoding="utf-8")
+     except FileNotFoundError:
+         continue
+     except (OSError, UnicodeDecodeError):
+         return None   # <- abandon, do NOT skip: dropping a layer from the merge
+                       #    could re-validate green and boot a config the user
+                       #    does not actually have
+     replay = replay_ledger_over_text(ledger=ledger, text=text)
+     deep_update(merged, updates=tomlkit.loads(replay.text).unwrap())
+
+ if all(plan.is_clean for plan in plans):
+     return None       # <- the ledger has nothing to say; not staleness.
+                       #    The caller's own error stands.
A healthy configuration pays nothing. It reads no ledger, re-parses no document, and does not even import the migration engine. That deferral is doubly required: the applier lives in the interpreter layer and the config loaders sit in the kernel layer, which must not load it.

The gates: you cannot land a schema change without accounting for it

A ledger nobody is forced to write is a ledger that will be forgotten on the one change that mattered. Three checks close that.

GateQuestion it asksRuns in
make check-ledger
cl		 Is what this entry says legal, and is replaying it harmless? An op may only act on material some version removed; replaying the whole ledger over the reference documents must return the very bytes it was given. agent-check + check
make check-migration-schemas
cmig		 Did a schema change go unaccounted for? Recomputes each surface's fingerprint and refuses a removed path, a lost enum spelling, or a narrowed value domain that no entry repairs. Also performs every migration against frozen before/after documents. check only
make up-migration-schemas
umig umigf		 Regenerates the goldens. Deliberately left make up — rewriting a head golden after deleting a field erases the very removal the gate exists to catch. on purpose, by hand
Because cmig is not in agent-check, an unaccounted schema change reaches a release unseen. That is why /release gained step 3b, which blocks on it and confirms a **Migration:** changelog bullet for every new breaking entry.

Catching a narrowing — the class of change that looks additive

A change can keep every path and every enumerated spelling and still break a user's file: int becomes str, a free string becomes an enum, a bound moves from ge=1 to ge=5. Read as a path diff those look like additions, so the gate used to ask for a golden regeneration, demand nothing, and let the next boot reject a valid file with a green gate behind it. The verdict is now split by direction.

To see a bound at all, the fingerprint has to record one — which is why annotated-types became a declared runtime dependency. It is a closed whitelist, and pattern is excluded permanently: regex containment is not decidable, so every pattern edit would read as a tightening and teach everyone to wave the gate through.

Critical diff — the constraint whitelist (fingerprint.py) 
+ from annotated_types import Ge, Gt, Le, Lt, MaxLen, MinLen, MultipleOf
+
+ CONSTRAINT_ATTRIBUTE_BY_CARRIER: dict[type[Any], ConstraintKind] = {
+     Gt: ConstraintKind.GT,   Ge: ConstraintKind.GE,
+     Lt: ConstraintKind.LT,   Le: ConstraintKind.LE,
+     MinLen: ConstraintKind.MIN_LENGTH,
+     MaxLen: ConstraintKind.MAX_LENGTH,
+     MultipleOf: ConstraintKind.MULTIPLE_OF,
+ }
+ # pattern is excluded ON PURPOSE and permanently.

The fingerprint is not raw model_json_schema() — that moves for reasons having nothing to do with our schema (ref layout, titles, ordering, pydantic's own version). A gate that cries wolf gets regenerated reflexively, and that is how a gate dies.

Replay neutrality, checked rather than asserted

The guarantee every machine depends on: replaying a ledger over a file already valid changes not one byte. The reference documents cannot prove it — they carry exactly one value per key, so they never reach the other legal spelling of an enumerated field. hypothesis (dev-only) generates documents that do, and checks neutrality, idempotence and prefix coherence.

Each generator carries its own vacuity check — test_the_generator_does_not_merely_re_emit_the_reference_document, test_the_generator_reaches_every_mutation_kind. Every one of these properties is trivially true over documents nothing acts on, so without those guards a green suite would prove nothing.

The breaking changes that rode along

[runtime.log.rich_log]

[runtime] / [inference]
[interpreter] / [kit]

Four roots mirroring the layers the code already had. The redundant _config suffix goes at every depth — class names keep theirs, because the redundancy was in the key, not the type. Three things are dropped rather than moved: [migration.migration_maps], session_id, and plugins.boot_orchestrator (now strictly a boot argument).

Templating style is now an authoring decision — pipelex-config@2 + inference-backend@2

How a pipe's inputs are tagged into a prompt is declared on the pipe, not inferred from the model — so the same method renders the same prompt shape everywhere. The global default is now XML tags instead of back-ticks, which means every prompt rendered for an OpenAI-family model changes shape. Compose, image-gen, search and structuring prompts follow the same default.

This is the change that created the inference-backend surface. #1104 deleted prompting_target from every backend file we ship — but those files were reachable by no surface, no walk and no gate, so the key survived on every installation that predates it, where it is fatal twice over: in [defaults] it is copied wholesale into every model of the file, and on a single model it is rejected by name.

Unknown per-model backend keys must be header-shaped

An unrecognised key in a per-model table is sent to the provider as an HTTP header. That mechanism is now documented and gated on shape: it must contain a hyphen. A typo like max_tokns used to go out on the wire silently while the real setting stayed unset; it now fails the boot naming the key, the model and the file. The key must also be usable as a header — RFC 7230 token characters, printable single-line string value.

Working with this from now on

  1. You change a config model. make cmig refuses, printing a fingerprint diff.
  2. Invoke the add-migration skill. It is the only thing that writes a ledger — it derives the entry from what the gate refused, bumps the schema version, regenerates the goldens and adds the changelog bullet.
  3. Never regenerate goldens to silence the gate. A green gate over an unaccounted removal is precisely the failure it exists to prevent.
  4. At release, step 3b blocks until every new breaking entry has a **Migration:** bullet naming its id, and a correct introduced_in.
Dogfood finding from cutting this release. A stale untracked .pipelex/pipelex_override.toml on a dev machine reddened three tests with Extra forbidden fields: 'pipelex'. It is not a code defect — it is exactly the situation this work exists for. Note that pipelex migrate has no scoping flag: it walks both directories, so it will also rewrite your global ~/.pipelex/inference/backends/*.toml. Backups are automatic, but be aware if you share a global config across worktrees.
