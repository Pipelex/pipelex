# Comment fidelity across a move — the bug report after v0.46.0, and what closed it

**Status: fixed on `fix/Migrator` (PR #1118, merged to `dev`), shipped in v0.46.1.** The applier now keeps a comment on the item it introduces through `move_key`, `delete_key` and `delete_table`, and settles what `set_key` and `ensure_table` insert before a table's trailing banner rather than after it. This note records why the phase-0 spike wrote the behaviour off as unfixable, why that was wrong, the rule that was chosen and where it is a reading rather than a fact, and what it does not do for files already migrated by v0.46.0.

## The report

> "The migration moves tables but not the comment banners, so banners ended up above the wrong tables."

Exactly the consequence the phase-0 spike measured on the kit template and the S1 contract then stated as a limitation (`docs/migration-ledger.md` → "Limits you will meet", now rewritten). A `~/.pipelex/pipelex.toml` seeded from the kit template is a banner block per section plus a comment per key; the reshape entry `pipelex-config@3` moved most sections, and each banner stayed where it was while its section left, so the migrated file read `# Log Config` above one section and `# Plugins` above another. Valid TOML, lying comments.

## Why the spike thought it could not be fixed, and why it can

The spike's finding was that tomlkit stores a banner "as trailing trivia of the previous sibling, inside that sibling's serialized string", so carrying it "would mean string surgery on a neighbour's tail". The first half is right and the second is not. Comments and blank lines are discrete keyless body entries — `(None, Comment)` and `(None, Whitespace)` — of whichever container the parser was filling when it met them: a comment above a key sits before that key in the same container, and a banner above a `[table]` header sits at the *tail of the previous table in document order*, inside its deepest last container, because everything up to the next header belongs to the table being parsed. Discrete entries can be located, detached and re-inserted; nothing about it is string surgery. What the library does not have is any notion of which item a run of trivia is *about*, and that is the part that needs a rule.

Three symptoms share the root cause, and a fix has to take all three: a moved table left its banner behind; a moved table carried the *next* table's banner away, because that banner sat at the moved table's own tail; and a table appended under an existing parent landed *after* that parent's trailing banner, stealing it the same way. The same held for keys — a moved scalar landed after the destination's trailing banner, and a deleted key left its own comment dangling onto the next one — and for the `.mthds` fix path, where a comment above a stripped native-concept redeclaration used to reflow onto the next table (a test pinned that as a "known artifact"; it now pins the fix).

## The rule

**A run of own-line comments and blank lines introduces whatever comes next.** A moved item takes its introduction along and leaves its trailing run — the next item's introduction — where it was; a deleted item drops its introduction and keeps its trailing run in place; an item inserted at the end of a table — a moved one, a key `set_key` adds, a table `ensure_table` creates — lands before that table's trailing run, never after it. Everything is put back where the parser would have put it — a previous table's deepest tail rather than an implicit parent's own body — because a comment inside a super table's body is exactly what makes tomlkit start rendering a `[parent]` header the file never had.

Two refinements decide the ambiguous cases, and both were forced by real files rather than invented:

- **Only the last comment block travels.** The kit template opens with a thirty-line file preamble, a blank line, the first section's banner, a blank line, then `[runtime.storage]` — one contiguous run of trivia. Taking the whole run would move the preamble to wherever the storage section lands. So what travels is the last block of consecutive comments, with the blank line above it and whatever follows it; earlier blocks stay. A run with no comment at all is spacing and moves whole. At the very top of the document, a *lone* comment block that a blank line separates from what follows is treated as the file's preamble and stays — only the blank line after it travels — so a hand-written config that starts `# My pipelex config` and then a section keeps its header line at the top.
- **The first entry of an implicit parent is introduced by what sits above the parent.** `[runtime.storage]` opening a file that never writes `[runtime]` is the first entry of a super table whose header is not rendered; its banner is at the root, above the `runtime` item. The applier climbs through such parents in both directions (finding the introduction, and putting the trailing run back), and only through them — a parent that renders a header owns what sits above it. A dotted assignment is the same shape — `pipelex.storage_config = { … }` at the top of a hand-written override is a `pipelex` super table whose header tomlkit never writes because the owning key is dotted, so the predicate that decides whether a parent renders a header takes the owning key into account, exactly as tomlkit's renderer does. The same climb handles a key that is the first entry of one *chunk* of an out-of-order table (`defaults@2.toml`, the frozen pre-reshape defaults, is written that way, and the reshape's `templating_config` move hit exactly this), and the case where deleting the last key of such a chunk makes tomlkit drop the emptied chunk from the parent altogether.

The rule is a reading and the doc says so: it is right for banners above sections, for the kit's per-key comments, and for preambles; it is wrong for a comment written on its own line *below* a key to annotate it, which will follow the next item. Inline tables are left alone — their whitespace entries are layout.

## What is pinned

`tests/unit/pipelex/pipeline/fixes/test_fix_applier_comment_fidelity.py` compares bytes: the three-symptom cases, the kit-style per-key comments, a table with a sub-table, deletes, the top-of-file shapes, an empty explicit destination, a nested created parent, an array of tables, a wildcard op applying several times over one document, and — the case the report was about — the shipped `pipelex-config` ledger replayed over the frozen pre-reshape defaults, asserting banner by banner that each `# <Name> config` still introduces its section wherever it moved, that the deleted section's banner is gone, and that every banner in the migrated file introduces a header. `test_fix_applier_config_surface_shapes.py`'s banner test now goes through the applier and asserts the guarantee instead of the limitation.

## What it does not do

- **Files already migrated by v0.46.0 are not repaired.** Replay is neutral on a current file, so nothing touches them again; the misplaced banners in such a file are a matter of hand-tidying, or of restoring the `.bak` beside it and running `pipelex migrate` again. The changelog says so.
- **A comment written below a key to annotate it** follows the next item. Stated in the contract as the cost of the rule; no heuristic distinguishes it from a banner without a blank line above the header, and the kit's own per-key style (comment glued above the key) is the far more common shape.
- **A comment sitting between two dotted chunks of one key** (`k.x = 1`, a comment, `k.y = 2`) is orphaned when `k` moves — tomlkit merges the chunks on the way and the applier does not chase the gap. Rare, and no worse than before.
