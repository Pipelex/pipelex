Pipelex · cost-reporting rework

From a leaky in-process registry to event-sourced cost on the run result The UsageRegistry success-path leak fix & distributed cost reporting — one piece of work

Status: shipped on fix/For-API-update PR #967 (core) · #968 (rename) Validated backend: NDJSON only — DynamoDB deferred

TL;DR

Cost reporting used to ride on a per-run, in-process UsageRegistry buffer. That buffer leaked on every successful run (it was only closed on the failure path) and it could not see usage from other worker processes, so distributed (Temporal) runs never reported their true cost. We removed the registry entirely and made cost an event-sourced artifact that rides back on PipeOutput, exactly like graph_spec already does.

  • The leak is gone by removal. No submitter-side registry is opened anymore, so there is nothing to leak — the bug is structurally impossible, not just patched.
  • Cost now rides on the run result. New PipeOutput.tokens_usages is assembled from the trace-event stream at end-of-run, in both direct and Temporal modes. A multi-worker run aggregates usage from every worker into a single end-of-run cost report.
  • New --costs / --no-costs switch (default on) decouples cost collection from --graph over a shared event-log transport. The old --cost-report flag is removed (no back-compat).
  • --mock-inference fakes the LLM leaf with reportable synthetic usage so the cross-worker path can be validated cheaply and deterministically — no tokens billed.
  • Companion rename (#968): GraphContext → TraceContext and the internal gate is_generate_costs → is_generate_usage — the object carries two streams (graph + usage), so it's named for what it is.
⚠ Read this — scope of what shipped

We only implemented & validated the cost-reporting event log through NDJSON. The read-back is backend-agnostic, so the code path covers DynamoDB for free — but making distributed cost reporting actually work on DynamoDB is deferred and is not a validation target of this work. Local NDJSON is the one backend we care about and test here.

1.Two bugs that were really one lifecycle

The investigation started as a narrow "the registry leaks on success" bug. On closer look it was the same object lifecycle as the long-deferred distributed cost-report aggregation. The UsageRegistry is a per-run, in-process cost buffer whose full lifecycle is open → populate → report → close. Two different steps were broken:

  • The leak = the close step never ran on the success path. The registry was opened in pipeline_run_setup but closed only inside if not success:. In a long-lived process (e.g. the Pipelex API) this orphaned a registry on every request, and reusing a pipeline_run_id could even collide on the leftover.
  • Distributed cost reporting = the cross-worker replay-populate step was never wired. Usage events from inference activities on separate worker processes landed in the backend but were never read back into a report. Cross-worker runs reported nothing.

Because they're the same lifecycle, fixing them separately would have meant baking in registry-placement decisions for the leak that the cost-reporting design then had to unwind. So they were designed and built together.

2.The fix — mirror graph-spec assembly (Option B)

Graph tracing had already solved the exact cross-worker problem: "analyze the event stream at the end of the run and ride the artifact back on PipeOutput." Cost reporting now does the literal same thing. We removed the submitter-side registry and instead assemble usage from the trace-event stream at the same hook that assembles the graph, attaching it to PipeOutput.tokens_usages. The submitter renders the cost report from that field.

✓ Why removal beats "remember to close"

With nothing populating a submitter-side registry, there is no registry to leak — on every entry point and both backends. The live _try_add_to_registry path and the dead inject_tokens_usages retired with it. The leak fix is a structural guarantee, not a discipline you can forget.

3.The load-bearing decoupling — --costs over a shared transport

This is the one piece that's not cosmetic. Previously usage events were only emitted when --graph + tracing were on (the event log was created inside if is_generate_graph). Once the live registry is gone, --no-graph would lose cost entirely. So we added a dedicated, default-on --costs switch that mirrors --graph: the event log is the shared transport; each switch gates its own event type and its own assembler; each rides its artifact back on PipeOutput.

4.Distributed cost reporting — cross-worker → one report

In Temporal mode a single logical run can span several processes: a parent workflow on one worker, a child on another, the inference activity on a runner. Every UsageReportEvent lands in one partition with a writer_id to disambiguate the producer. At end-of-run, a single event read feeds both assemblers, and the aggregated usage rides home on PipeOutput.

ℹ Single source of truth = events

In direct mode, inference no longer also adds to a live registry — that path was removed. Cost always comes from the aggregated event stream, so there is no double-counting to guard against. One run, one source.

5.--mock-inference — validate the distributed path for free

Proving cross-worker cost reporting used to need real LLM spend in a real multi-worker topology. --mock-inference is a LIVE run (operators dispatch real activities — the true distributed path is exercised) whose AI call is faked at the inference leaf with reportable, non-zero synthetic usage. So a cost report actually renders from cross-worker usage, deterministically, with nothing billed.

  • It is not --dry-run: dry-run swaps the generator before dispatch, so it never reaches the activity and emits zero-token (suppressed) usage. Mock-inference keeps run_mode = LIVE and mocks only the leaf — the one thing dry-run can't validate cheaply is a rendered cost report.
  • LLM leaf only. Image-gen / extract / search under --mock-inference fail loud with MockInferenceUnsupportedError (pointing at --dry-run) rather than silently calling the real provider — their output is stored above the leaf, so a leaf-level mock would push synthetic data through the storage path.
  • Mutually exclusive with --dry-run; main run subcommands only (agent CLI deferred).

④ The only cost renderer is now event-sourced new module

The main CLI renders from pipe_output.tokens_usages. One aggregation pass feeds both the suppression decision and the render. Note the gate: dry runs are suppressed, but real runs on free/zero-price models still report their token usage (with a zero total) — gating on cost alone would wrongly hide them.

pipelex/reporting/cost_report_renderer.py 
def render_run_cost_report(
    *, pipeline_run_id: str,
    tokens_usages: Sequence[AnyTokensUsage] | None,
    is_generate_costs: bool,   # public flag name kept; cost domain stays cost-named
) -> None:
    if not is_generate_costs or not tokens_usages:
        return
    reporting_config = get_config().pipelex.reporting_config
    print_to_console = reporting_config.is_log_costs_to_console      # default now TRUE
    is_csv_enabled  = reporting_config.is_generate_cost_report_file_enabled
    if not (print_to_console or is_csv_enabled):
        return
    try:
        aggregated = CostRegistry.aggregate_costs(tokens_usages)    # single pass
        if not aggregated.has_reportable_usage:                     # any tokens OR any cost
            return                                                  # → suppresses dry runs only
        ...
        CostRegistry.render_report(aggregated, pipeline_run_id=pipeline_run_id, ...)
    except (OSError, UnicodeEncodeError, PipelexError) as e:
        log.warning(f"Cost report generation failed (run succeeded): {e}")

A cost-report failure never fails an otherwise-successful run — aggregation, CSV setup, and render all sit inside one run-succeeded try. The agent CLI takes a different path: no Rich table, a machine-readable cost_report object on its --with-memory JSON envelope instead.

8.Companion rename (#968) — GraphContext → TraceContext

Once usage rides on the same per-run object as the graph, the name GraphContext under-described it — a cost concern was riding on something called "Graph." But usage isn't a free-rider: each UsageReportEvent.node_id is stamped from the context's parent_node_id, so graph events and cost events are two projections of one substrate — the per-execution node tree. The rename names the object for what it is.

Renamed

  • GraphContext → TraceContext (file, type, the graph_context attribute incl. JobMetadata.trace_context)
  • is_generate_costs → is_generate_usage (config field; the gate feeds emit_usage_events, so "usage gates usage")
  • with_execution_overrides(generate_costs=…) → generate_usage=…

Deliberately kept

  • The public --costs / --no-costs flag — "costs" is the deliverable the user asked for.
  • The whole cost domain: CostRegistry, cost_report_renderer.py, render_run_cost_report(is_generate_costs=…) — they genuinely compute money.
  • The graph_id → run_id nit — deferred to a focused follow-up.

9.Explicitly deferred / non-goals

⚠ The headline deferral — DynamoDB

Distributed cost reporting is validated on NDJSON only. The end-of-run read-back is backend-agnostic, so DynamoDB rides along in the code path for free — but the DynamoDB-specific concerns (BatchWriteItem batching, the shared-filesystem invariant, per-thread writer_id) are not exercised or guaranteed by this work. Treat DynamoDB-backed distributed cost reporting as unproven until it's a deliberate validation target.

Other deliberate non-goals (none block the shipped work)
  • Cost-per-node breakdown. Each UsageReportEvent already carries the producing pipe's node_id, but the report aggregates by model only. A per-node view is a future projection over the same stream — data's already there.
  • Costs-only in-memory tracer skip (deep half of E1). Under --no-graph --costs the tracer still accumulates the in-memory graph (cheap; never assembled). The cheap half — gating per-pipe serialization on emit_graph_events — landed; fully skipping the tracer is deferred (must still mint node ids for usage attribution).
  • --mock-inference coverage. LLM leaf only; img-gen / extract / search fail loud. Agent CLI doesn't expose it yet. Full per-operator synthetic-output coverage comes via the dry-run-refactor follow-up (run_mode=DRY).
  • Two design decisions (see cost-report-deferred-decisions.md). #3 — cost reporting is coupled to tracing_config.is_enabled (costs-on + tracing-off ⇒ no report). #6 — the agent CLI gates on the raw costs param while the main CLI gates on the resolved is_generate_usage config. Both want a deliberate call, not a reflexive patch.
  • T3 — request-scoped tracing state instead of the process-singleton ReportingManager. Removing the registry shrank the singleton's surface but the per-context dict remains. Open follow-up.
  • Pre-existing bugs flagged, not fixed here: the cost report ignores reasoning/audio/prediction token costs; DIRECT vs Temporal object re-validation use different dump modes. Both predate this work.
