# Registry / cost-reporting — deferred follow-ups

Durable home for the follow-ups this feature deliberately left out of scope. The leak fix + distributed cost reporting shipped in **PR #967** (+ companion rename **#968**); see [`cost-reporting-overview.html`](cost-reporting-overview.html) for the as-built overview. The items below are the known, intentional non-goals — none blocks the shipped work.

Two further deferred items — both *design decisions* rather than follow-up work — live in their own doc: [`cost-report-deferred-decisions.md`](cost-report-deferred-decisions.md) (#3 cost reporting coupled to `tracing_config.is_enabled`; #6 agent-CLI vs main-CLI "is cost reporting on?" gating divergence). Those want a deliberate call; the items here are scoped work to pick up when signals warrant.

## Optimizations

- **D5 — costs-only in-memory tracer skip (deep half of review item E1).** In `--no-graph --costs` mode the graph tracer still runs in memory (minting node ids, accumulating the in-memory graph) even though no `GraphSpec` is ever assembled or output. Phase 2 landed the *cheap* half: per-pipe graph serialization (`pipe_abstract.py` IOSpec dumps, pipe/concept registry, `pipe_parallel.py` controller-output registration, `graph_tracer.teardown` spec build) is gated on `emit_graph_events`, so costs-only no longer pays for serialization. The *deep* half — skipping the in-memory tracer entirely in costs-only mode — is deferred. Watch-item: `on_pipe_start` still mints node ids so usage-event `node_id` correlation is unaffected; any skip must preserve that.

- **Cost-per-node correlation via `UsageReportEvent.node_id`.** Each `UsageReportEvent` already carries the `node_id` of the pipe that produced it, but the assembled cost report aggregates by model only. A future report could break cost down per graph node (which pipe/step cost what), correlating usage events to graph nodes via `node_id`. Not built; the data is already in the event stream.

## Altitude / architecture

- **Review item A1 — `TraceContext.from_execution_config(...)` factory.** The `(graph, costs) → (event_log routing, set_event_log, flags)` decision is currently made at each tracing arm (DIRECT `pipeline_run_setup`, TEMPORAL `wf_pipe_router`). A2 captured most of the value by threading the emit flags into `open_tracer`/`setup` (so the returned `TraceContext` is born correct and the post-hoc `model_copy` footguns are gone). A single factory that owns the whole decision for both arms is the remaining polish — deferred as low-value-now.

- **`graph_id → run_id` rename + the shelved `TraceContext` split (left over from the merged #968 rename).** #968 renamed `GraphContext → TraceContext` and the gate `is_generate_costs → is_generate_usage`, but deliberately parked two follow-ons: (1) the `graph_id → run_id` field rename — it really is the run id, but the rename ripples into the graph-named `GraphTracerManager.open_tracer(graph_id=…)` plumbing and the `make_node_id` format, so it wants a focused pass; (2) a *type* split — a `TraceContext` base with a `GraphContext(TraceContext)` subclass (Option 2), or extracting the `emit_graph_events` / `emit_usage_events` toggles into an `EmitPolicy` value object (Option 3). Both splits are low-value now: the node tree is **always** built (even under `--no-graph --costs`, per D5), so the runtime object is always the full graph-capable context — a split would only narrow what the reporting seam is allowed to *see*, never drop machinery. Revisit Option 2 only if reporting grows graph-independent consumers; Option 3 only if a third trace stream appears. Do **not** touch `UsageReportEvent.node_id` — cost-per-node attribution to the tree is a deliberate feature.

- **Review item T5 — `wf_pipe_router.py` setup-failure `except` doesn't restore `job_metadata.trace_context`.** On a tracer-setup failure the pipe can run with a `tracer_key` pointing at a closed tracer. Pre-existing latent issue (not introduced by this work; Temporal is unshipped — see [[project_temporal_not_shipped]]). Flag-and-fix candidate, parked.

- **T3 — request-scoped tracing state instead of the process-singleton `ReportingManager`.** The deeper refactor in the distributed-execution track ([`../distributed-execution/tracing-cost-reporting.md`](../distributed-execution/tracing-cost-reporting.md) T3). Removing the submitter-side `UsageRegistry` shrank the singleton's surface, but the per-context `_event_log_contexts` dict on a process-global manager remains. Open follow-up.

  **Facet flagged on PR #967 (codex, P1) — activity usage writes can mutate a workflow-registered buffer.** In a *single-process* Temporal deployment (one worker hosting both `WfPipeRouter` workflows and the inference activities), the workflow registers its `BufferingEventLog` in the process-global `ReportingManager._event_log_contexts`. An inference activity in the same process then hits the fast path (`_emit_via_registered_context`) and appends to the workflow's in-memory buffer — an activity side effect that is **not** part of Temporal's deterministic replay (the activity *result* replays from history, but the buffer append does not), so on replay the later drain/flush can diverge or drop usage. **Why this is deferred, not patched on this PR:** (1) it is *pre-existing* — the fast path + per-context registration predate this work (the registry track kept the emit core unchanged; it only removed the submitter-side registry), so PR #967 neither introduced nor worsened it; (2) the **recommended split router+runner topology does not hit it** — activities run on the runner process, which never registered the workflow's buffer, so they correctly take the per-process activity-log fallback; (3) the clean fix is request-scoped tracing state (this T3 refactor) or making activities always bypass workflow-registered buffers — bolting Temporal-awareness (`activity.in_activity()`) into the generic, non-Temporal `ReportingManager` would be a layering violation; (4) Temporal is not shipped to prod. Pick this up with the T3 refactor.

- **Costs-only event-log handle relies on `__del__`, not an explicit close (codex P2, PR #977 v0.32.0 release re-review).** In `--no-graph --costs` mode, `pipeline_run_setup` creates the `event_log` and registers it on the report delegate (`set_event_log`) but passes `event_log=None` to the tracer (D5: costs-only emits no graph events). So the tracer never owns it, and `GraphTracer.teardown()` — the only path that *explicitly* closes an event log — has nothing to close. On run end, `runner.py` (and the setup error-path) call `ReportingManager.clear_event_log`, which only `pop`s the `_event_log_contexts` entry; it does **not** close the log. The NDJSON file handle is therefore closed only by `NdjsonEventLog.__del__`. **This is *not* the unbounded FD leak the finding described:** `make_event_log` returns a *fresh* `NdjsonEventLog` per run, so once `clear_event_log` drops the delegate's reference (and the setup-local falls out of scope) the instance is refcount-collected and `__del__` closes the handle promptly under CPython — no descriptor growth across runs. The valid residual is that the costs-only path has no *explicit* close and leans on GC finalization. **Clean fix:** have `ReportingManager.clear_event_log` close the popped context's `event_log` before discarding it (`NdjsonEventLog.close()` is idempotent — in `--graph --costs` mode the tracer's `teardown` close and this close are both safe, the second being a no-op). Deferred off the v0.32.0 release branch (docs-only pass); land via normal `dev` flow. Closely related to **T3** above — the request-scoped `_event_log_contexts` refactor would subsume this.

## Pre-existing gaps surfaced during the PR #967 final review (flag, not fix-here)

These were found by the gstack `/review` adversarial pass (Codex + Claude). They are **pre-existing** (not introduced by the registry/cost work) and out of scope for this PR's purpose, so they are flagged here rather than expanding the PR. Per the repo "flag and fix existing bugs" rule, each is a candidate follow-up.

- **Cost report ignores reasoning / audio / prediction token costs.** `CostRegistry.complete_cost_report` only computes cost for `INPUT` (→ joined/cached/non-cached) and `OUTPUT`; `aggregate_costs` / `compute_total_cost` only sum those. The `TokenCategory` enum also has `OUTPUT_REASONING`, `OUTPUT_AUDIO`, `OUTPUT_ACCEPTED_PREDICTION`, `OUTPUT_REJECTED_PREDICTION`, `INPUT_AUDIO` — providers (e.g. the OpenAI Responses factory) populate some of these, but their cost is never computed or summed, so a run with reasoning/audio tokens **under-reports total cost**. Pre-existing (this PR only refactored `compute_total_cost`; it did not change the category set). Fixing it properly means extending `compute_cost_report` / `complete_cost_report` / `aggregate_costs` / the render columns / the agent summary to handle the extra categories, with per-provider unit-cost wiring — a cost-model change, separate from the leak/distributed work.

- **DIRECT vs TEMPORAL object re-validation use different dump modes.** `ContentGenerator._revalidate_against_object_class` (DIRECT) dumps with `model_dump(serialize_as_any=True)` (python mode) while `ContentGeneratorInWorkflow` (Temporal) uses `model_dump(mode="json", serialize_as_any=True)`. Same logical re-validation, two serialization modes — so a `--mock-inference` synthetic object (or any object) can round-trip cleanly in one execution mode and raise `MockInferenceObjectFidelityError` in the other. The divergence predates this PR (each arm kept its existing behavior), but the shared-helper framing makes it load-bearing. Aligning the two on one canonical mode is the durable fix; which mode is canonical is the judgment call.

## `--mock-inference` coverage

- **LLM leaf only.** `--mock-inference` mocks the LLM inference leaf (`llm_gen_text`/`object`/`object_list`). Image-gen / extract / search **fail loud** with `MockInferenceUnsupportedError` (their output is stored *above* the leaf by `generated_content_factory`, so a leaf-level mock would push synthetic data through the storage path — whereas `ContentGeneratorDry` short-circuits storage). Full per-operator synthetic-output coverage comes via [`../dry-run-refactor/followup-leaf-run-mode-mock.md`](../dry-run-refactor/followup-leaf-run-mode-mock.md) B2, which replaces each hard guard with a real synthetic-output branch.

- **Main `run` subcommands only.** The flag is on `pipelex run pipe|method|bundle`, not the agent CLI. The mechanism (`JobMetadata.is_mock_inference` + leaf branch + `PipelexRunner`) is surface-agnostic, so the agent CLI can adopt it trivially when needed.

- **`is_mock_inference` fate after the dry-run-refactor follow-up.** Decided 2026-06-06: build the interim flag now (Phase 5 is the follow-up's B1 core — a reusable leaf-level dry helper), settle retirement at B2. Open sub-decision: *fully retire* `--mock-inference` (DRY-on-Temporal covers cross-worker dispatch + `tokens_usages` assembly once it dispatches) vs *keep a thin reportable-mock* (DRY emits zero-token usage → suppressed report, so the cheap *rendered* cost-report validation — Tier 8b — is unique to a non-zero mock). Decide at B2 time. See [`../dry-run-refactor/followup-leaf-run-mode-mock.md`](../dry-run-refactor/followup-leaf-run-mode-mock.md).
