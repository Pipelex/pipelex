Test durations: refreshing the shard map in seconds, not minutes

Why .test_durations was costing us a full suite run and a 21,000-line diff at every release — and what we replaced it with.

Working notes · 2026-08-18 · shipping in v0.46.1

TL;DR

  • make store-test-durations no longer runs the whole test suite. It collects the tests (~8s), measures only the ones missing from the map, and leaves recorded values alone. A typical release refresh went from several minutes to a few seconds, and from a 21,000-line diff to no diff at all.
  • The reason is one measurement. A duration map can be wrong two ways — stale values, or missing entries. We measured both against the real 8-way split. Stale values across 17 days cost about 7% of shard balance. Missing coverage over the same period cost over 50%. They are not remotely the same problem, and only the second one is worth paying for.
  • So the refresh is triggered by coverage, not by calendar age. An age-based rule (“skip if newer than a week”) measures the wrong variable: a quiet week wastes a full run, and a week that lands a 500-test branch reports “fresh, skip” while the map is already 50% out.
  • Three new things: the incremental refresh (default), make store-test-durations-force (stdf) for a full re-measure, and a stabilisation pass that keeps any value which has not meaningfully moved — cutting the file’s diff by ~95%. Plus a fourth we needed anyway: the refresh now prunes dead entries, making the existing test_test_durations_paths gate self-healing.
  • Nothing about CI changed. Same map, same eight shards, same gha-tests. Only how the map gets maintained.

1. What the map actually does

.test_durations is a committed JSON map of pytest node id → seconds — currently 10,633 entries covering about 2,740 seconds of test time. Its only consumer is pytest-split, which uses it to divide the suite across eight free GitHub runners instead of one large paid machine.

Two workflows do this: tests-check.yml on PRs to dev (floor Python only) and tests-full-check.yml on PRs to main (four versions × eight shards = 32 jobs). Both call the same target with SPLITS=8 GROUP=<n>. Locally those variables are unset, the flags expand to nothing, and the map is ignored entirely.

The detail that makes the rest of this document make sense: pytest-split’s default algorithm is duration_based_chunks, and it is contiguous. It walks the tests in collection order and cuts whenever accumulated duration crosses one eighth of the total. Each shard is a consecutive slice of the collection — not a cherry-picked set. So a wrong duration does not just mis-size one test; it moves every cut after it.

Within a shard, -n auto --dist=worksteal rebalances across the runner’s own cores. So intra-shard distribution is self-correcting and the map only ever buys us inter-shard balance.

2. The measurement that changed the design

We simulated the real eight-way split over the actual collection order (10,568 node ids), using the freshest durations as ground truth, and compared what a 17-day-old map does against a current one.

That is the symptom. The interesting part is the cause, which we isolated by decomposing the stale map into its two independent failure modes:

ScenarioSlowest shardOvershoot
Fresh map, exact values342.6s0.9%
17-day-old map, as-is560.3s65.0%
17-day-old values, but coverage complete365.2s7.6%
Current values, but the same entries missing524.6s54.5%

Stale values are nearly free. Missing coverage is ruinous. Essentially all the damage from an old map comes from tests it has never heard of — not from the tests it has, whose timings drifted.

The staleness curve is also sharply non-linear, which is why “refresh every release” felt like it was working right up until it wasn’t:

1 release (1 day)362.7%
4 releases (17 days)1,20865.0%

3. Why the mean is the villain

When pytest-split meets a node id it has never seen, it imputes the mean of the durations it does know. Our suite’s distribution makes that a catastrophic default:

A block of newly added fast tests is therefore charged about a hundred times its real cost — and because the chunks are contiguous, that phantom weight shoves every boundary after it. Genuinely slow new tests break it from the other direction: they are billed at 0.248s while really costing seconds, and land somewhere the balancer thinks is cheap.

We tried to dodge the measurement entirely. It doesn’t work.

If the fallback value is the problem, the obvious fix is to top up unknown entries with something saner than the mean before pytest-split sees them — no test run required. We tried the median, the 25th percentile, and a value between. All three stayed above 56% overshoot on the 17-day map, against 65% for doing nothing.

The reason is that the missing tests carried about 401 seconds of real time — 15% of the whole suite — spread unevenly across the collection. No single fill value can put that time in the right places. Coverage genuinely has to be measured. That negative result is what forced the incremental design rather than a pure post-processing trick.

4. What we shipped

The default target now measures only what is missing. It collects the suite, diffs the collected node ids against the map, and runs pytest over the difference. When nothing is missing it measures nothing at all and exits after the collection.

This is legitimate rather than a partial overwrite because --store-durations merges into the existing file — only --clean-durations, which we do not use, replaces wholesale. That single fact in pytest-split’s plugin.py is what makes the whole approach possible.

Guard rail: if more than 40% of the suite is missing, it re-measures everything instead. At that point the incremental path buys little and the node-id argument vector gets unwieldy.

Every duration is rounded to 4 decimals, and a recorded value is kept whenever the new measurement is within max(30% × stored, 0.05s) of it.

Both terms earn their place. The relative term spares slow tests, where a fixed floor would be far too tight — a 1s swing on a 10s test is noise. The absolute floor spares the thousands of sub-millisecond tests, whose relative jitter between runs is enormous and meaningless.

Rounding happens on both sides of the comparison, and the rounded stored value is what gets kept. Keeping the raw spelling instead would be self-defeating: an in-tolerance entry would preserve its original long float forever and the file would never converge.

Entries whose test file no longer exists are dropped. We needed this because --store-durations only ever merges — before this change, nothing could clear a dead entry, so the existing test_test_durations_paths gate could fail with no command able to fix it. Its error message even said “regenerate”, which would not have worked.

The criterion is deliberately the filesystem and never the collected set. A marker-filtered collection legitimately hides a large slice of the suite (most of tests/e2e), so pruning against it would delete live entries. A vanished file, by contrast, cannot come back under any marker.

6. What you actually run

SituationCommandRoughly costs
Release time, nothing much addedmake std~8s, no diff
After a branch that added testsmake stdseconds
Recorded values no longer comparable
(machine changed, suite reshaped)		make stdffull suite

Run it more often than you used to. The incremental refresh is nearly free when nothing is missing, so there is no reason to save it for release day. Running it right after a branch that adds a lot of tests is now the cheap, correct move — and that is exactly the moment the map degrades.

Both targets regenerate the CI-profile test-model fixtures first, then hand off to pipelex-dev store-test-durations. While wiring that up we also hoisted the CI marker expression into a single GHA_PYTEST_MARKERS variable shared with gha-tests; it had been duplicated, which meant the map could in principle have been measured against a different selection than CI runs.

7. Stabilisation, and why the diff mattered

Re-measuring the suite rewrites essentially every line, because timings never repeat exactly. The old full refresh produced a diff of over 21,000 changed lines — and that is not merely noisy. On release PR #1117 it helped push the branch past the size limits of two automated reviewers: Greptile declined on file count, Cubic on reviewable changed lines, most of them this file. Neither posted a single comment. The near-silence on that PR was evidence of a diff too large to read, not of clean code.

Here is what the options cost, measured the same way as everything else:

PolicyLines changedOvershoot
Raw values (what we had)10,5320.9%
Round to 0.052,2041.0%
Round to 0.11,7110.9%
Round to 0.251,2184.3%
Keep unless moved >30% or >0.05s4701.7%

Plain rounding plateaus around 1,700 lines — the residue is genuinely noisy slow tests whose timing moves more than any sane grid. The stateful policy gets to 470 for eight tenths of a point of balance. And in practice it does better than that, because with complete coverage the incremental refresh re-measures nothing at all, so the steady-state diff is zero lines.

One-time cost, already paid in this branch. The first run normalised all 10,633 entries onto the rounded grid — a single large diff, visible in the staged changes, which also shrank the file from 1.87 MB to 1.73 MB. Every refresh after it is small. Don’t be alarmed by the diff size on this particular commit; that is the last one.

8. How we verified it

Every claim above is measured rather than reasoned about. The behavioural ones were checked end to end:

  • Steady state really is a zero-line diff. Two consecutive runs on a complete map: 0 added, 0 rewritten, 0 pruned, and git diff empty.
  • Incremental cost is real. The run that measured our own 21 new tests took 15 seconds end to end, against several minutes for the full suite.
  • Self-healing works. We injected a dead entry, watched test_test_durations_paths go red, ran the refresh, watched it prune the entry by name and the gate go green.
  • The force path was exercised on a narrow marker selection, confirming it runs the whole selection rather than a node-id list.
  • The new tests were mutation-tested. Five mutations of the implementation — dropping the relative term, dropping the absolute floor, removing rounding, a naive node-id split, disabling pruning — each reddened the intended test. One test turned out too weak to catch the missing-rounding mutation and was replaced with a grid invariant that does.

Gates: make agent-check fully green (pyright, mypy over 2,564 files, ledgers, keyword-only, hub-layering, drift), full make agent-test passed, make docs-check builds with only the pre-existing anchor INFO in orchestrator-plugins.md.

9. Things worth knowing

Incremental measurements are taken under different conditions

Tests measured incrementally run in a smaller batch, under less parallel contention, than they would in a full-suite run. So their recorded values are not measured under conditions identical to the rest of the map.

Given how little precision is worth — stale values across weeks cost about 7% — this is a good trade for turning a multi-minute step into a multi-second one. make stdf is the remedy if the accumulated inconsistency ever looks like it matters. This is written down in the docs page too, not just here.

Stabilisation introduces a small one-directional bias

Keeping a value that moved slightly means the stored number lags reality. Across the whole map that showed up as a total of 2,654s against a true 2,719s — about 2.4% low. It is bounded per test by the tolerance and self-corrects whenever a test crosses it, so it does not compound. Worth knowing it exists.

Dead node ids still accumulate; dead file paths do not

Pruning is on the file path. If a test is renamed but its file survives, the old node id stays in the map. That is deliberate and benign — pytest-split simply imputes any id it does not recognise, and pinning node ids would need a full unfiltered collection plus a tolerance policy for legitimate parametrization drift. The cost is a little file size, not balance.

How much is all of this actually worth in CI wall clock?

Less than you might think, and that is an argument for the design rather than against it. The gap between a perfectly fresh map and a one-release-stale one is about 6 seconds of shard time — and since each shard runs -n auto on a 4-vCPU runner, we estimate roughly 1.5s of actual wall clock.

At release cadence the old full-suite regeneration was buying almost nothing. It is the multi-week gaps that bite, hard and non-linearly. So the right move was never “refresh more thoroughly” — it was to make the refresh cheap enough and correctly-triggered enough that the gap never opens.
