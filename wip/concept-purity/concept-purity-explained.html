Getting the class registry out of Concept

A protocol-owned wire model was answering behavioural questions by reaching into a process global. Pulling that out split compatibility into two tiers and fixed three live bugs on the way.

TL;DR

  • Concept subclasses the MTHDS-protocol wire model ConceptAbstract — pure serialisable data — but four of its methods read the process-global class registry. It could not answer a question about itself without a Pipelex runtime booted around it, and every caller holding a Concept inherited that dependency invisibly.
  • Compatibility is now two tiers. A declaration tier on Concept, pure over the model's own fields. A class tier in tools/typing/, pure over two already-resolved classes. ConceptLibrary.is_compatible composes them — declaration first, classes only if that's inconclusive.
  • Class lookup moved to the provider. ConceptProviderAbstract.get_structure_class(concept) is now the single seam that turns a structure_class_name string into a type.
  • Three live bugs closed: cross-package refines aliases silently failed to resolve at five call sites; an unresolvable structure class answered False instead of failing; native.Anything was answered for the wrong reason.
  • What to watch out for when you touch this: a core data-model function that needs a concept — or its class — takes a concept_provider parameter. Don't import a hub, and don't reach for get_class_registry(). A golden-set test fails the build if a new module under core/concepts/ does.

01 The problem

Concept carries five fields and nothing else: code, domain_code, description, structure_class_name: str, refines. The MTHDS standard owns that shape. Yet four of its members answered questions that needed a type, not a name — so they called get_class_registry() and looked the name up in a process global.

Three consequences, in increasing order of how much they cost us:

Layer inversion

A standard-owned wire model depended on a Pipelex process global. core/ is supposed to state its dependencies as parameters — that's the doctrine the hub split established.

Untestable

Asking two concepts whether they were compatible required a booted runtime with the right classes registered. The compatibility matrix could not be tested with plain classes.

Wrong answers

The one that actually bit. Two verdict bugs and a silent resolver bypass, all invisible because False was a legal-looking answer. See §05.

02 The new shape

The insight is that "are these two concepts compatible?" was always two questions wearing one coat. One is about declarations — what the author wrote — and is pure string work over the model's own fields. The other is about classes and needs types. Only the second needs a registry, and resolving a name into a type is a library's job.

pure · no registry, no ambient state owns resolution the coupling we removed

The asymmetry is deliberate, and it matters

At the declaration tier, True means "established by the declarations". False means "not established at this tier" — it does not mean incompatible. Two concepts whose declarations say nothing about each other may still be compatible through their classes. Reading tier 1's False as a verdict is the mistake the old single-method design made structurally easy; the docstrings now say so explicitly.

pipelex/tools/typing/class_utils.py

The class tier lands next to the two helpers it already used. It takes types, never names — which is what makes it testable with two throwaway classes and no boot.

+def are_structure_classes_compatible(*, class_1: type[Any], class_2: type[Any], strict: bool) -> bool:
+    """Whether `class_1` can stand in for `class_2`, structurally.
+
+    Structural equivalence always suffices. Beyond that, `strict` decides how much slack:
+    strict accepts equivalence only, loose also accepts a subclass relationship (a refined
+    concept's generated class inherits from the refined one's) and a class that merely
+    *carries* a compatible value in a field — the "nested" case a template needs when it
+    pulls an image out of a document.
+
+    Pure over the two classes: it takes resolved types, never names, and reads no registry.
+    """
+    if are_classes_equivalent(class_1, class_2=class_2):
+        return True
+    if strict:
+        return False
+    try:
+        if issubclass(class_1, class_2):
+            return True
+    except TypeError:
+        pass   # not both classes; fall through to field checks
+    return has_compatible_field(class_1, target_type=class_2)

05 The three bugs this closed

1 · Cross-package refines aliases silently failed to resolve

Five operator call sites compared two Concept values directly instead of going through ConceptLibrary.is_compatible. That meant concept_resolver=None, and a refinement written across a package boundary — refines = "imgdep->native.Image" — never resolved at those sites. Every other compatibility check in the tree already went through the wrapper.

What it looked like: a concept that legitimately refines native.Image through a dependency alias was not recognised as an image by the template analyser, so @pic produced no image reference — at authoring time, with no error to read. Same class of failure on the PipeLLM text-vs-object run branch.

Pinned by test_template_image_analyzer_cross_package.py, which drives the public analyze_template_for_images rather than a private resolver. It failed red with 0 == 1 before the fix. The other four sites are the same one-line swap through the same wrapper.

2 · An unresolvable structure class answered False, not an error

The old class tier did if concept_1_class is None or concept_2_class is None: return False. "I could not resolve this name" and "these are incompatible" are different answers, and callers cannot tell them apart. Now it raises ConceptStructureClassNotFoundError.

This one was load-bearing for the whole refactor. It's the reason the tiers had to be composed by the library rather than merged: only the thing that owns resolution can tell "no class" from "not compatible", so only it can decide which to return.

3 · native.Anything was answered for the wrong reason

NativeConceptCode.ANYTHING.structure_class is None by design — it is the untyped vehicle — while structure_class_name still derives "AnythingContent" mechanically, a name no registry ever holds. So is_compatible(Anything, Text) returned False via the silent None branch: right answer, wrong reason. Making bug #2 raise would have turned that into a crash.

Fixed at the source rather than papered over: NativeConceptCode.is_structureless_concept + Concept.declares_a_structure_class make "this concept has no structure" a declared property, checked before the class tier. Verdicts are unchanged in both directions; the reasoning is now correct. Pinned by test_the_structureless_native_concept_is_answered_not_raised.

06 Judgement calls worth knowing about

Why pipe_abstract.py still reads the registry directly

It decorates graph-registry entries with a concept's JSON Schema, and it cannot import either hub. The constraint is a static-analysis cycle, not a runtime one — worth knowing before you "fix" it:

  • A clean-interpreter probe after import pipelex.runtime_hub shows pipe_machinery.pipe_abstract, pipe_run.pipe_job and plugins.orchestrator_registry all absent — those edges are TYPE_CHECKING-only.
  • But pyright's reportImportCycles counts them, so importing either hub there is a hard type-check failure via runtime_hub → plugins.orchestrator_registry → pipe_run.pipe_job → here.
  • A deferred import doesn't dodge it: pyright reports at interpreter_hub.py, where no line-level ignore can reach.

So it uses the below-both-hubs accessor, deliberately with the lenient get_class (no bound, None rather than a raise) because the schema is optional decoration. This is the one sanctioned read-side exception in the tree, and it's stated as such in class_registry_access.py.

Why --save-csv resolves through an empty library

Found by an e2e test, and it's the surprise of the branch. PipelexMTHDSProtocol.execute tears the run library down on its way out — so every post-run step in _execute_run (the CSV save, the pretty print, the working-memory dump) runs with no current library. Migrating the CSV row-model lookup to get_concept_library() produced RuntimeError: No current library set.

The old code never noticed because it read the process-global registry, which is never unregistered at teardown — the classes outlive the library that defined them. ConceptLibrary.make_empty() reads that same registry while keeping the single typed "name → class, or a typed error" implementation.

The lifecycle smell underneath is real and out of scope: a post-run step needing the method's declarations is running after the method is gone. The honest fix is a result object carrying what post-run steps need, or holding the library window open across them.

Four except arms: two removed, two deliberately not added

ConceptFactory refuses to build a concept whose declared structure class does not resolve — a bad structure = "…" raises ConceptFactoryError, and the basic-blueprint path generates the class. Every Concept(...) construction in pipelex/ source lives inside that factory. So a concept in a loaded library always has a resolvable structure class.

Consequently: resolve_input_kind's except ConceptValueError → InputKind.DYNAMIC fallback was unreachable and was removed (keeping it would restore exactly the silent degradation bug #2 removes), and the two run-path lookups the plan flagged as needing guards were left unguarded. Adding them would be guarding an impossible scenario, and bug #2's fix already made the error self-describing — it names the concept ref and the class.

The asymmetry with the guarded validation siblings in the same files is intentional: the /validate sweep needs per-pipe granularity or one bad pipe aborts the whole bundle. A run has no sweep.

The purity lock, and why it's a golden set rather than a rule

test_concept_registry_boundary.py asserts that exactly two modules under pipelex/core/concepts/ touch the class registry, and both are the materialisation write side — concept_factory registering generated classes, structure_generation/generator.py looking up base classes to generate against. That's genuinely the registry's business and stays.

A golden set, not a predicate, for the same reason the cogt boundary test gives: nothing separates a sanctioned write-side read from a new read-side one, so the value is turning a third module into a diff a reviewer sees. No other gate can see this edge — both the accessor and its users are runtime-layer, so the hub-layering guard is blind to it by construction.

It matches four spellings, because an import-name-only walk waved three of them through: the accessor by name, the module path, the attribute call (runtime_hub.get_class_registry()), and two indirect roots — KajsonManager.get_class_registry() (which skips library scoping entirely, and has a live precedent in runtime_bridge) and ClassRegistryUtils.

07 What this does not do

The scoping half is not done. ConceptLibrary.get_structure_class calls get_class_registry(), which selects a registry from the current async context — not one the provider carries. A ConceptLibrary holds no registry at all; the per-library ClassRegistry lives on Library. So passing a specific library as concept_provider does not scope class resolution to it.

Codex raised this as a P1 on the PR. The mechanism is real; the divergence it describes is not reachable:

  • Provider-library and registry-library are two reads of one variable. Every non-forwarding concept_provider= source is get_concept_library() → LibraryManager.get_current_library() → the _library_id ContextVar, which is the same one _resolve_scoped_class_registry reads. They cannot name different libraries.
  • The one place that installs a per-library registry pairs them. runtime_bridge/primitives/rehydration.py calls set_class_registry and set_current_library on the same library in adjacent statements.
  • Two sites deliberately depend on the ambient read — the post-teardown --save-csv lookup and every boot-free test using make_empty(). Carrying a registry on the provider would break both unless it re-derived the global fallback get_class_registry() already implements.

Not a regression either: on dev, the removed Concept.get_structure_class() read the same registry. This PR moved where the call lives, never which registry it reads. What it did buy is that scoping it later is now a one-place change.

Trip-wires that would make it real

  1. A caller passes library_manager.get_library(library_id=X).concept_library instead of get_concept_library().
  2. A dependency/child library's concept_library is used as a provider. Child Library objects live in Library.dependency_libraries and are not in LibraryManager._libraries, so get_library_class_registry structurally cannot see their registry. This is the sharpest of the four.
  3. InterpreterHub.set_concept_library gains a live writer — it currently has zero callers, so its standalone-library fallback branch is dead code.
  4. A set_class_registry call site appears that is not paired with set_current_library on the same library.

Also deliberately out of scope

  • The write side stays ambient. Making libraries own their class registry explicitly is a separate, larger track.
  • No StaticConceptProvider — build it when something needs it, not for symmetry.
  • No operator parameterisation. Interpreter-layer get_concept_library() calls are the sanctioned idiom for that layer today.
