# Engine intent hints — H2 design

Milestone H2 of the input-form program (workspace `wip/devx/input-form-roadmap.md`), on branch `feature/Engine-hints`, cut from `dev` after the `feature/Input-semantics` program branch merged (base includes `46a3f5df2`, which carries D2's deriver). Inputs: the accepted intent-hints standard (`mthds` PR #56 at `98883bb` — `docs/spec/intent-hints.md`, the expanded input-slot form in `mthds-format.md`, the effective-hints normalization in `library-crate.md`), the H1 design log (`mthds/wip/intent-hints-design.md`), the workspace descriptor spec's reserved-hint-slot section (`../docs/specs/mthds-input-form-descriptor.md`), and the request `../wip/inbox/2026-08-22-pipelex-h2-intent-hints-engine.md`.

**Scope:** the engine round trip — hints authored in a bundle reach the wire input-form descriptor. Parse at three sites, validate strict-shape/lenient-content, carry through the crate with effective-hints normalization and fingerprint neutrality for hint-free crates, warn on unknown content, populate the descriptor's reserved `hints` slot, promote the no-hint presentation defaults from heuristics to specified rules, regenerate `mthds_schema.json`, and grow spec/conformance.

**Gate (roadmap H2):** the hint round trip proven on one real method; spec and conformance updated. The engine-side provable half is authored-in-a-bundle → visible-on-the-wire-descriptor (integration test + the trace harness's hop-5 capture); the "visible in a rendered control" half needs a consumer that reads the wire descriptor, which arrives with M1/H3 — the checkpoint records this reading so the roadmap can reconcile it.

## The contract, in one paragraph

The normative rules live in the standard and are not restated here: `hints` is a flat string→string TOML table; shape violations are structural bundle errors; unknown keys and unknown `intent` words warn on the advisory channel and are preserved; three sites (concept, structure field, expanded input slot `name = { concept = "…", hints = { … } }`), unknown slot-table keys rejected; precedence is key-by-key, site over concept, nearer chain declaration wins; normalization materializes each concept's effective hints at refinement-flattening, removes empty tables, and keeps hint-free crates byte-identical (fingerprint-stable); hints ride the hashed members; the vocabulary this version defines is one key `intent` closed over `prose`, `label`, `rating`, `quantity`, with applicability defined over text-valued and number-valued sites and per-item judgment on plural sites. Hints are non-normative: no verdict, no execution behavior, no gating decision ever reads them.

## Dataflow overview

Authored bundle → blueprint models (parse + strict shape) → library crate (hints ride the blueprint objects) → qualification (pass-through) → normalization (effective hints on concepts; fingerprint) → advisory lint (content warnings on the validation report) → input-form deriver (site-over-concept merge, `hints` slot populated, intent feeds the kind defaults). Runtime execution models never carry hints — that is the structural enforcement of non-normativity.

## Part 1 — Parsing the three sites

**(a) Concept blueprint.** Add `hints: dict[str, str] | None = None` to `ConceptBlueprint` (`pipelex/core/concepts/concept_blueprint.py:12`). `extra="forbid"` is already in force there (line 13), so a misspelled member fails loudly today; the typed field gives strict shape for free — pydantic rejects a non-table `hints` and non-string values as structural validation errors, which is exactly the spec's shape rule.

**(b) Structure-field blueprint.** Add the same field to `ConceptStructureBlueprint` (`pipelex/core/concepts/concept_structure_blueprint.py:50`). That model has no `model_config`, so extras are silently ignored (finding E7, `wip/input-semantics/findings.md` §E7) — meaning a *misspelled* `hint = {…}` on a field still vanishes silently after H2. Per the H1 design log, the E7 `extra="forbid"` fix is deliberately separate work (it belongs to S2's strictness sweep, where the whole language ceiling becomes enforceable at once); H2 adds the field and does not change the extras policy. A *present, well-spelled* `hints` member is still strictly shape-checked by its type — the H2 guarantee holds where the spec states it.

**(c) The expanded input-slot form.** Today a slot value is a bare string: `PipeBlueprint.inputs: dict[str, str] | None` (`pipelex/pipe_machinery/pipe_blueprint.py:186`), validated by `generic_validate_inputs` (lines 281–323) against the ref+multiplicity+presence grammar. Add a slot table model beside it:

- `InputSlotBlueprint(BaseModel)` with `model_config = ConfigDict(extra="forbid")` and exactly two fields: `concept: str` (the full existing slot grammar — ref, optional `[]`/`[N]`, optional `?`/`!`) and `hints: dict[str, str] | None = None`. `extra="forbid"` implements the spec's "unknown slot-table keys MUST be rejected" — the form is deliberately closed so future per-slot semantic keys (`description`, defaults) land here without a second syntax.
- Widen `inputs` to `dict[str, str | InputSlotBlueprint] | None`. The union widens every `Pipe*Blueprint` subclass at once (the union is assembled at `pipelex/mthds_parsing/pipelex_bundle_blueprint.py:59-73`), and `generic_validate_inputs` validates the `concept` value of a table arm with the same grammar it applies to the string arm — one grammar, two spellings.
- **Parse-time collapse rule:** a slot table carrying no hints (absent or empty `hints`) collapses to its plain string at model validation — `x = { concept = "S" }` and `x = { concept = "S", hints = {} }` become the string `"S"` in the blueprint. The spec sanctions this ("`x = { concept = "S" }` and `x = "S"` are the same slot in the crate and hash identically"; an empty table is equivalent to no hints), and it buys a strong invariant downstream: *a slot value that is a table carries non-empty hints*, so hint-free bundles produce byte-identical blueprints to today by construction, and the string-assuming code paths stay dominant.

Two downstream sites iterate slot values as strings and need the table arm: `crate_qualification._qualify_io_ref` (`pipelex/libraries/crate_qualification.py:140-141`) must qualify the table's `concept` through the same marker-preserving rewrite (`_render_ref_with_markers`, lines 191–198) while passing `hints` through untouched (a hints table contains no refs — qualification never rewrites it), and `crate_normalization._collect_referenced_natives` (`pipelex/libraries/crate_normalization.py:235`) must read the table arm's `concept`. `InputStuffSpecsFactory.make_from_blueprint` (`pipelex/core/pipes/inputs/input_stuff_specs_factory.py:26`) accepts the union and extracts the `concept` string for the runtime spec — and nothing more: `StuffSpec` (`pipelex/core/pipes/stuff_spec/stuff_spec.py:11`) does **not** grow a hints field. The deriver reads slot hints from the qualified crate instead (Part 6). Keeping hints out of the runtime input models is the design's structural answer to "an implementation MUST NOT consult hints when executing a pipe": the execution path cannot read what it never receives.

**Fixture consequence:** the committed rejection fixture `tests/data/input_semantics/rejected/per_input_description.mthds_invalid` (`inputs = { doc = { concept = "Text", description = "…" } }`) **remains a valid rejection** — `description` is an unknown slot-table key and the expanded form rejects unknown keys. Its rationale shifts from "tables are not accepted" to "this key is not accepted"; update its commentary, verify the new failure surfaces as the slot-table extras error, and add accepted-fixture siblings for `{ concept = "…" }` (collapses to the string form) and `{ concept = "…", hints = { intent = "prose" } }`.

## Part 2 — Serialization and the fingerprint hazard

This is the highest-risk detail in the milestone. Both fingerprint functions (`pipelex/libraries/library_crate.py`: `compute_fingerprint_from_content` lines 51–68, `compute_normalized_fingerprint` lines 74–98) hash `model_dump(mode="json")` payloads **without** `exclude_none`. A naïvely added optional field therefore lands as `"hints": null` in every dumped concept and field, changing **every existing crate digest** — the exact opposite of the spec's "a library that authors no hints keeps its fingerprint".

The fix is the spec's own rule made local: "absent hints are an absent member — never `null`, never an empty table". Give `ConceptBlueprint`, `ConceptStructureBlueprint`, and `InputSlotBlueprint` a `@model_serializer(mode="wrap")` that drops only the `hints` key when it is `None` — the exact pattern `InputFormField.serialize_without_inapplicable_slots` already uses (`pipelex/pipeline/input_form.py:183-189`). Deliberately *not* a blanket `exclude_none`: the crate spec's general absent-members-not-null canonicalization is a separate forward contract whose adoption would migrate every existing fingerprint, and H2 must not smuggle that in. The targeted serializer keeps every current digest stable, makes hinted crates hash differently (correct — a hint edit is a semantic change to authored presentation, the domain-`description` precedent), and satisfies the crate encoding rule everywhere blueprints are dumped, including codegen's crate encoding. JSON canonical ordering is free (`sort_keys=True` in both fingerprint functions covers the "hints entries emitted sorted by key" rule); if `pipelex/codegen/crate_encoding.py`'s TOML encoding orders keys differently, it needs the same sorted-emission check.

**Byte-identity guards:** a unit test asserting the serialized JSON of a hint-free concept/field/pipe contains no `hints` key at any depth; the existing determinism and idempotency tests (`tests/unit/pipelex/libraries/test_library_crate.py::test_fingerprint_determinism`, `test_crate_normalization.py::test_normalization_is_idempotent`, `tests/integration/pipelex/libraries/test_crate_normalization_round_trip.py`) re-run unchanged; and one pinned-fingerprint regression test — compute the normalized fingerprint of a committed hint-free fixture bundle on current `dev`, hardcode the hex in the test, and land the pin *before* the hints fields so the suite proves the digests did not move.

## Part 3 — Crate travel and effective hints

Hints need no new crate machinery to *travel* — they are blueprint content and ride `LibraryCrate.concepts`/`pipes` like every other member. The work is in normalization (`pipelex/libraries/crate_normalization.py`):

- **Effective hints are assembled where the refinement chain is already walked**: `_flatten_refinement` (lines 117–137) via `_resolve_refinement` (lines 139–189). The chain structure makes this cheap: `refines` XOR `structure` means at most the chain's *end* carries structure, so the existing walk already visits every intermediate link — it only needs to accumulate hints as it goes. Extend `_RefinementResolution` (line 53) with `effective_hints: dict[str, str] | None`; while walking child→base, merge with first-seen-wins (nearer declaration wins, key by key — the shared merge helper of Part 4). Per the crate spec, this applies to every refining concept whose bases resolve in-crate — the one flattened to a bare structure *and* the one that keeps its `refines` link (native-backed chains; the pinned natives carry no hints this version, so they contribute nothing to the merge). A merge that yields nothing leaves the concept without a `hints` member. Mind the memoization at lines 187–188: a cached resolution must carry the hints of *its* position in the chain, not the querying concept's.
- **Empty-table removal** is already done at parse time (the Part 1 collapse rule normalizes `hints = {}` to absence on slots, and the concept/field models can do the same in a validator), so the crate never holds an empty `hints` table and step-5 materialization owes nothing.
- **Structure-field and slot hints are carried as authored** — the site-over-concept merge is the consumer's (here: the deriver's), both layers being present in the crate. Qualification passes them through untouched.
- Idempotency: re-normalizing a normalized crate must be a no-op — a concept whose hints are already its effective hints re-merges to the same table (`test_normalization_is_idempotent` extends to a hinted fixture).

## Part 4 — One shared hints module

New module `pipelex/language/intent_hints.py` (beside `mthds_schema_generator.py` — this is language-standard knowledge, not runtime config), the single owner of:

- The constants: `INTENT_HINT_KEY = "intent"` and the closed vocabulary `prose`, `label`, `rating`, `quantity`, pinned per standard version like the native concept definitions.
- `merge_hints(layers)` — the one precedence implementation: key-by-key, later (nearer) layer wins, empty result is `None`. Called from the normalizer's chain walk, from the deriver's site merge, everywhere. The codebase already has three refinement-chain walks (`crate_normalization._resolve_refinement`, `InputFormDeriver._refines_chain`/`_merged_structure`, codegen's native expansion); hints must not add a fourth *merge semantics* — the walks stay where they are, but they all call this one merge.
- The applicability predicates: text-valued and number-valued site judgment per the spec's Applicability section (structure-field types; refinement chains reaching `native.Text`/`native.Number`; description-only concepts are text-valued; plural sites judged per item), plus `applicable_intent(hints, *, site) -> str | None` returning the effective `intent` word only when it is known *and* applicable — the deriver's and the lint's shared question.

## Part 5 — The advisory lint

The spec's SHOULD-warn rules (unknown key, unknown `intent` word, applicable-word-on-inapplicable-site) cannot live in pydantic validators — a validator can only raise, and these must never reject. The engine already has the right pattern: a post-parse lint pass producing `ValidationErrorItem`s onto the report's `warnings` list (`pipelex/pipeline/validation_report.py:70`), exactly as `build_optionality_warnings` does (`pipelex/pipeline/optionality_warnings.py:33`, wired at `pipelex/pipeline/validate_in_process.py:114`).

New module `pipelex/pipeline/hint_warnings.py` with `build_hint_warnings(...)` sweeping the qualified crate's three sites and emitting one advisory item per finding: an unknown hint key, an unknown `intent` word, an `intent` word on a site it does not apply to. Each warning names its site (concept code / field name / pipe code + slot name) so the author can find it. Well-formed unknown content is *only* warned about — it is preserved into the crate and the descriptor untouched.

Error-type registry: add a dedicated advisory enum (working name `HintLintErrorType`: `hint_unknown_key`, `hint_unknown_intent`, `hint_inapplicable_intent`) joined into the `ValidationErrorType` alias (`pipelex/validation_error_types.py:285`), rather than growing `PipeValidationErrorType` — hints attach to concepts and fields too, so the pipe enum is the wrong home, and a new enum sidesteps rippling through the pipe enum's exhaustive `match` property blocks while still implementing whatever properties the render layer requires. Two gates will trip and must be updated deliberately: the error-identity snapshot (`tests/unit/pipelex/errors/test_error_identity_snapshot.py`, `make gei`) and the error-reference docs pages (`make gep`).

## Part 6 — Populating the descriptor

The reserved slot already exists and is never written: `InputFormField.hints` (`pipelex/pipeline/input_form.py:131`). Its `None`-dropping serializer means population is wire-additive and absent-when-unset for free. Narrow its annotation from `dict[str, Any]` to `dict[str, str]` — the flatness invariant is contract.

**Getting slot hints to the deriver without touching runtime models:** `build_input_form` (line 199) already computes `qualify_crate(crate)`; keep its `concepts` and also keep `pipes`. For each pipe, the qualified blueprint's `inputs` map yields, per slot name, either a string (no hints) or a slot table (hints). `InputFormDeriver` grows a per-derivation lookup (pipe ref → slot name → hints) or simply receives the slot's hints as an argument to `derive_slot` from the `build_input_form` loop — the loop is where both the runtime `StuffSpec` and the crate blueprint are in hand. The fallback path (no crate loaded) derives with no hints, as today.

**Where each site's hints are stamped:**

- Concept nodes (`_blueprint_node`, lines 274–303, and `derive_concept`): the concept's *effective* hints — the deriver works over the qualified (unflattened) crate, so it computes the chain merge itself via its existing `_refines_chain` walk calling the shared `merge_hints`. String-shorthand concepts, natives, and class-backed concepts author no hints this version and stamp nothing.
- Structure fields (`_structure_field`, lines 425–470): `merge_hints([referenced concept's effective hints (concept-typed and concept-item fields only), field.hints])` — the site layer winning key by key, stamped via the `model_copy(update=…)` pattern already used at the `concept` arm (line 444).
- Input slots (`derive_slot`, lines 231–250): `merge_hints([slot concept's effective hints, slot hints])`, stamped in the final `model_copy(update=…)` at line 250 beside `presence`/`required`/`gating`.
- Plural slots and list fields: the merged hints are stamped on the `list` node **and** on its `item` descriptor, mirroring the `concept_ref` duplication precedent ("the list node is where a renderer reads the slot's identity; the item is what it renders once per entry") — the spec judges applicability per item, and a renderer reading either node finds the same answer. Conformance pins this duplication.

Everything well-formed rides the slot — including unknown keys and unknown words (preserved content per spec); a consumer ignores what it does not know.

**Intent feeds the kind defaults — never competes with them.** The descriptor spec's ruling: an applicable `intent` word is an *input* to the deriver's kind-and-presentation defaults, never a second answer beside a derived `kind`. Concretely, via `applicable_intent(...)` from the shared module:

- On a **text-valued node**, effective `intent = "prose"` yields `kind: "prose"` and `intent = "label"` yields `kind: "text"`; absent (or inapplicable, or unknown) intent leaves the node on the no-hint default.
- On a **number-valued node**, `rating` and `quantity` do not change `kind` (both are `number` — the union has no finer kind); they ride the `hints` slot and the renderer decides what a judgment-versus-amount presentation means. The semantic bounds a rating presents against are already the constraint slots.
- An intent word on an inapplicable site changes nothing in `kind` (the lint already warned); it still rides the `hints` slot as preserved content.

**Promoting the no-hint defaults from heuristics to specified rules** is the other half of H2's mandate: the deriver's existing text-versus-prose and per-node kind assignments do not change behavior, but they get written down — as a stated rule table in `docs/under-the-hood/input-form-descriptor.md` and reflected into the workspace descriptor spec's kind-assignment section — so the no-hint case is specified, not folklore. H2 changes a node's kind only where an applicable authored intent says so.

## Part 7 — Schema regeneration and propagation

`mthds_schema.json` regenerates from the blueprint models (`pipelex/language/mthds_schema_generator.py:39`), so the two new `hints` fields and the slot-form union propagate automatically via `make gms` / checked by `make cms`. The slot union renders as an `anyOf` in Draft-4; if Taplo's disambiguation misbehaves on it, `_patch_construct_schema` (lines 218–304) is the precedent for a hand-patch. The generated file is gitignored (`derived/`), so drift is invisible in PRs — run `make cms` in the milestone's check loop. Propagation to the served schema and the vendored copies is the `/mthds-schema-sync` workspace plugin (`internal-tools/plugins/mthds-schema-sync/`), release-gated with a manual S3 step — it runs at the release that ships H2, not in this branch. The mthds site's intent-hints "Specification Status" section (which currently records that the served schema predates hints) gets its conformance assertion updated at the same release — an `mthds`-repo follow-up, filed at milestone close.

## Part 8 — Tests

- **Parsing (unit):** each site accepts a valid flat table; non-table `hints`, non-string values, and nested tables fail as structural errors at all three sites; unknown slot-table keys still fail; the collapse rule (`{ concept = "S" }` ≡ `"S"`, empty hints ≡ none); grammar preserved through the table arm (multiplicity + markers on `concept`). Homes: `tests/unit/pipelex/core/concepts/concept_blueprint/`, `tests/unit/pipelex/mthds_parsing/`.
- **Fingerprint neutrality (unit + integration):** the pinned-fingerprint regression (landed before the fields), the no-`hints`-key serialization assertion, determinism/idempotency/round-trip suites extended with a hinted fixture; a hinted crate's fingerprint differs from its hint-free twin.
- **Normalization (unit):** effective-hints merge along a chain (nearer wins, key by key), on both the flattened and the `refines`-keeping arms; memoized mid-chain resolution carries its own position's hints; empty merge leaves no member. Home: `tests/unit/pipelex/libraries/test_crate_normalization.py`.
- **Lint (unit):** unknown key warns, unknown word warns, inapplicable word warns, all with site attribution; a warned bundle is still valid; warned content survives into crate and descriptor. Home: beside `test_validation_errors.py`; snapshot and docs gates re-generated.
- **Deriver (unit + integration):** site-over-concept and chain precedence visible on the wire; `prose`/`label` flip `kind` on text-valued nodes only; `rating`/`quantity` leave `kind` untouched and ride the slot; list/item duplication; hint-free descriptor output byte-identical to today. Extend the probe bundle under `tests/data/input_semantics/` with hinted fixtures, and `tests/integration/pipelex/pipeline/test_input_form.py`'s kind table.
- **Corpus:** one MTHDS Test Corpus entry authoring hints at all three sites (`pipelex/test_extras/mthds_corpus/`), `make generate-corpus-vocabulary` re-run; the entry is the "one real method" the gate's round-trip proof runs on, and `mthds-corpus-sync` propagates it at close.

## Phased plan

**Phase 1 — Language surface.** The shared `intent_hints` module (constants, `merge_hints`, applicability). The pinned-fingerprint regression test, landed first against unchanged models. Then the three site additions: `ConceptBlueprint.hints`, `ConceptStructureBlueprint.hints`, `InputSlotBlueprint` + the `inputs` union + `generic_validate_inputs` table arm + the parse-time collapse rule. The targeted `None`-dropping serializers. Fixtures: accepted siblings, the reinterpreted rejection fixture, parse unit tests, fingerprint-neutrality assertions green.

**Phase 2 — Crate travel.** Widen `_qualify_io_ref` and `_collect_referenced_natives` for the table arm; `InputStuffSpecsFactory` accepts the union and extracts the concept string only. Effective hints in `_resolve_refinement`/`_flatten_refinement` via the shared merge; normalization unit tests incl. idempotency on hinted fixtures; round-trip integration green.

**Checkpoint A** — the crate layer is done: hints parse at three sites, travel qualified and normalized, hint-free crates provably keep their digests. Update this doc with decisions taken and any deviation folded into the later phases; verify cold-start readiness.

**Phase 3 — Advisory lint.** `hint_warnings.py`, the advisory error-type enum joined into `ValidationErrorType`, wiring in `validate_in_process` beside the optionality warnings, error-identity snapshot and error-docs regenerated, lint unit tests.

**Phase 4 — Descriptor population.** Slot-hints plumbing from the qualified crate through `build_input_form` into `derive_slot`; concept/field/slot stamping via the shared merge; the intent→kind rule on text-valued nodes; `InputFormField.hints` narrowed; list/item duplication; deriver unit + integration tests over the hinted probe bundle; hint-free descriptor byte-identity.

**Checkpoint B** — the round trip exists end to end in-engine: authored hints visible in `hop5_input_form.json` via the trace harness on the hinted corpus method. Same checkpoint protocol as A.

**Phase 5 — Schema, corpus, docs, close.** `make gms`/`cms` (Taplo patch if the slot union needs it); the corpus entry + vocabulary regen; Part 9's docs and changelog; `make agent-check` + `make agent-test`. Milestone close per the workspace protocol: roadmap checkpoint with SHAs, the workspace-side spec/conformance edits, inbox items for the `mthds`-site status assertion and the `mthds-corpus-sync`/`mthds-schema-sync` runs that ride the next release, and the H3 handoff note.

## Out of scope, stated

- The E7 `extra="forbid"` fix on `ConceptStructureBlueprint` (S2's strictness sweep) — H2 notes the boundary in Part 1(b).
- Per-slot *semantic* keys (`description`, defaults, examples) on the expanded form — the form is their future home, the language does not define them yet.
- Hints on class-backed (Python-defined) structures and on native definitions — no authoring surface this version.
- The crate spec's general absent-members-not-null canonicalization and step-5 materialization — forward contracts; H2 implements only the hints-specific absence rule.
- Builder/authoring-CLI emission of hints (`pipelex/builder/operations/concept_ops.py` writes concepts today and would drop authored hints on a rewrite) — flag as its own small follow-up unless it turns out to be a one-liner in Phase 5; it sits beside the known E8 spelling bug in the same writer.
- The kernel rendering hints (H3) and the wire-descriptor swap in consumers (M1).

## Open questions

1. **Advisory enum home:** the design proposes a new `HintLintErrorType` joined into the `ValidationErrorType` alias; if the render layer's required properties make a shared enum cheaper, deciding at Phase 3 with the code in view is fine — the wire strings (`hint_unknown_key`, …) are the contract, the enum layout is not.
2. **Gate wording:** "visible in a rendered control" — this design reads the engine-provable gate as wire-descriptor visibility (Checkpoint B), with the rendered-control demonstration completing when a descriptor-reading consumer exists (M1/H3). To reconcile in the roadmap at close.
3. **`derive_slot` signature vs lookup:** whether slot hints reach the deriver as a per-call argument or a pipe-ref-keyed map is an implementation-taste call made in Phase 4; the invariant that matters is that runtime `StuffSpec` stays hint-free.
