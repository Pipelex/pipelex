Framework-agnostic Pipelex runtime bridge

Mistral Workflows and Temporal are both execution frameworks that embed Pipelex — and they need the same things from it. The runtime bridge is the single surface that gives them those things, so each one stops re-implementing the handshake.

PR #959 + #966 branch feature/Runtime-bridge-extraction base dev new package pipelex/runtime_bridge/ ~795 lines of core code

The problem. Pipelex never runs in a vacuum — it runs inside an execution framework. Two of them matter to us today: Mistral Workflows and Temporal. They look nothing alike, but the moment either one wants to run a Pipelex pipe from inside one of its own activities, it asks Pipelex for the exact same things, in the same order:

  • boot the Pipelex runtime (once, safely, even under concurrency);
  • validate the incoming request;
  • load the pipe's definition (which may travel inside the request itself);
  • hydrate a job from plain JSON inputs;
  • dispatch the pipe;
  • serialize the result back into something that survives the wire.

That handshake was being copy-pasted into every framework — and quietly drifting apart, so a fix or a hardening landing in one copy rotted in the others.

What we did. We named that shared handshake and gave it one home — the runtime bridge. Now Mistral Workflows, Temporal, a future plugin, or plain Python all ask for what they need through one function and one JSON-safe input type:

from pipelex.runtime_bridge.bridge import run_pipe_via_bridge, PipelexPipeRunInput

output = await run_pipe_via_bridge(
    PipelexPipeRunInput(pipe_code=..., inputs={...}, execution_mode=...)
)

Input and output are extra="forbid" pydantic models, so the boundary survives a serialization hop across a worker/activity without leaking Pipelex internals. The diff touches ~140 files, but the code core is small and concentrated — most of the line count is a vendored skill and triage notes that are explicitly out of scope.

Why we built it

Pipelex is increasingly embedded inside other people's execution engines. Three live consumers already exist: our own raw-Temporal worker path, the new Mistral Workflows plugin, and plain in-process Python. Each one needs to take a serialized request from somewhere (an activity argument, an HTTP body) and turn it into a running pipe. That request-to-pipe path is identical every time — and was being copied every time.

Before — N hosts, N copies

Each host re-implements boot, validation, working-memory hydration, dispatch, and result serialization. Bug fixes and hardening land in one copy and rot in the others. The optional Temporal SDK leaks into import paths that don't need it.

After — one boundary

Every host goes through run_pipe_via_bridge and the same JSON-safe types. Boot/validate/hydrate/dispatch live once. Host SDKs (temporalio, mistralai) are lazy-imported only inside the matching mode branch.

The entry point & boundary types

The whole public surface is two pydantic models and one async function in pipelex/runtime_bridge/bridge.py. Both models forbid extra fields so a malformed or version-skewed payload fails loud at the boundary instead of silently dropping data.

+ pipelex/runtime_bridge/bridge.py  (new)
class PipelexPipeRunInput(BaseModel):
    """JSON-safe input crossing the host-runtime / Temporal boundary."""
    model_config = ConfigDict(extra="forbid")

    pipe_code: str
    inputs: dict[str, Any] = Field(default_factory=dict)
    output_name: str | None = None
    pipeline_run_id: str | None = None
    user_id: str | None = None
    library_crate_dump: dict[str, Any] | None = None        # pipe definition travels in the request
    execution_mode: PipelexExecutionMode = PipelexExecutionMode.DIRECT
    delivery_assignment_dump: dict[str, Any] | None = None  # webhook / storage target

class PipelexPipeRunOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")

    output_dict: dict[str, Any]        # WorkingMemory.dump_for_temporal()
    main_stuff_name: str | None = None
    pipeline_run_id: str
    workflow_id: str | None = None     # set for the Temporal / Mistral modes
    is_completed: bool                 # False for fire-and-forget
    graph_spec_dump: dict[str, Any] | None = None

The output always uses WorkingMemory.dump_for_temporal() — the same format Pipelex uses internally for Temporal transit — so the shape is stable whether or not a library_crate was attached, and a caller with the matching class registry in scope can reconstruct a typed WorkingMemory.

Execution modes

The caller chooses the runtime via PipelexExecutionMode (a flat StrEnum — not a plugin registry; there is no speculative extensibility here).

ModeWhat it doesNeedsBlocks?
DIRECT In-process, no Temporal. The activity blocks until the pipe completes. Works even inside a Temporal-enabled worker — it forces local execution. nothing yes
TEMPORAL_BLOCKING Dispatch the pipe as a Pipelex Temporal workflow and await it. Runs durably on Pipelex's worker fleet. pipelex[temporal] yes
TEMPORAL_FIRE_AND_FORGET Dispatch and return the workflow_id immediately. Completion arrives out-of-band via the DeliveryAssignment (webhook / storage). pipelex[temporal] + delivery target no
MISTRAL_NATIVE Decompose the pipe into native Mistral Workflows primitives — controllers become child workflows, leaves become activities — surfacing per-step retry / signals / cancellation through the host APIs. pipelex-mistralai-workflows yes

Optional deps stay optional

The bridge module imports nothing host-specific at top level. Mode-specific dependencies are pulled in by a lazy import inside the matching branch only. So DIRECT runs with neither extra installed, and a missing extra raises a precise, install-hint error rather than an ImportError at module load.

How a call flows

run_pipe_via_bridge is a short, linear pipeline. Every step is a guard or a hydration; the only branch is the final mode dispatch.

Step 4 is what lets a stateless / multi-tenant worker run a pipe whose definition travels in the request — without leaking dynamic concept classes into the global registry.

The scoped library (step 4)

When the caller passes a library_crate_dump, the bridge opens a per-call scoped library with its own ClassRegistry pre-seeded from the global one, loads the crate into it, and tears it down on exit. Classes generated from the crate's inline structured concepts register into the scoped registry — discarded on teardown — rather than colliding in the global Kajson registry. This mirrors the Temporal worker hydration path.

The primitives lift

The framework-agnostic bodies behind the Temporal activities — graph assembly, delivery, trace flush, hydration, pipe classification, submitter hydration — were moved out of pipelex.temporal into runtime_bridge.primitives. The pipelex/temporal/tprl_pipe/act_*.py files are now thin @activity.defn wrappers that decode their arg and delegate to the shared primitive. The Mistral-native path calls the same primitives. Behaviour-neutral: only the home of the logic changed.

# Thin @activity.defn wrapper — decodes the arg, delegates to the shared primitive.
from pipelex.runtime_bridge.primitives.graph_assembly import assemble_graph_for_pipeline_run

class AssembleGraphArg(BaseModel):
    pipeline_run_id: str
    domain_code: str | None = None
    main_pipe_code: str | None = None

# Deliberately NOT decorated with @convert_pipelex_errors: the shared primitive degrades
# EXPECTED failures to None for best-effort observability; programming bugs propagate.
@activity.defn(name="act_assemble_graph")
async def act_assemble_graph(arg: AssembleGraphArg) -> GraphSpec | None:
    return await assemble_graph_for_pipeline_run(
        pipeline_run_id=arg.pipeline_run_id,
        domain_code=arg.domain_code,
        main_pipe_code=arg.main_pipe_code,
    )
# No host-runtime import. Both Temporal and Mistral wrap this.
async def assemble_graph_for_pipeline_run(pipeline_run_id, domain_code=None, main_pipe_code=None) -> GraphSpec | None:
    tracing_config = get_config().pipelex.tracing_config
    if not tracing_config.is_enabled:
        return None
    try:
        event_log = make_event_log(tracing_config)
        try:
            events = event_log.read_events(pipeline_run_id)
            if not events:
                return None
            return GraphSpecAssembler.assemble(events=events, graph_id=pipeline_run_id, ...)
        finally:
            event_log.close()
    except (OSError, json.JSONDecodeError, ValidationError, PipelexConfigError,
            MissingDependencyError, EventLogReadError) as exc:
        # Best-effort observability: graph assembly must never fail the pipeline run.
        # Programming bugs (KeyError, ...) are NOT caught here — they surface in dev.
        log.warning(f"Graph assembly failed: {exc}")
        return None

The two subtle hardening fixes worth your attention

Most of the bridge is mechanical. Two correctness fixes are not, and they came out of the PR review threads. Both are about context not leaking across a boundary.

1 · DIRECT mode must scope its own router fixed

Inside a Temporal-enabled worker, the hub's default pipe router is the Temporal router. DIRECT mode runs the root pipe in-process — but nested controller sub-pipes (a sequence, a batch) dispatch through get_pipe_router(), which would resolve the hub default and leak the nested pipes back to Temporal — defeating the entire point of DIRECT.

The fix adds a contextvar-scoped router override in hub.py and wraps the whole _run_direct body in it, so the root pipe and every nested sub-pipe resolve the in-process router.

  pipelex/hub.py
+_current_pipe_router: ContextVar["PipeRouterProtocol | None"] = ContextVar("current_pipe_router", default=None)
+
+@contextmanager
+def scoped_pipe_router(pipe_router):
+    """Set as active router for the scope; restore prior value on exit (success or error)."""
+    prev = _current_pipe_router.get()
+    _current_pipe_router.set(pipe_router)
+    try:
+        yield
+    finally:
+        _current_pipe_router.set(prev)   # restores OUTER override, not just None
+
 def get_pipe_router() -> "PipeRouterProtocol":
+    override = _current_pipe_router.get()
+    if override is not None:
+        return override
     return get_pipelex_hub().get_required_pipe_router()

The scoped form is preferred internally over the raw set_pipe_router / teardown_current_pipe_router pair: the raw teardown unconditionally resets to None, clobbering an outer caller's override. The raw pair is kept only because the external Mistral plugin still depends on it.

  pipelex/runtime_bridge/bridge.py :: _run_direct
 async def _run_direct(pipe_job, delivery_assignment) -> PipelexPipeRunOutput:
+    # Scope the in-process router for the WHOLE run so nested controller sub-pipes
+    # — which dispatch through get_pipe_router() — resolve THIS router rather than
+    # falling back to the hub default (the Temporal router in a temporal worker).
     direct_router = PipeRouter()
+    with scoped_pipe_router(direct_router):
+        pipe_run = PipeRun(pipe_router=direct_router)
+        pipe_output = await pipe_run.run(pipe_job=pipe_job, delivery_assignment=delivery_assignment)
     return _serialize_completed_output(pipe_output=pipe_output, pipe_job=pipe_job, workflow_id=None)

2 · graph_context is honored for DIRECT only fixed

A host (e.g. a streaming activity) can pass a graph_context so per-step trace events flow through its tracer. But threading it into the Temporal modes would make Pipelex's Temporal workflow open its tracer under the host's graph id and merge its trace events into the host's graph — exactly the cross-contamination the contract forbids. The Temporal modes already have their own event-log infrastructure via pipeline_run_setup.

Why this is the right shape

Each of these is a claim a reviewer can check against the diff.

Separation of concerns

"How a host invokes a pipe" (bridge) is now distinct from "how Pipelex executes a pipe" (pipe_run) and from "Temporal SDK glue" (pipelex.temporal).

Verify: grep -rn "import temporalio\|import mistralai" pipelex/runtime_bridge/ returns only docstring prose.

One boundary, not N

Every host goes through the same entry point and the same JSON-safe types.

Verify: the Mistral plugin and the Temporal activities both consume runtime_bridge rather than duplicating it.

No duplication across runtimes

The lift means Temporal and Mistral share one copy of graph-assembly / delivery / etc.

Verify: act_*.py are wrappers; the logic lives once under primitives/.

Not overengineered

No abstraction without a real second consumer. The mode set is a flat enum, not a plugin registry; __init__.py is empty (no re-export indirection, per project convention); no speculative interfaces or config.
