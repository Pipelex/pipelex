Pipelex · refactor/Hub · architecture note

Splitting pipelex.hub

One god-object became two hubs with a single enforced arrow between them — and importing the Pipelex runtime now loads zero interpreter modules.

TL;DR

  • What was wrong. pipelex/hub.py brokered every cross-cutting dependency — config, console, secrets, storage, the model deck, the inference workers — and the concept/pipe libraries, the router, the pipeline manager. Four module-level imports meant that asking it for get_console() loaded the entire MTHDS interpreter. It also formed a real import cycle, papered over by three importlib.import_module("pipelex.hub") hacks that no lint and no type checker can see.
  • What we did. Deleted pipelex/hub.py outright — no alias — and replaced it with pipelex/runtime_hub.py (RuntimeHub) and pipelex/interpreter_hub.py (InterpreterHub). One rule: the interpreter hub may import the runtime hub; the runtime hub must never import the interpreter hub. Then the misplaced types moved down, and core's data model got injected providers so it could join the runtime layer.
  • What it bought. The inference layer went from 50 interpreter modules to 0; the runtime closure from 357 modules / 29,193 SLOC to 269 / 20,299. Six core.* entry points went 50 → 0 each. The cycle and its three hacks are gone.
  • It is mechanically enforced, not review-enforced. An AST guard (make check-hub-layering, in make agent-check and CI) checks the rule on imports and on string literals; a subprocess closure test pins the property across eight runtime entry points, with a negative control so it can never pass vacuously.
  • What changes for you. Pick your hub by what you need: infrastructure → pipelex.runtime_hub; anything about the loaded method → pipelex.interpreter_hub. A stale from pipelex.hub import … fails loudly at import time, by design.
  • Not done yet. The layer rule is enforced only one hop deep — 4 of 476 declared runtime-layer modules breach it transitively, all in pipelex.plugins, and the headline property is unaffected. Remedy decided, its own PR after #1062. The cross-repo sweep is release-gated: external repos still import pipelex.hub and break the moment this ships.

01 The problem

One module brokered everything, so everything imported it: 309 files. Because the hub annotated its own getters with Library, LibraryManagerAbstract, PipeAbstract and Concept, those annotations dragged the whole interpretation layer into the import graph of every consumer — including consumers that only ever wanted a console handle.

Three consequences, all of them daily costs:

  • An unanalyzable cycle. core/concepts/concept.py, concept_factory.py and structure_generation/generator.py each carried an identical lazy-import shim to break a circular dependency with the hub. All three wanted exactly one symbol — get_class_registry, an infrastructure-level one. Those shims are invisible to every import lint and to pyright's module graph: real coupling, load-bearing, unanalyzable.
  • A layer boundary that existed but could not be expressed. Of the 309 importers, 134 used only infrastructure symbols, 139 only method-machinery ones, and just 36 straddled. Every package below core used infrastructure symbols exclusively, with zero exceptions. The architecture was already layered — the hub was the one place the layering was unstateable, and therefore the one place it silently rotted.
  • Import cost paid by everyone. pipelex-api's health check, the CLI's --version, every plugin registration module and every test touching get_console paid for the full interpreter.

02 What we built

pipelex/hub.py is deleted, not aliased. That is deliberate: a stale import must fail loudly at import time rather than silently resolve to the wrong layer, and it matches the repo's no-backward-compatibility principle. In its place, two containers with genuinely different lifecycles.

Why these names

It is the textbook language-implementation split, so it explains itself to anyone who has implemented a language: the runtime is the machinery present at execution time (allocator, stdlib, FFI — here: models, workers, config, values); the interpreter reads the program and executes it (here: reads .mthds, builds pipes, routes them). It also gives one word across both layer and hub. The earlier working names service_hub / method_hub never shipped — service collides with the hosted product (from pipelex.service_hub import get_secret inside pipelex-platform reads two ways one line apart), and method borrows an MTHDS language noun for a Pipelex runtime container, against the brand-boundary rule.

03 The critical code

Six changes carry the design; everything else in the 535-file diff is import churn.

Four imports, serving nothing but type annotations

This is the entire cause. Each annotated a getter's return type, and each dragged a subtree behind it.

--- a/pipelex/hub.py   (deleted)
-from pipelex.libraries.library import Library                    # concrete → concept_library, pipe_controllers, codegen
-from pipelex.libraries.library_manager_abstract import LibraryManagerAbstract   # → core.bundles → all twelve pipe blueprints
-from pipelex.core.pipes.pipe_abstract import PipeAbstract        # → graph.graph_tracer_manager
-from pipelex.core.concepts.concept import Concept                # ← the cycle behind the three importlib hacks

Deferring them under TYPE_CHECKING would not have been the fix — that keeps the god object and adds a fig leaf. The four annotations belong to getters that are interpreter concerns, so they moved to the module where naming them is free.

Three identical lazy-import shims become one plain import

--- a/pipelex/core/concepts/concept.py   (also concept_factory.py, structure_generation/generator.py)
-def _get_class_registry() -> ClassRegistryAbstract:
-    """Lazy import to break circular dependency between concept.py and hub.py."""
-    import importlib  # noqa: PLC0415
-
-    hub = importlib.import_module("pipelex.hub")
-    return hub.get_class_registry()  # type: ignore[no-any-return]
+from pipelex.system.registries.class_registry_access import get_class_registry

Note where the import points: not at runtime_hub. core.concepts.concept sits inside runtime_hub's own closure (runtime_hub → cogt.llm.llm_worker_abstract → system.telemetry.otel_factory → core.pipes.pipe_output → core.stuffs.stuff → core.concepts.concept), so importing the hub from there is a hard cycle in both orders. The accessor lives one level below both hubs instead.

Library scoping crosses downward at boot, never as an import

get_class_registry() must stay library-scoped — a Temporal workflow pins its own registry — but resolving which library is current is interpreter knowledge. So the runtime side holds a defaulted callable slot, and the interpreter installs the real resolver when it is constructed.

# pipelex/system/registries/class_registry_access.py — imports nothing from pipelex
class ClassRegistryScoping:
    def __init__(self) -> None:
        self._resolver: Callable[[], ClassRegistryAbstract | None] = _no_library_scoping

    def install(self, *, resolver: Callable[[], ClassRegistryAbstract | None]) -> None:
        self._resolver = resolver

    def reset(self) -> None:
        self._resolver = _no_library_scoping

class_registry_scoping = ClassRegistryScoping()

def get_class_registry() -> ClassRegistryAbstract:
    scoped = class_registry_scoping.resolve()
    if scoped is not None:
        return scoped
    return KajsonManager.get_class_registry()          # degrade, never raise

# pipelex/interpreter_hub.py — set_interpreter_hub() installs the library-scoped resolver.
# pipelex.runtime_hub.get_class_registry delegates here and stays the public accessor.

The default matters: a process that only ever builds a RuntimeHub — the doctor path, most unit tests — degrades to the process-global registry instead of raising. A defaulted callable, never an unset attribute; the same shape as the existing HubSlot.ISOLATED_EXECUTION_PROBE.

What a straddling call site looks like now

36 of the 309 files used symbols from both halves. Those are the only ones that gained a second import line — and the line itself now says which layer each symbol belongs to.

--- a/pipelex/pipe_operators/llm/pipe_llm.py
-from pipelex.hub import (
-    get_class_registry,
-    get_concept_library,
-    get_content_generator,
-    get_model_deck,
-    get_native_concept,
-    get_required_concept,
-)
+from pipelex.interpreter_hub import get_concept_library, get_native_concept, get_required_concept
+from pipelex.runtime_hub import get_class_registry, get_content_generator, get_model_deck

Everything else was a one-line module swap, applied by an AST pass over whole import statements — not a regex, because 29 of the blocks were parenthesized and multi-line.

Core's data model stopped reaching upward

Five core/ modules looked concepts up through the hub. They now declare what they need as a parameter, which is what lets them join the runtime layer.

--- a/pipelex/core/stuffs/stuff_factory.py
-def make_from_blueprint(cls, blueprint: StuffBlueprint) -> "Stuff":
-    concept_library = get_concept_library()                          # ← reaches into the interpreter
-    if isinstance(blueprint.content, str) and concept_library.is_compatible(
-        tested_concept=concept_library.get_required_concept(concept_ref=blueprint.concept_ref),
-        wanted_concept=get_native_concept(native_concept=NativeConceptCode.TEXT),
+def make_from_blueprint(cls, blueprint: StuffBlueprint, *, concept_provider: ConceptProviderAbstract) -> "Stuff":
+    if isinstance(blueprint.content, str) and concept_provider.is_compatible(
+        tested_concept=concept_provider.get_required_concept(concept_ref=blueprint.concept_ref),
+        wanted_concept=concept_provider.get_native_concept(native_concept=NativeConceptCode.TEXT),
     ):

ConceptProviderAbstract is a new read-side contract owned by core/: resolve a ref, resolve a native code, answer compatibility. ConceptLibraryAbstract extends it, keeping add/remove/list/setup/teardown in the interpreter layer. The split is the point — core depends on resolution, never on a library lifecycle. Injection happens on the interpreter side: pipe_factory, the renderers and pipeline/execution_seams.py call the hub themselves and hand the result down.

Boot builds both, then changes nothing else

# pipelex/pipelex.py — Pipelex.__init__
self.runtime_hub = RuntimeHub()
set_runtime_hub(self.runtime_hub)
self.interpreter_hub = InterpreterHub()
set_interpreter_hub(self.interpreter_hub)          # also installs the class-registry resolver

The setter sequence after this is byte-identical in order, deliberately. Reordering to get a clean “runtime first, then interpreter” run would have moved setters across documented ordering dependencies — the storage-provider block resolves after secrets is on the hub, so the GCP factory's secret read works — a real behavior risk at a checkpoint whose bar was zero behavior change. Constructing both hubs up front already delivers what the ordering was protecting: no setter can run against a missing hub.

Teardown releases both, and drops any scoping the interpreter hub installed — pinned by tests/unit/pipelex/test_hub_lifecycle.py.

04 Where core/ splits

The original plan assumed all of pipelex/core/ could join the runtime layer once the five hub-straddling modules were converted. Measurement said otherwise, and this is the main finding of the work: beyond those five, seven core/ modules import the interpreter directly — no hub involved, so no amount of dependency injection touches them. core.pipes.pipe_abstract alone loads 30 interpreter modules while importing no hub at all.

05 What we gained

Import cost — the measurable part

Be precise about what this buys: it does not make pipeline execution faster. It removes import cost from every consumer that never needed the interpreter. Measured today as a proxy — adding pipelex.interpreter_hub on top of the runtime entry point costs +90 pipelex modules and ~50 ms of in-process import time (median of seven runs, warm cache, one machine). Before the split that was unavoidable: every caller of get_console() paid it. Who collects the refund:

  • pipelex-api's health and version paths, and any cold container or Lambda start that imports the runtime before serving.
  • The CLI's fast paths — --version, which, anything that does not load a method.
  • Every plugin registration module, which by definition runs at import time inside a host process.
  • The test suite: hundreds of unit tests that touch the runtime no longer parse and execute ~9,000 lines of interpreter to do it.

On that timing figure: the before/after wall clock was never captured at the base commit, so the number above is measured today as “what the interpreter half costs to load”. The durable, reproducible numbers are the module and SLOC counts.

Working on this codebase with agents

Blast radius is now structural

A change to a pipe blueprint's module-level imports cannot perturb the import graph of cogt any more. Before, it could — silently. That is the difference between “please be careful” and “the arrow does not exist”.

Failures are loud and local

Deleting pipelex.hub outright means stale knowledge — a model's memory of the old API, a copied snippet, an old branch — produces an ImportError at import time, not a wrong-layer resolution that works until it doesn't.

Placement has a mechanical answer

“Which hub does this new accessor go on?” used to be taste. Now it is two partition tables plus one rule — if it names a Pipe, it is interpreter-layer — and getting it wrong fails a check rather than a review.

String references are caught too

The guard scans string constants, not just imports. That is the class of edit tooling gets wrong most often: mocker.patch("pipelex.hub.get_console", …) broke 36 tests once, and is invisible to every import-graph tool and to pyright.

Smaller closure, smaller context

Reasoning about the runtime layer no longer means reasoning about the interpreter. Fewer modules in the graph is fewer files to read before an answer is trustworthy.

The property is tested, not just the rule

A stray import elsewhere can re-drag the interpreter without touching a hub. The subprocess closure test catches exactly that, and prints the offending modules so the shortest path to the fix is in the failure message.

Cleaner dev docs and a real plugin contract

  • The partition tables are the contract. A plugin author or external consumer reads one of two scoped tables instead of a 300-symbol god module. Placement is decided by kind, not by in-tree usage — which is why accessors with no in-tree importers were kept rather than deleted: several are live external plugin contract.
  • Plugin registries are filed by layer. inference_backend, model_lister, orchestrator, bundle_validator, storage_provider, secrets_provider are runtime-layer; the PipeFunc executor and its registry are interpreter-layer, because their protocol lives in pipe_operators/func/. That call is recorded with its underlying inversion rather than quietly rounded off.
  • The spec is shipped, not tribal. docs/contribute/hub-layering.md follows the shape the repo already uses for a mechanically-enforced convention, and docs/under-the-hood/architecture-overview.md names the boundary. A hub-layering-convention drift contract keeps both from rotting: touch the guard or either hub, and you owe a review.
  • One outward-facing claim, now true and pinned: importing the Pipelex runtime loads zero interpreter modules — the inference engine does not know the MTHDS language exists, so it can be embedded without loading a line of the interpreter.
  • Two documented-but-inert APIs were found and fixed in passing. docs/advanced/observer-provider-injection.md documented hub.set_observer() as the supported way to register an observer — the value was written and never read, so anyone following that page got a silently ignored observer. That page and docs/advanced/index.md, which showed a bare hub being hand-constructed and was equally inert, were rewritten to the mechanism that actually works.

Two things the guard taught us, worth stealing for the next one

Generalizing the string check is what made it work. The plan framed it as an importlib.import_module special case. Scanning every string constant for an exact-or-boundary match on the module path catches importlib, mocker.patch, pkgutil.resolve_name and any config-driven dotted path in one mechanism, with no call-site special-casing. Matching is exact-or-dotted-prefix, which is why pipelex.runtime_hub does not match pipelex.hub, and why a docstring that merely mentions a module is not a reference.

A negative control has to assert the message, not the exit code. The closure test's dirty entry point exits 1 for a second reason — pipelex.interpreter_hub in sys.modules — whatever the offender predicate does. An exit-code-only control would have passed over a completely broken detector, leaving all eight real entry points green and vacuous forever. It asserts the offender message too. Confirmed by mutation: typo the package set, and the control fails while everything else stays green.

Every item in the test-hardening pass was verified by mutation — remove the pinned behavior, watch the new test fail, revert. Watching a new test go green proves nothing about what it pins, and two of those items existed precisely because an existing test appeared to pin something it did not.

08 Known limits — stated, not hidden

  • The layer rule is enforced only one hop deep. The guard checks direct imports, so a runtime-layer module can reach interpreter_hub transitively with both gates green. Blast radius measured exactly: 4 of 476 declared runtime-layer modules, all in pipelex.plugins — the other ten declared packages are clean across 345 modules — via three transitive routes. The headline property is not damaged: the inference layer and runtime_hub still measure 0 and never reach the breaching modules. The remedy is decided — split the built-in plugins by layer, give the two interpreter-touching ones a single interpreter-side home, and teach the guard the transitive check. Its own PR after #1062 merges; simulated at 0 of 128 breaching once three modules relocate.
  • Known inversions, named so the docs stay honest. Two plugins/ modules import from pipe_operators/ and one from pipeline/. They import no hub, so the guard does not flag them — which is exactly why they are written down. Remaining measured cross-layer edges: cogt → core (21), system → cogt (7), plugins → runtime_bridge (6), tools → cogt (3), and one genuine wart, cogt/model_backends/model_lists.py importing a CLI exception.
  • A general layering ratchet is a sequel, not this change. “No runtime module may import any interpreter module, with an allowlist” is a much cheaper argument now that the two biggest clusters are gone — but it is a bigger change than this one should carry.
  • One eager optional-SDK import is out of scope but worth knowing: tracing/event_log_factory.py imports the DynamoDB event log at module level, which runs a module-level try: import boto3, so boto3 and friends load in every process that touches the tracing factory. Three-line fix, entirely independent of this work.
