# The fourth surface — items deferred from the PR #1116 review

What the review-bot pass on [PR #1116](https://github.com/Pipelex/pipelex/pull/1116) surfaced and this branch did **not** fix, with why. Four of the confirmed items were fixed on the branch: the boot-tolerance retry rebuilt a backend's file path with `Path(dir) / name` while the load that preceded it used an f-string, which agree for every ordinary name and diverge for an absolute one — the two are now one `backend_toml_path` helper, so the retry reads the file the load read by construction rather than by coincidence; the "claims no file" guard on both the ledger's `[surface]` block and the registry's `Surface` tested `is None`, so an empty `base_file` or `tier_glob` parsed, claimed nothing and migrated nothing in silence, and both now reject empty alongside absent; the stale-backend e2e class promised in its own docstring that the kit's `pipelex_gateway.toml` is asserted untouched while its neighbours snapshot filtered out every `.toml` in the directory, so the one file the whole `(directory, name)` claiming rule exists to protect was the one file nothing checked — it excludes the two aged files by name now, and a simulated rewrite of the gateway file reddens it; and the `/release` skill's renumbering paragraph said "unbullet-ed". Two of the highest-severity findings — the boot catching only `InferenceBackendLibraryValidationError` when the loader raises its sibling, and `[defaults]` being admitted as if it were a model table — were already fixed by the branch's head commit before the bots' verdicts were read, and are answered on the threads with the code and the pinning tests. Three were refuted: `fingerprint@2` is not inverted against `@3` (the chain runs the other way — `fingerprint@N` is the shape *at* version N, `pipelex-config@3` *is* the reshape, and `check-ledger` and `check-migration-schemas` are both green); the `cli-docs` drift ack does not mismatch (`make drift-check` passes on a clean tree, and the recorded trigger blob OIDs equal `git rev-parse :<path>` — the bot most likely recomputed against GitHub's PR merge commit); and the private-repo-names finding is about text this PR only relocates, byte-identical to what has been on public `main` since `#1099`.

## 1. A backend name is never checked for being a path

**Reporter:** Cubic (`pipelex/cogt/model_backends/backend_library.py`) — [thread](https://github.com/Pipelex/pipelex/pull/1116#discussion_r3797076387).

The fix that landed makes an absolute backend name *harmless* — both the load and the retry now resolve it under the backends directory — but it leaves the name itself unexamined. A backend name is a raw top-level table key of the user's own `inference/backends.toml`, TOML permits a quoted `["/abs/path"]` or `["../elsewhere"]` key, and nothing between the file and `InferenceBackend.name` (a plain `str`) rejects one. The same shape is built a third time for the health report at `pipelex/cli/commands/doctor_cmd.py`, which still uses the `/` operator.

**Why deferred:** rejecting a path-like key is a *new refusal* on a user-facing surface, not a review fix — it decides that a configuration which loads today stops loading, and it needs its own message, its own error class placement (`InferenceBackendLibraryValidationError`, so it lands in `BACKEND_LIBRARY_REFUSED` and inherits the surface-aware migration report for free) and its own migration question. Nothing is broken while it is absent.

**Recommendation:** add the guard in `load`, right after the enabled/CI skips, refusing a name that is absolute, contains a separator, or is `.`/`..`, and naming the backend and `backends.toml` the way the index-file refusal already does. Do it together with a sweep of the doctor's own path construction onto `backend_toml_path`, so all three sites are one spelling rather than two.

## 2. The diagnosis reports a header's name, never its value

**Reporter:** Cubic, second half of the admission finding (`pipelex/migration/surfaces.py`) — [thread](https://github.com/Pipelex/pipelex/pull/1116#discussion_r3797076393).

The first half — `[defaults]` treated as a model table — was already fixed on the branch. The half that remains is real: a header-shaped key on a *model* table whose value the loader refuses (`x-foo = 3`, or a value with a line break or a trailing space) is admitted by `admits_unnamed_key` and therefore never appears in a downgrade diagnosis, because only the key's spelling is examined. The illegal-header-*name* case the same comment raises is already closed by `is_legal_header_name`.

**Why deferred — and this one is a "no", not a "later".** The diagnosis has exactly one sentence to say about a key it reports: *the current schema has no setting there, and no ledger entry retires it — either the name is a typo, or this file was written by a newer pipelex*. For `x-foo = 3` both halves of that are false, so reporting it would replace silence with wrong advice. It would also make the backend the only surface whose diagnosis reads values (`[runtime.log] level = 42` is accepted by the main configuration's diagnosis the same way), and it would fix nothing the user is missing: a scan that finds nothing attaches no migration block, so the loader's own sentence reaches them whole, naming the model, the backend and the file. The reasoning is now recorded in the `admits_unnamed_key` docstring, where the next reader will find it.

**Recommendation:** leave it. Revisit only if the diagnosis ever grows a second note — a *this key is known but its value is not usable* verdict — at which point admitting the value half becomes cheap and honest at the same time.

## 3. Private repo names and deep paths in committed docs of a public repo

**Reporter:** Cubic (`wip/pipe-refs/implementation-plan.md`) — [thread](https://github.com/Pipelex/pipelex/pull/1116#discussion_r3797076399).

The observation about the doc is accurate — it names internal sibling repos and their exact file paths, and it is internally inconsistent about it, calling the transport layer "the layer that is not open core" on one line and spelling its exact path two lines down. The claim *about this PR*, though, does not hold: those paragraphs are byte-identical to `TODOS.md` on public `main`, where they landed with `#1099`, and this PR only moves them into `wip/pipe-refs/`. Net new public exposure is zero. The bot's own private/public list is also partly wrong: one repo it calls private is public in a different org, and two of the names it flags do not exist under those names at all.

**Why deferred:** the real question is repo-wide and predates this branch. It is not answerable inside a PR that relocates already-published text, and answering it there would leave every other occurrence standing while looking like the matter was handled.

**Recommendation:** decide once whether internal repo names belong in this repo's committed docs at all, then sweep. The sweep must start with shipped code, not docs — `pipelex/pipe_run/delivery_executor.py` names an internal repo and a path inside it in a comment that goes out in the PyPI wheel, which is a wider audience than a `wip/` doc has. If the answer is "role language only", the `#1099` genericization pass simply needs finishing; if it is "these names are fine", the doc's inconsistency should be resolved the other way, by naming the transport layer plainly on both lines.
