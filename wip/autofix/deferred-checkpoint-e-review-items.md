## Fixed in this branch (confirmed bugs)

These were verified reachable against the code and fixed at checkpoint exit.

1. **mkdocs nav orphan** — `mkdocs.yml`. `docs/tools/cli/fix.md` was added only to the llmstxt plugin's page-title map (the `Reference:` block ~line 269), not to the site `nav:` `CLI Reference` block (~line 489). The page was unreachable from site navigation and `mkdocs build --strict` would flag it. Fix: added `- Fix: tools/cli/fix.md` after `Validate` in the real `nav:`.

2. **`validate` footer not shell-safe** — `error_handlers.py` ~line 367. The actionable `pipelex fix bundle <path> -L <dir>` footer was built by bare f-string interpolation of `bundle_path` and each `-L` dir. A path containing a space rendered a command that splits when copy-pasted (the one-click remediation the feature exists for). Fix: `shlex.quote` each interpolated path.

3. **`fix` still-invalid tip contradicts its own suggested-fix lines** — `_fix_core.py` ~line 120. The still-invalid arm always printed "…they have no deterministic safe fix, so they need a manual edit", but `remaining_errors` routinely carries items **that do** have a `💡 Suggested fix:` line — errors skipped by `--select`/`--ignore`, dropped for being out of write scope, or left by a `max_iterations`/no-progress/collision bail. The shipped integration test `test_select_filter_is_honored_end_to_end` produces exactly this contradiction. Fix: make the tip conditional — when any remaining error still carries a suggested fix, point at the filters / `-L` / bail reason instead of claiming a manual edit is the only option.

4. **`--diff` PipeSignature wording asserts the file is valid** — `_fix_core.py` ~line 94. Under `--diff`, a run that converges to valid-with-pending-signatures printed "Bundle is valid but NOT yet runnable …" in the same non-conditional phrasing as a real write, even though nothing was written and the on-disk bundle is still invalid. Fix: make the pending-signature messaging preview-aware ("would be valid but would still not be runnable").

5. **`--diff` crashes and mislabels on a missing `-L` dir; diverges from the real run** — `_diff_sandbox.py` + `_fix_core.py`. A non-existent `-L` dir makes `shutil.copytree` in `mirror_bundle_for_preview` raise `FileNotFoundError`, which `execute_fix`'s blanket `except FileNotFoundError` mislabels as `"bundle file not found: '<bundle_path>'"` (the bundle exists — the `-L` dir is what's missing) and exits 2. The **real** (non-`--diff`) run tolerates a missing dir (`library_utils.get_pipelex_mthds_files_from_dirs` skips it; `resolve_library_dirs` keeps it in `effective_dirs` so multi-file semantics are unchanged) and still produces a 0/1 verdict. Fix: `mirror_bundle_for_preview` creates an **empty** copy dir for a missing `-L` dir instead of copying it — no crash, the dir contributes no files (matching the real loader), and the 1:1 dir count preserves `is_single_file`, so the preview verdict tracks the real run.

## Deferred (real, but design tradeoffs or niche — not snap-fixed at checkpoint exit)

Per the house pattern (`feedback_defer_design_tradeoff_findings`): findings that are genuine but are design tradeoffs, currently-unreachable latent gaps, or DRY refactors whose correct fix touches a layering boundary — captured here rather than patched reflexively at exit.

- **A. `validate` footer over-counts fixable errors** — `error_handlers.py` ~line 365. `fixable_count` counts every `ValidationErrorItem` carrying a `suggested_fix`, but `pipelex fix`'s loop then drops fixes that are UNSAFE, source-less under multi-file validation (`_safe_fixes`), or target files outside the per-call write scope (`_partition_by_write_scope`). So in ambient/multi-file edge cases (a fixable error whose fix is sourced at a hub-default / `PIPELEXPATH` file, validated with no `-L`) the footer promises "N can be fixed" and the suggested command then bails "outside write scope", applying nothing. **Not reachable in the common single-file, all-safe-rules path** (all shipped rules are SAFE; sources are backfilled). A faithful count would have the renderer re-derive `resolve_library_dirs` + `_safe_fixes` + write-scope — coupling the validate presentation layer to fix-loop internals. **Recommendation:** either (a) soften the footer from a promise to a hint ("may be auto-fixable — try:") — cheap but slightly dilutes the good common-case UX, or (b) factor a shared `count_applicable_fixes(items, *, library_dirs)` helper in the fixes package that both the loop and the footer call, so the promise is exact. Prefer (b) when an UNSAFE rule or heavier multi-file usage ships; until then the over-promise is confined to niche ambient setups.

- **B. `--diff` sandbox copies each `-L` dir separately — no resolved-path dedup** — `_diff_sandbox.py` ~line 71. Each explicit `-L` dir is mirrored into its own `lib_<i>`, so overlapping/duplicate/nested `-L` values (`-L a -L a`, or directory mode `dir/` combined with `-L $PWD/dir`) become physically distinct files that defeat the real loader's resolved-path dedup (`library_manager` collapses them). The preview then reports duplicate pipe/concept declarations and "would still be invalid" (exit 1) while the real run dedupes and converges (exit 0). **Niche** (requires the user to pass overlapping `-L` dirs). Correct fix: dedupe `-L` dirs by resolved path before mirroring and let `to_original` map multiple original roots onto the single copy (the mapping currently assumes one original per copy). Deferred because the multi-origin `to_original` change deserves its own tests, and the trigger is unusual. Note the adjacent question of whether `resolve_bundle_target`'s directory auto-injection should itself dedupe against an explicit `-L` (it string-compares the injected relative dir against an absolute `-L`).

- **C. `resolve_bundle_target` duplicated across the human and agent CLIs** — `pipelex/cli/commands/bundle_path_resolver.py` re-implements `pipelex/cli/agent_cli/commands/bundle_path_resolver.py` near-verbatim (same `expanduser`, `DEFAULT_BUNDLE_FILE_NAME` precedence, single-`*.mthds` glob fallback, library-dir injection), differing only in error presentation (typer red-err vs the agent's structured error). ~60 lines now live twice; a future change to the resolution rules applied to one twin silently diverges the surfaces, breaking the "fix patches exactly the file validate judged" invariant. **Recommendation:** extract a shared core that resolves and raises a typed `BundleTargetResolutionError`, each CLI rendering it in its own presentation. Deferred as a DRY refactor, not a live bug (behavior is currently identical). This is the same shape as the step-3/4 shared-resolver work; fold it into the next surfacing wave rather than a checkpoint-exit patch.

- **D. `_reject_invalid_rule_filters` duplicated across the human and agent CLIs** — `pipelex/cli/commands/fix/bundle_cmd.py` duplicates the identically-named check in `pipelex/cli/agent_cli/commands/fix/bundle_cmd.py` (same `--select`/`--ignore` mutual-exclusion rule and `KNOWN_FIX_CODES` set-math), differing only in presentation. Same risk and remedy as C: extract the set-math into a shared helper returning the violation, each CLI presenting it. Deferred with C.

- **E. Dry-run diagnostic can be dropped in `fix`'s still-invalid arm** — `_fix_core.py` still-invalid rendering. `validate`'s human handler re-prints `exc.dry_run_error_message` alongside categorized errors (the shared items builder projects the dry-run channel only when it is the sole failure channel). `fix`'s still-invalid arm renders only `remaining_errors` (same builder output) and has no equivalent guard, and `FixBundleResult` does not carry `dry_run_error_message` separately. **Currently unreachable:** `validate_bundle`'s raise arms never produce categorized errors and a dry-run message together (the finder acknowledged this). Latent only. Fixing it means adding a `dry_run_error_message` field to `FixBundleResult` and threading it — more than a rendering tweak, for a case the code can't currently hit. Deferred as a latent-consistency item; revisit if `validate_bundle` ever raises the mixed shape.

## Considered and rejected (not a defect)

- **`ValidationErrorCategory.is_dry_run` property is "speculative API for one call site"** — `base_exceptions.py`. A finder argued the 4-arm exhaustive-match property should be an inline `item.category == ValidationErrorCategory.DRY_RUN`. **Rejected:** this contradicts the repo's Python standard (`.claude/rules/python-standards.md` → "Never test equality to an enum value: use match/case … add `@property` methods to the enum class such as `is_foobar()`"). The property is the house-preferred form precisely so that adding a `ValidationErrorCategory` member makes the linter flag every site that must handle it. Keeping it.
