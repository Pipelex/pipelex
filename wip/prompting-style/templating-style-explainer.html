Engineering note · branch fix/Keyless-dry-run

<Retiring prompting_target>

How a method’s inputs get tagged into a prompt is now something the author declares, not something the runtime infers from whichever provider happens to serve the model. The per-provider dialect map is deleted. Every OpenAI-family prompt changes shape from back-tick fences to XML tags.

Status all phases built & green; final two staged, uncommitted Repo Pipelex/pipelex Date 2026-08-14 Breaking yes

TL;DR

  • What. A PipeLLM can declare templating_style — a bare tag-style string ("xml", "ticks", "square_brackets", "no_tag") or a full { tag_style, text_format } table. Anything that declares nothing takes one runtime default, shipped as xml. prompting_target, the per-target style map and derive_templating_style are gone; nothing consults a model, a deck or a credential to decide prompt shape.
  • Why. Sending back-ticks to OpenAI and XML to Anthropic maintained a distinction current frontier models no longer make — and the data was infra-shaped, declared once per backend rather than per model. The direction was ruled on 2026-08-03 and deferred as KF-16.
  • Why now. A keyless boot was silently rendering different prompts in dry runs. We started to fix that, realised the fix was to delete the mechanism we had already agreed was obsolete, and did that instead. The bug is dissolved, not repaired.
  • What breaks for you. Prompt text changes for every OpenAI-family model, and for any template using | tag on any model. Any repo shipping its own .pipelex/inference/backends/*.toml fails to boot until every prompting_target line is deleted — and portkey.toml carries it per-model as well as in [defaults].

01 The mechanism we deleted

Prompt shape used to be the tail end of a six-link inference chain: the pipe resolved an LLM setting, the setting named a model handle, the handle was looked up in the deck, the deck returned an InferenceModelSpec, the spec carried a prompting_target string, and that string indexed a map in pipelex.toml which finally produced a TemplatingStyle. Six links, each of which had to succeed, to answer a question the method author could simply have been asked.

02 Why now: the dry-run divergence

The branch is called fix/Keyless-dry-run because it was cut to fix a different bug. A dry run exists to rehearse a real run without spending money, which is why it is documented as needing no API keys — naturally read as same program, mocked leaves. It was not true: a dry run booted without credentials rendered different prompts from one booted with them, and nothing in either run said so.

Same method, same inputs. Every backend declares its key as a ${VAR}, so on a keyless machine the lenient load skipped every backend and the deck came out empty — and the style derivation took its documented None path, written for a case (a model served by an external plugin) that a keyless boot satisfies for every model at once. Both runs complete, both report identical usage records, neither logs the difference.

Why it stayed invisible: any gate whose two sides boot the same way cannot see this variable at all — and reads as evidence that it does not matter. Two keyless sides agree perfectly. The divergence only surfaces against a side that cannot boot keyless.

The turn — and the relationship, stated precisely

A four-part fix plan was written: build a seam letting a credential-free process load model metadata without model credentials. Then the obvious thing landed — the headline symptom only exists because prompt shape is derived from infrastructure at all. Delete the derivation, and keyless and keyed boots render byte-identical prompts by construction.

The bug surfaced and scheduled this work; it did not motivate it. Every argument for the change holds with no bug in the picture. Had we fixed the bug as planned, we would have built a metadata seam whose main beneficiary was a derivation we were about to delete.

The diagnosis in that bug report is untouched — a keyless boot still yields an empty deck — but the two silent symptoms (back-tick step-2 prompts, an ignored llm_setting.prompting_target) are dissolved rather than fixed. What survives is loud or minor: max_prompt_images and image param-support checks need a populated deck; handle-pinned bundles are rejected keylessly; the two CLIs disagree on whether --dry-run needs credentials. Whether the expensive half of that plan still earns its blast radius is now an open question rather than a settled one.

03 What it looks like now

Before — infra decided

pipelex/pipelex.toml 
[pipelex.prompting_config]
default_prompting_style = { tag_style = "xml" }

[pipelex.prompting_config.prompting_styles]
openai    = { tag_style = "ticks" }
anthropic = { tag_style = "xml" }
mistral   = { tag_style = "square_brackets" }
gemini    = { tag_style = "xml" }

Plus a prompting_target line in every backend TOML, and per-model overrides in portkey.toml.

After — the author decides

pipelex/pipelex.toml 
[pipelex.templating_config]
default_templating_style = { tag_style = "xml" }

One default for anything that declares nothing. No per-model, per-backend or per-preset override exists — deliberately.

any .mthds file — bare string is the tag_style shorthand, inline table is the full struct 
[pipe.summarize_article]
type             = "PipeLLM"
inputs           = { article = "Text" }
output           = "Text"
templating_style = "square_brackets"

[pipe.render_note]
type             = "PipeLLM"
templating_style = { tag_style = "xml", text_format = "markdown" }

Each style below shows what @article produces for an input named article. The tag name comes from the variable; a value with no name of its own falls back to data. The two sigils are governed by different halves of the style: @variable on its own line wraps the whole input per tag_style; inline $variable inserts it formatted per text_format, unwrapped.

square_brackets[article] … [/article]
no_tagthe value, bare

The two edits that carry the change

pipelex/kernel/templating_style_ops.py — new, and this is the whole thing 
+def resolve_templating_style(*, authored: TemplatingStyle | None) -> TemplatingStyle:
+    """The style a prompt renders under: the authored one, else the configured default."""
+    return authored or get_config().pipelex.templating_config.default_templating_style

Total, deck-free, credential-free. Its totality is the point — because it can never return None, nothing downstream has to carry an optional style and invent a fallback for it.

pipelex/tools/jinja2/jinja2_filters.py — the fallbacks die 
-    tag_style_str = context.get(Jinja2ContextKey.TAG_STYLE)
-    tag_style = TagStyle(tag_style_str) if tag_style_str else TagStyle.TICKS
+    tag_style = TagStyle(require_templating_style_value(
+        context=context, jinja2_context_key=Jinja2ContextKey.TAG_STYLE))

This is what makes the class of bug unreachable rather than merely fixed. A missing key now raises Jinja2ContextError, with no default, deliberately: every prompt-rendering entry point resolves a style before rendering, so a missing one means the render was set up wrong. The old TICKS default is exactly how a triple-backtick style used to reach prompts nobody had chosen it for.

04 Three traps worth knowing about

Trap 1 — an unknown key becomes an HTTP header

backend_library.py reclassifies any per-model TOML key that is not in InferenceModelSpecBlueprint.model_fields as an outbound HTTP header. Deleting the model field while a per-model prompting_target = "gemini" line survived would have shipped that line to the provider as a header, silently. The field deletion and the TOML deletions had to land in one commit, verified by grep across the source tree and the synced kit copies.

This is the trap in the downstream sweep too, and it is why deleting only the [defaults] line is worse than doing nothing: the boot starts working again while the per-model occurrences quietly become headers.

Now scheduled to be closed — wip/rogue-extra-headers-guard-plan.md, gated on this branch merging. The bag stays open (the gateway genuinely needs to be served new x-portkey-* headers without a client release) but gets a shape rule: an unknown key is accepted as a header only if it is header-shaped, i.e. contains a hyphen. Blueprint field names never do, so every removed field and every snake_case typo — max_tokns — becomes a loud error from a local TOML and a silent prune from the served payload, instead of a string posted to the provider. endpoint_path, which is routing metadata rather than a header and only escapes the wire by luck today, is promoted to a real field.

Trap 2 — the remote config outlives the field, and the skew is routine

Deleting prompting_target from the blueprint made the entire test suite fail at boot, one cause. The Pipelex Gateway does not read its model specs from this repo: they are fetched from the API and cached, and that served config still declared the key. The blueprint is extra="forbid", so a config written by a different release than the client reading it stopped the boot dead. Fixed with a general tolerance rather than a shim for one field — drop_unknown_gateway_defaults prunes unknown keys from the remote config’s defaults. Local files stay strict.

That tolerance is load-bearing every day, not just on deploy days. The cache is one file per machine, ~/.pipelex/cache/remote_config.json, shared by every worktree — and it records schema_version, cached_at and the body, but no source URL. So a checkout pinning _12 cannot tell it is reading an _11 body. On this machine on 2026-08-14 it was doing exactly that: the cache held _11 byte-for-byte, because the other seven checkouts all pin _11 and one had booted more recently. Make remote unknowns fatal and that ordinary local condition turns the suite red.

Trap 3 — deleting the key from the served config is a live change

The served gateway config is owned by pipelex-back-office. Removing the key there would have flipped every gateway prompt already deployed in the field from XML to back-tick fences — because an older client never reaches its configured default (get_prompting_style(None) returns None, not the default), so no style reaches the filter and the old TICKS fallback applies.

That never happened because the config is versioned in its URL and this branch bumps it: pipelex_remote_config_12.json, was _11. _11 is frozen and still carries the key, so every earlier release keeps rendering XML. The URL bump is the compatibility boundary for any breaking change to that config — worth knowing before the next one.

05 What you need to do

If you author .mthds methods

Nothing, unless you want the control. Prompts for OpenAI-family models change shape from back-tick fences to XML tags — that is the change. If a specific pipe wants a different shape, declare templating_style on it; if your whole project wants a different house style, set default_templating_style in your .pipelex/pipelex.toml.

If your repo ships its own backend TOMLs — not optional

Local backend files are read strictly. On the version bump, every repo shipping .pipelex/inference/backends/*.toml dies at boot with Extra forbidden fields: 'prompting_target' — confirmed in pipelex-server/worker/, pipelex-api/, cocode/, pipelex-cookbook/, pipelex-demos/, mthds-ui/, plus pipelex-js/ fixtures. Delete every occurrence, [defaults] and per-model alike, and grep to prove it. Re-read trap 1 first: a partial fix is worse than none.

If you use a template with | tag or | format

Those filters no longer have a default of their own. Through any normal prompt path you are fine — a style is always resolved for you. Drive the kernel API directly and omit the style, and you now get a loud Jinja2ContextError instead of a silently-chosen shape.

Other things this change also does, that you might not expect
  • Compose, image-gen, search and structuring prompts all changed too. They previously rendered style-less, which the filters silently absorbed as back-ticks and plain text. If your PipeCompose template or a construct-mode template field uses | tag, its output changes shape — on any model family, not just OpenAI’s.
  • PipeImgGen and PipeSearch have no authored knob (deliberately, for now). They inherit the config default.
  • Lenient loading got narrower. InferenceBackendLibrary.load(lenient=...) exists so a keyless boot can skip backends with missing credentials — but it caught the error base classes, so a malformed local TOML was skipped just as quietly. Now only InferenceBackendCredentialsError is tolerated; malformed configuration is fatal in both modes.
  • The format filter had a latent bug, fixed in passing: its argument was annotated TextFormat | None, but Jinja2 hands a template-supplied {{ x | format("markdown") }} over as a raw str.
  • A dead module went with it: llm_prompt_template.py, llm_prompt_factory_abstract.py, llm_prompt_template_inputs.py and LLMPromptTemplateInputsError — a hardcoded XML+Markdown style that predated the configurable one and had no production consumer.
