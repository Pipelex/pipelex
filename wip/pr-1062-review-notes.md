# PR #1062 review notes — deferred items

Triage record for the SWE-agent review threads on [PR #1062](https://github.com/Pipelex/pipelex/pull/1062) (the `pipelex.hub` split into `runtime_hub` / `interpreter_hub`, plus the layering guard and the import-closure test). One unresolved thread, from Codex ([`PRRT_kwDOOwmMFc6T2CA7`](https://github.com/Pipelex/pipelex/pull/1062#discussion_r3652317405)), on `tests/unit/pipelex/test_runtime_layer_import_closure.py`: the closure predicate only recognised five interpreter top-level packages, which is narrower than the interpreter layer `docs/contribute/hub-layering.md` describes.

Two of the three parts were fixed in-place — the doc's `pipe_output` misclassification, and the predicate widening that closes the real `core.pipes.pipe_blueprint` blind spot. This file captures the part deliberately **deferred**. Its thread is left **open**.

## 1. Interpreter-named packages leak leaf models into every runtime closure

- **Reporter:** Codex (thread `PRRT_kwDOOwmMFc6T2CA7`), on `tests/unit/pipelex/test_runtime_layer_import_closure.py`. Codex asked for the predicate to cover "the complete documented interpreter layer", naming `pipeline` and `pipe_run` among the gaps.
- **Verdict:** confirmed as a fact, but it is a *placement* problem, not a broken hub arrow — so naming those packages in the closure predicate would turn the test red without any code being wrong in the sense the test measures.
- **What is actually loaded.** Measured in a clean subprocess:
    - `pipelex.runtime_hub`'s own closure pulls `pipelex.pipeline.pipeline_models` (`SpecialPipelineId`), `pipelex.pipe_run.pipe_run_mode` (`PipeRunMode`) and `pipelex.graph.graphspec` (`GraphSpec`) — all three reached through `pipelex.core.pipes.pipe_output`, which names them as fields.
    - `pipelex.core.stuffs.stuff_factory` additionally pulls `pipelex.pipeline.exceptions`, `pipelex.pipeline.validation_errors` and `pipelex.pipeline.fixes.planner`, which in turn pull `pipelex.core.bundles.exceptions` (`PipelexBundleBlueprintValidationErrorData`) and, as collateral, the empty `pipelex.core.bundles` package placeholder.
- **Why deferred:** every one of those is a leaf model or an exception type — a `StrEnum`, a run-id constant, a graph spec, structured validation-error data. None of them imports the interpreter; none of them needs a loaded method. They are interpreter-layer only by virtue of *which package they were filed in*. Resolving that means relocating types across package boundaries, which changes public import paths (`GraphSpec` and `PipeRunMode` are both consumed outside this repo) — a refactor with cross-repo churn, not something a PR-review pass should decide unilaterally.
- **Current state in the test.** The predicate covers the five interpreter top-level packages plus core's Pipe-machinery modules by name (`core.bundles`, `core.interpreter`, `core.registry_models`, `core.pipes.pipe_abstract` / `pipe_blueprint` / `pipe_factory` / `rendering`). `core.bundles.exceptions` and the bare `core.bundles` placeholder are excluded by **exact** match, so the rest of `core.bundles` stays flagged. `pipeline`, `pipe_run` and `graph` are absent entirely.
- **Recommendation — two candidate resolutions, pick one deliberately:**
    1. **Relocate the leaves down**, mirroring the `JobMetadata` / `TraceContext` moves this PR already records under "Placement, not coupling": `SpecialPipelineId` and `PipeRunMode` into `pipelex/system/`, and decide a home for `GraphSpec` that is not `graph/` (which also carries mermaid/reactflow rendering). Then the predicate can name `pipeline` and `pipe_run` wholesale and the exclusion tuple disappears. This is the resolution consistent with the doc's own stated lesson — "when a package straddles the boundary, moving the odd module out is usually cheaper than teaching the guard about exceptions."
    2. **Declare them straddling**, i.e. accept that `pipeline` / `pipe_run` / `graph` are not single-layer packages the way `core/` is not, and say so explicitly in "Where core splits" (renaming it accordingly). Cheaper, but it weakens the claim that the boundary falls on package lines.
- **Note on `core.bundles.exceptions` specifically:** the reason it is imported from `pipeline/` at all is that `PipelexBundleBlueprintValidationErrorData` is the payload of `pipeline`'s validation-error types. If option 1 is taken, that one is the awkward case — the data shape genuinely belongs with the bundle blueprint, and the importer is the thing in the wrong layer.

## Not deferred — fixed on this branch

Recorded here only so the thread's three parts are traceable:

- **`pipe_output` was misclassified in the doc.** `docs/contribute/hub-layering.md` listed `core.pipes.pipe_output` under "The Pipe machinery — interpreter" with the justification "Every one of them names a `Pipe`". It names no `Pipe`: it holds the working memory, graph spec and token usage a run *produced*. It imports zero interpreter modules, and it sits inside `runtime_hub`'s own closure — which the same document shows three sections later, in the class-registry import chain. The guard's own docstring (the enforcement source of truth) correctly omitted it. Moved to the runtime data-model bullet.
- **`core.pipes.pipe_blueprint` was a genuine blind spot.** Documented interpreter-layer by both the doc and the guard, yet it loads zero heavy packages and no hub — so a runtime-layer import of it passed a package-only predicate. Every other documented interpreter module was caught only *transitively*, through the `pipe_operators` / `libraries` it happens to drag in. The widened predicate now names them, so it states the boundary instead of approximating it.
