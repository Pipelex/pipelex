## L-260916-a1dbd5, round 1 (fields, context, no stack walk)

- **Caller attribution rides a fixed frame depth** (*unverified*, cubic). `CALLER_FRAME_DEPTH` in `pipelex/tools/log/log_dispatch.py` counts the frames between the frame lookup and the code that called `log.<level>(...)`, so a helper inserted into or removed from that call chain would attribute records to the wrong module and apply the wrong logger level. The tests in `tests/unit/pipelex/tools/test_log_caller_module.py` emit through every level and assert the caller's module, path and function, which is what catches such a change. A walk up the frames until one leaves the log package would remove the constant at the cost of a loop per line; the fixed depth stays until a second facade entry point makes the constant wrong for one of them.
- **A given `field_<name>` beside a colliding `<name>`** (*unverified*, cubic). Prefixing a colliding entry could overwrite an entry the caller gave under the prefixed name. Deferred here on the reading that the ordered attach kept both values; round 2 verified that it did so in one order only, and fixed it: the prefix is now applied until the destination is free.
- **The traceback rides the message rather than `exc_info`** (verified by inspection, code-review and the implementer). `include_exception` appends `traceback.format_exc()` to the message text in the dispatch. A structured sink wants the exception as `exc_info` or `exc_text`; setting it today would make the Rich handler render the traceback twice. The sink member L-260916-aa6e58 owns that decision, and the note on it carries the detail.

## L-260916-aa6e58, the migration finding, settled by the owner on 2026-09-17

**`pipelex-config@5` stays `safe`, and this finding is closed rather than deferred.** It was raised on every round of this member and once more by a Codex pass reading `origin/dev` during the Rich member's round 1, each time as the same reading: the entry deletes `is_console_logging_enabled = false` without translating it, and boot tolerance replays the ledger in memory, so an upgrade alone hands a silenced deployment its console back.

An implementer cured it on 2026-09-17 by making the entry `unsafe`, and that change was reverted the same day on the owner's decision. What the block cost is what decided it. `safety` is a property of an entry, entries are one per schema version and contiguous (`pipelex/migration/ledger.py:197`), and this version's link owns all four key removals, so the block cannot be narrowed to the case that matters. An `unsafe` entry is rehearsed and never applied (`pipelex/migration/engine.py:118`), so the retired keys survive the boot-tolerance replay, the re-validation fails again against a model that is `extra="forbid"` (`pipelex/system/configuration/config_model.py:12`), and `load_config_and_validate` re-raises (`pipelex/system/configuration/config_loader.py:530`). The block therefore converts "boots with a warning" into "fails to boot" for **every** file still carrying any of the four keys at their old defaults — every full copy of an older base file — for the sake of the few that chose otherwise.

The owner's reading is that nothing chose otherwise: no deployment set these keys, nothing depends on the flag outliving its removal, and this project keeps no backward compatibility. Round 3 had already recorded the corroborating fact, that no repository in the workspace sets the flag.

**Reopening this needs a new fact, not a new reading** — a configuration that actually sets one of the retired keys and a reason it may not be edited by hand. The rationale is recorded in the entry's own comment in `pipelex/migration/ledgers/pipelex-config.toml` so that it travels with the code rather than with this document.

Two corrections outlived the revert, both independent of the safety decision and both kept: the entry's guidance and `docs/configuration/config-practical/logging-config.md` had said `is_console_logging_enabled = false` "silenced every handler on the root logger", where `LogDispatch.dispatch` returned early and third-party loggers still reached the handlers, and the entry's comment had named `default_log_level = "OFF"` as the replacement where the base pins `pipelex` in `package_log_levels` and the root level alone silences none of Pipelex's records.

One finding from the reverted work is real and stays: `BlockedEntry` carries no `title` or `description` (`pipelex/migration/plan.py:72`), so a blocked entry reaches its reader through `guidance` and `detail` alone. It is latent — no shipped ledger entry is `unsafe` — and it is the mirror of L-260916-5d142f, which carries a safe step's unrendered guidance; the note on that item records it.
