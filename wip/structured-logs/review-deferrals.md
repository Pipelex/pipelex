## L-260916-a1dbd5, round 1 (fields, context, no stack walk)

- **Caller attribution rides a fixed frame depth** (*unverified*, cubic). `CALLER_FRAME_DEPTH` in `pipelex/tools/log/log_dispatch.py` counts the frames between the frame lookup and the code that called `log.<level>(...)`, so a helper inserted into or removed from that call chain would attribute records to the wrong module and apply the wrong logger level. The tests in `tests/unit/pipelex/tools/test_log_caller_module.py` emit through every level and assert the caller's module, path and function, which is what catches such a change. A walk up the frames until one leaves the log package would remove the constant at the cost of a loop per line; the fixed depth stays until a second facade entry point makes the constant wrong for one of them.
- **A given `field_<name>` beside a colliding `<name>`** (*unverified*, cubic). Prefixing a colliding entry could overwrite an entry the caller gave under the prefixed name. Deferred here on the reading that the ordered attach kept both values; round 2 verified that it did so in one order only, and fixed it: the prefix is now applied until the destination is free.
- **The traceback rides the message rather than `exc_info`** (verified by inspection, code-review and the implementer). `include_exception` appends `traceback.format_exc()` to the message text in the dispatch. A structured sink wants the exception as `exc_info` or `exc_text`; setting it today would make the Rich handler render the traceback twice. The sink member L-260916-aa6e58 owns that decision, and the note on it carries the detail.

## L-260916-a1dbd5, round 3 (bar necessity)

The bar admitted only what the round-2 pass itself introduced or what the branch could not ship without. The three entries marked *verified* were confirmed by reproduction and deferred because they predate that pass, no runtime caller reaches them, and the sink member L-260916-aa6e58 owns the same modules before the sprint's release; the note on that item carries each with its fix.

- **The collision guard reads only the record's instance dict** (*verified*, codex:review and codex:adversarial). `attach_log_record_extra` in `pipelex/tools/log/log_fields.py` tests `name in vars(record)`, which misses the attributes the `LogRecord` class owns: `fields={"__class__": ...}` and `{"__dict__": ...}` raise `TypeError` out of the log call, and `{"getMessage": ...}` shadows the method so the formatter fails and the stdlib's `handleError` drops the record. The fix is `hasattr(record, attribute)` in place of the `vars` lookup, keeping the `FORMATTER_OWNED_ATTRIBUTES` clause since `message` is not on a fresh record, with a regression test per key. No caller in `pipelex/` passes `fields=` yet; the exposure is a consumer forwarding a mapping whose keys it does not control, a kajson-encoded object among them.
- **A circular-reference content raises `ValueError` out of the facade** (*verified*, code-review). `_render_content` hands a `dict` or `list` to the `purify_json*` helpers, which catch `TypeError` only, and `json.dumps` raises `ValueError` on a cycle. Byte-identical on dev, where the raise is unconditional; the branch's docstring in `log_fields.py` is what promises a log call never raises. The fix is a guard on the log path, a `ValueError` caught beside the `TypeError` in the helpers or a fallback rendering in `_render_content`, and the promise narrowed if neither lands.
- **The changelog bullet is four sentences against the rule's three** (*verified*, code-review). The closing cross-reference is its own sentence since the branch's first commit; it folds into the previous one when the bullet is next touched.
- **A process entry cannot clear an inherited identifier** (*unverified*, cubic and code-review). `LogContext.merged_with` reads `None` as inherit, so `PipeRun.run` invoked inside an existing binding keeps the ambient `pipe_run_id` until `live_run_pipe` mints one; `request_id` and `pipeline_run_id` are always set by a run and cannot leak. No call site runs `PipeRun.run` inside a binding today; a replace-or-clear semantics on `bind_log_context` is the fix if an embedder or a nested run ever does.
- **`fields` values ride by reference while `data` is a snapshot** (*unverified*, code-review). A field given a live `dict` or `list` reads whatever the caller did to it by the time a queued sink serializes it. `docs/tools/logging.md` advises JSON-ready values as guidance rather than guarantee; whether the sink snapshots on emit or the contract states the requirement is the sink member's call.
- **`data` is re-parsed on every structured call before any sink reads it** (*unverified*, code-review). `json.loads(rendered)` in `_render_content` builds a second object graph per record at an enabled level; a lazy attribute or a sink-side parse is the sink member's design choice.
- **The reserved-name comment claims `ErrorReport` carries the identifiers** (*unverified*, code-review). The comment above the constants in `pipelex/tools/log/log_context.py` says a record and the `ErrorReport` agree on the key; `ErrorReport` carries none of the three, and the only `request_id` reachable from it is the provider's, a different identifier. The comment should name the run result and the payload fields alone.
- **The deleted gateway tests were the only mechanical guard on the no-log-on-load-path invariant** (*unverified*, code-review). Round 1 removed two tests that asserted the absence of a `RuntimeError` that no longer exists; the invariant they stood beside, that nothing logs on the gateway load path because a pre-configure line lands on stderr unformatted, is now prose only in `gateway_config.py`. A test that asserts no record is emitted on that path restores the guard.
- **Nits** (*unverified*, code-review): `pipe_run.py` still interpolates `pipeline_run_id` into five message strings while the same value rides the record as a field; `test_log_fields.py` hardcodes the DEV level as a number beside an imported constant; `bedrock_client_boto3.py` uses `run_in_executor`, which does not propagate contextvars, so a log call from that thread would lose the identifiers, though only a boto3 call runs there.

## L-260916-a1dbd5, round 4 (bar freeze)

The bar changed no code. Every reviewer raised the class-owned attribute collision again, and code-review the circular-reference raise, the console flag and the round-3 nits; those keep their entries above. What follows is new.

- **A filter attached to the `pipelex` logger no longer sees the records** (*unverified*, cubic). Python consults a logger's filters only for records originating on that logger, never while a descendant's record propagates, so a filter an integration attached to `logging.getLogger("pipelex")` stops running now that records originate on module loggers. No repository in the workspace attaches one. The changelog's "Loggers are named by module" bullet says a filter keyed on the bare package name must key on the prefix, which does not help a filter attached to the logger: such a filter must move to the handler, and the bullet and `docs/tools/logging.md` should say so.
- **A dict with a non-string key raises `TypeError` out of the facade** (*unverified*, code-review). `json.dumps` applies its `default` to values, not keys, so `log.info({(1, 2): "a"})` raises from the `purify_json*` fallback too. Byte-identical on dev; the same guard as the circular-reference entry above covers it.
- **The logging doc overstates what `data` is** (*unverified*, code-review). The "Structured content" section says any other object is carried as the dictionary or list its serialization produces; a scalar content lands as itself, an object that defeats both `json` and `kajson` lands as the `purify_json` warning wrapper, and a `float("nan")` survives the `json.loads` round trip as a float standard JSON cannot re-emit. A sink author iterating `record.data` meets a scalar. The sink member decides the shape and the page follows.
- **The caller-info test fixture's teardown is process-global** (*unverified*, code-review). `log_with_caller_info` in `tests/unit/pipelex/tools/test_log_caller_info.py` calls `Log.reset()`, which removes and closes every root-logger handler and calls `logging.shutdown()`. `Log.reset()` is pre-existing; the unit suite is green under random and fixed ordering, so this is a latent isolation hazard rather than a failure. A fixture that removes only the handler it added would remove the hazard.
- **The dev-side caller-info fix is filed under Changed** (*unverified*, code-review). `FUNC_MODULE` and `FUNC_MODULE_LINE` raised `KeyError: 'module'` on dev at the first log line after boot; the branch passes the module and covers it in `test_log_caller_info.py`, and the changelog folds that into the logger-naming bullet rather than a Fixed entry.
- **Out of scope, unverified: seven findings on the `main..dev` delta** (code-review, whose skill diffed `main...HEAD`). Files this branch does not touch, listed here so they can be chased and never as this branch's: `pipelex/pipeline/input_normalizer.py:232` (`HttpUrl`'s length cap rejects long signed URLs); `pipelex/tracing/ndjson_event_log.py:163` and `pipelex/tracing/dynamodb_event_log.py:170` (corrupt-vs-refused decided without checking `loc == ()`); `pipelex/tracing/ndjson_event_log.py:164` (raw `validation_error` interpolation leaks traced content); `pipelex/cli/commands/graph_cmd.py:59` (`json_invalid` misreported as a stale-file error); `pipelex/graph/mermaidflow/templates/_interactive_scripts.js.jinja2:275` (the JSON tab falls back without consulting `disabled`); `pipelex/tools/misc/http_utils.py:22` (whitespace accepted against the documented rule); `pipelex/runtime_hub.py:210` (`reset_boot_state` reverts the agent CLI's SILENT printer).

## L-260916-aa6e58, round 1 (bar open)

The pass fixed the nine confirmed findings: the OTLP handler's re-entrancy filter and its teardown guard, the mixed-type sequence, the JSON sink's non-finite floats and its reserved keys, the holding handoff, the console formatter's prefix under `exc_info`, the doctor's fallback sink and the migration entry's account of what a poor-mode or silenced file loses. The refuted finding (the override and kit configs carrying `sink` without `[runtime.log.otlp]`) was rejected: the kit carries the user-facing subset by design and the deep merge supplies the rest. What follows was read as real and left.

- **The held-record window spans the remote config fetch** (*unverified*, code-review). Between `Log.configure` and `log.install_sink` in `RuntimeBoot.setup`, the registrar is built and the remote config may be fetched, so a boot that logs verbosely on that path holds those records in memory up to the holding handler's capacity; beyond it the oldest are dropped. The capacity is generous for a boot and the window is documented in `docs/under-the-hood/log-sink-plugins.md`; a sink installed earlier would need the registrar earlier, which is the boot order's decision and not this member's.
- **The JSON sink binds its stream at factory time** (*unverified*, code-review). `pipelex/tools/log/json_log_sink.py` resolves `sys.stdout` or `sys.stderr` when the factory runs, so a consumer that swaps `sys.stderr` after boot, pytest's capture among them, keeps writing to the stream the sink captured. Resolving the stream per emit would follow the swap at the cost of a lookup per line; deliberate for now, and the test module patches the stream before installing.
- **A `console_log_target = "file"` raises a bare `ValueError`** (*unverified*, code-review, pre-existing). `stream_for_target` in `pipelex/tools/log/log_sink.py` inherits dev's handling of the third target value, which has no file path to open. The enum member predates this branch and no caller sets it; retiring the member or giving it a path is a config change of its own.
- **`redirect_to_stderr` imports Rich unguarded** (*unverified*, code-review). A server install without the CLI extra fails on that path. L-260916-fe7969 moves Rich behind the extra and adds the import guard, and the note on it carries this.
- **The Rich handler raises `MarkupError` out of a log call** (*verified by the round-1 verifier*, pre-existing). With `is_markup_enabled = true`, `RichHandler.emit` renders the message outside its own `try`, so a message whose text reads as a stray closing tag, `[/pipe]` for one, raises out of `log.info`. The holding drain now contains it for held records; a live record still raises. Dev's Rich mode did the same. A console handler subclass whose `emit` routes the error to `handleError` is the fix, owned by the console sink's next pass or by L-260916-fe7969 when it reworks the Rich path.
- **The doctor duplicates the log-sink composition root** (*unverified*, cubic). `doctor_cmd.py` performs discovery, registry construction, selection and installation that `RuntimeBoot.setup` also performs, and the fallback added this round widens the difference. Extracting one function both call is a refactor below this bar; it is worth doing before a third caller appears.
- **The migration deletes `log_mode` and `is_console_logging_enabled` without translating them** (*verified by the round-1 verifier*, cubic). A `remap_value` onto `sink` is refused by the ledger check because `sink` is an open token, an intermediate schema for a split into a safe and an unsafe entry has no golden a model ever had, and an `unsafe` entry blocks every full copy of an older base file at its defaults for the sake of the few that chose `poor` or `false`. The entry stays `safe`; what a person running `pipelex migrate` sees is the step's title, so the title names what a poor-mode file then sets by hand, and the description and guidance say what the deletion undoes for both keys. The engine gap underneath, that a safe entry's guidance is rendered nowhere, is L-260916-5d142f.
- **The migration coverage gate is blind to a deleted enum key** (*verified by the round-1 verifier*, tooling). `_check_enum_members_remapped` in `pipelex/migration/coverage.py` continues when a path does not survive into the new schema, which is how a `delete_key` on `log_mode` passed the gate. Filed as L-260916-0e1435.
