Per-request Gateway key

Give every hosted run the Portkey key of the tenant who asked for it — on the runner or on any Temporal worker — instead of the one key the whole environment shares today.

The idea in one breath

The platform stamps an opaque gateway_key_ref on each run it dispatches. The runtime carries it through Temporal on JobMetadata — a reference, never key material. A small hosted resolver plugin turns it into the tenant's Portkey key on whichever worker runs the inference call. Nothing is cached per credential; the shared SDK clients stay exactly as they are. Portkey then attributes usage, budgets and rate limits per tenant with no work on our side.

API Gatewayauthorizer; /v1/* → platform. Unchanged.
platformstamps the reference from the authenticated org/user, on both runner hops
runneropaque field → JobMetadata
Temporalrides on every workflow and activity payload
workerresolver plugin → tenant's key, per call, TTL-cached
Portkeyx-portkey-api-key = that tenant's key

Where pipelex-server does its work. Everything else is the runtime's job (§2).

What pipelex-server builds

Stamp the referenceplatform/
  • Run dispatch: payload["gateway_key_ref"] in services/pipeline_runner.py, the same way the org-scoped storage plan carries storage_scope.
  • Tooling proxy: the platform sets X-Gateway-Key-Ref on /build/* hops in runner_proxy.py; a client-supplied value is never passed through.
  • Small matching change in public pipelex-api: a body field plus one trusted-proxy header, both opaque, threaded to JobMetadata. No API Gateway change. (§4.1)
Resolve itgateway-keys/ (new member)
  • A plugin lib like temporal/ or transport/: pins pipelex==X.Y.Z, installed by both api-hosted/ and worker/, contributes a GatewayKeyResolver via entry point.
  • Reads the tenant's key row with boto3 directly (neither image installs pipelex-shared). Never provisions. Never logs the key.
  • One process-scoped cache keyed on the reference: positive TTL, shorter negative TTL, LRU cap. The positive TTL is the revocation SLA. On any failure it raises; the fallback decision belongs to the runtime's policy switch. (§4.2)
Provision keysplatform/ + order webhook
  • Per-user Portkey keys already exist (provision_gateway_key, race-safe, shared) and now carry paid top-up credit. Provisioning stays where the Portkey admin credential is.
  • Because the platform fronts dispatch, it can provision-on-dispatch, so a fresh tenant never hits fail-closed. Which row holds the key depends on §6.1. (§4.3)
Config, IAM, deployapi-hosted/ worker/ infra/
  • Fail-closed missing-reference policy in both images' .pipelex/pipelex_{env}.toml; local stack keeps the fallback.
  • Read grant on worker_task_role and api_task_role for the key row (plus kms:Decrypt if the plaintext moves under envelope encryption). Every worker needs it — the shared queue can't route tenants.
  • Table env var on runner and worker; version bumps across api-hosted, worker, platform and the new member — make deploy-plan must select all three deployables. (§4.4)

Built against — the runtime contract

  • JobMetadata.gateway_key_ref: str | None — opaque, printable-ASCII, bounded; travels for free through every Temporal hop.
  • GatewayKeyResolver.resolve(gateway_key_ref) -> str — plugin-contributed, consulted only by the gateway plugin, inside activity execution. Default returns the boot key.
  • A missing-reference policy switch: fall back to the boot key (OSS default) or fail the call (hosted).
  • All six gateway handles honour the resolved key per request; a retry re-resolves on whichever worker takes it. The hosted plane re-implements none of this. (§2)

Two corrections to the design doc

The runner never sees X-Org-Id. Every /v1/* route goes to the platform, which handles /start and /execute itself and proxies the tooling routes, forwarding only X-User-Id. api-hosted/ has no source of its own. So the reference is stamped by the platform, one hop later than the design assumed, and API Gateway is untouched.

Per-tenant Portkey keys already exist — per user, and money-bearing. The credit top-up work that just merged lands purchased credit on the user's own Portkey key. That makes the "user or org?" question a product decision (see §6.1), not the technical afterthought the design treated it as.

Decide before starting

  1. User or organization as the v1 reference?Is hosted usage meant to consume the credit a user buys? Yes → user id, existing key, nothing new to provision. No → org id, a new per-org key beside the per-user one. The resolver is indifferent; the product is not.Product call
  2. Where the plaintext lives.On the tenant's DynamoDB row as today, or behind envelope encryption now (which turns the read grant into a fleet-wide KMS decrypt grant).Recommend: row for v1
  3. Cache numbers.Positive TTL, negative TTL, entry cap. The positive TTL is the revocation SLA — write it down as one.Needs numbers
  4. Fail-closed in the hosted plane?Only shippable once both platform hops stamp and the legacy direct-to-runner routes are gone or accepted as failing.Recommend: yes
  5. Ride the org-scoped storage change?It threads storage_scope through the same sites (pipelex, pipelex-api, platform, transport, temporal). Doing both at once saves a second runner/worker rebuild and a second pipelex version move.Recommend: together

Done when

  • Two tenants running the same method on the same worker fleet show two distinct Portkey attributions, and no run touched PIPELEX_GATEWAY_API_KEY.
  • A run that reaches the runner without a reference fails at the inference call, on the execute path and on the build path.
  • Revoking a tenant's key stops that tenant's runs within the stated TTL on every worker.
  • The local stack still runs end to end for a developer holding only the shared key.
Not touched by this work: SdkClientRegistry, InferenceManager, ModelHandle, the instructor wrappers, any Temporal workflow, activity or converter, any non-gateway backend, tenant-supplied keys.
