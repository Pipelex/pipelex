Pull Request Story

Signature-Based Validation

A new PipeSignature pipe type lets authors and AI agents sketch a whole pipeline top-down — declaring each pipe's contract before writing its implementation — and still validate it at every step.

branch · feature/Validate-with-signatures 7 phases · strict TDD new pipe type across 3 layers ~1,800 LOC of tests

Why we did this

Validating a bundle dry-runs every pipe with mock inputs. Dry-run requires that every sub-pipe of every controller already exists as a fully-defined pipe. There was simply no way to validate a half-built pipeline.

That blocks the most natural way to build a pipeline: sketch the orchestration first, fill in the operators one at a time. It blocks AI agents especially — they want to lay out a PipeSequence of five steps, then implement step 1, validate, implement step 2, validate, and so on. Until now, the bundle wouldn't even load for validation until all five were done.

The gap

A controller referencing a not-yet-written pipe fails at dry-run with a generic "pipe not found" — indistinguishable from a typo. There was no first-class way to say "this pipe is a deliberate placeholder; here is its contract; I'll implement it later."

The idea — a contract-only pipe

A PipeSignature is a contract: inputs, output, description — and no implementation. It is a first-class pipe type that any pipe in a bundle can reference as a placeholder.

a PipeSignature in a .mthds file
[pipe.summarize_extracted]
type = "PipeSignature"
description = "Summarize extracted text (contract only)."
inputs = { extracted = "Text" }
output = "Summary"

Three use cases drove the design:

01

Agents building iteratively

Sketch the orchestration with signatures, fill implementations one pipe at a time, validate at every step.

02

Contract bundles

Library authors publish a bundle of signatures for downstream teams to implement against.

03

Safe refactors

Stub a pipe with its prior contract while the body is rewritten — the rest of the graph still validates.

Two validation modes

This is the central design decision. Validation has two distinct purposes, so it gets two distinct modes — selected by one flag, --allow-signatures.

STRICT · default

"Ready to ship"

Fails fast if any pipe reachable from the target is a PipeSignature. CI gates, release checks, and production deploys must reject half-built bundles. Raises SignaturesNotAllowedError listing every signature and the controller chain that reached it.

LENIENT · --allow-signatures

"Still authoring"

Accepts signatures. They participate in dry-run by minting a mock output from their declared contract. This is the agent / authoring loop — the agent CLI's validate surfaces the flag for exactly this use.

The two modes are complementary with a third line of defense — live-run enforcement. Even if strict validation is skipped, executing a signature for real raises PipeSignatureNotExecutableError. A half-built pipeline can never silently run on mock data.

The design in one picture

A signature is a real pipe type, mirrored across all three layers of the Pipelex stack — the same spec → blueprint → runtime path every other pipe takes. No discriminator machinery changed; the factory lookup convention (f"{pipe_type}Factory") just needed one new registration.

A signature is neither an operator (no inference) nor a controller (no sub-pipe orchestration) — it earns its own PipeCategory.

A third category is a feature, not overhead: Pipelex enums are matched exhaustively with no case _ default, so the linter forces every match-case in the codebase to acknowledge the new value. Nothing that needs to know about signatures can silently forget them.

How strict mode finds signatures

Before any dry-run starts, strict mode walks the dependency graph from the target pipe and collects every reachable signature. The walk is a pair of free functions in pipe_signature/signature_walk.py — collect_signature_refs(pipe) and its companion collect_signature_paths(pipe), which records the controller chain that reached each signature so the error message is actionable.

The walk is cycle-safe (visited-set keyed by qualified pipe_ref) and deterministic (sorted dependency iteration), so error messages are stable.
A real import-cycle constraint

The walk needs to resolve dependency codes to pipe objects via pipelex.hub.get_optional_pipe. That import cannot live in pipe_abstract — the cycle pipe_abstract → hub → library → pipe_library → pipe_abstract is real and breaks at runtime, not just under pyright. So the walk is not a method on PipeAbstract: it lives as free functions in pipe_signature/signature_walk.py, a module downstream of hub, where importing get_optional_pipe is free of any cycle. PipeAbstract keeps only pipe_dependencies() and is_signature — pure local data the walk reads.

+             raise SignaturesNotAllowedError(
+                 offending_pipe_refs=offending,
+                 signature_refs=signature_refs,
+                 dep_paths=collect_signature_paths(pipe=pipe),
+             )
      try:
          ...  # existing dry-run logic unchanged

3 — The runtime's two paths. The whole point of the type is in these two methods: dry-run mints a contract-shaped mock; live-run refuses.

pipelex/pipe_signature/pipe_signature.py
  async def _live_run_pipe(self, ...) -> PipeOutput:
+     raise PipeSignatureNotExecutableError(pipe_ref=self.pipe_ref)

  async def _dry_run_pipe(self, ..., output_name=None, ...) -> PipeOutput:
+     mock_name = output_name or self.code
+     typed_named = convert_stuff_spec_to_typed_named(stuff_spec=self.output, name=mock_name)
+     mock_stuff = WorkingMemoryFactory.make_mock_stuff(typed_named_stuff_spec=typed_named)
+     working_memory.set_new_main_stuff(stuff=mock_stuff, name=mock_name)
+     return PipeOutput(working_memory=working_memory, ...)

No content generator, no LLM-mock — just make_mock_stuff, a helper extracted from the existing make_mock_inputs so the per-stuff mock logic is shared rather than duplicated.

The subtle one — aggregation order

dry_run_pipes does a pre-pass over the whole batch so the user sees every offending signature in one error, not just the first. The first cut aggregated dep-paths "first wins" — but when the signature pipe itself was iterated before its controller, that recorded an empty chain and never replaced it. Fixed: the aggregator keeps the longest known dep chain, so the message always shows the most informative path.

CLI surface

  • pipelex validate pipe <code> [--allow-signatures] and validate bundle <path> [--allow-signatures] — strict by default.
  • pipelex validate --all — strict; iterates non-signature pipes only (orphan signatures aren't flagged — they're deliberate placeholders).
  • The agent CLI's validate subcommands carry the same flag — strict by default, so CI behaviour is consistent across both CLIs.
  • In lenient mode the summary line gains a suffix in-place: Successfully validated bundle 'X' (2 signatures) — empty when no signature was involved, so finished bundles read naturally.
  • Strict-mode failures render under an "Unimplemented Signatures" heading showing the dep chain, via error_handlers.py.

Merge gate — do not skip

One item is open by design. The bundled plxt JSON Schema (shipped from vscode-pipelex) does not yet know about type = "PipeSignature". On this branch, .pipelex/plxt.toml declares a [[rule]] block pointing **/*.mthds validation at the locally-regenerated derived/mthds_schema.json.

Reviewers — read this

That [[rule]] block is the intended, correct configuration on this branch — not a workaround to flag. The local schema is the only one that accurately describes the runtime change here. plxt lint is green against it.

At merge time (tracked as Phase 7.4 in the archived plan):

  1. In vscode-pipelex: regenerate the bundled MTHDS schema so PipeSignature is a valid pipe type; cut a plxt / extension release.
  2. In this repo, in the merge commit: remove the [[rule]] block from .pipelex/plxt.toml so the bundled schema takes over again.
  3. Re-run make agent-check with the new plxt and no local rule — plxt lint must accept the signature fixtures against the bundled schema. That green is the actual ship-readiness signal.

Explicit non-goals

  • Signature concepts — concept stubs analogous to pipe signatures. Bigger design, separate plan.
  • signature_for-driven mocks — e.g. signature_for = "PipeImgGen" minting a real ImageContent URL. The field is captured today as a tooling hint only; specialization is deferred.
  • Bundle migration — existing bundles are untouched. Authors opt in.
  • Parallel [signature.foo] TOML table — possible syntactic sugar later, not a structural alternative.
