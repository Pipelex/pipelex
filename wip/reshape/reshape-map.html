The Configuration Reshape

Twenty-six things live at the root of PipelexConfig today under three different organizing principles. This is what they become, why, and in what order the migration touches them.

ledger entry pipelex-config@2 base dev @ 052b9df06 ops 37 normative source wip/migrator-3/reshape.md

What this changes

One address change, no value changes

The reshape rewrites PipelexConfig and the TOML it validates so the root carries one scheme — the layers the code already has — instead of the five unrelated entries it carries now. Every setting keeps its value. Only its address moves.

The axis is not invented for the occasion. docs/contribute/hub-layering.md already names a kernel layer (brokered by runtime_hub) and an interpreter layer (brokered by interpreter_hub), and pipelex/kernel/ already holds operator-execution semantics callable on a RuntimeBoot-only process. The configuration is the last surface that still says “one blob” while the code says two layers plus an inference seam.

It ships as a Migrator ledger entry, so every user’s ~/.pipelex/pipelex.toml migrates in place rather than breaking. The _config suffix is dropped in the same pass at every depth, because each read site is touched exactly once either way.

Why these three names

The layer axis already exists in the code

Ruling R3 placed the four ambiguous sections by measuring which layer actually reads them, and the census settled every one. A read downward — the interpreter reading kernel configuration — is permitted, so it never forces a section upward.

The three deletions

Two of these were never configuration at all — they were process state and a boot argument that happened to live on the config object. Neither is set in any TOML anywhere in the workspace, so both delete_key ops skip on every real file and exist only to account for a schema path.

session_id
Process state on the config object since the initial commit, and extra="forbid" let a user pin it from TOML by accident. Nothing in pipelex/pipelex/ reads it. Its one chain ends at a Temporal search attribute that is disabled in every deployed environment and queried by nothing. The plugin will mint its own per-process id; JobMetadata.session_id stays as its wire carrier.
plugins.boot_orchestrator
Set in no TOML anywhere. RuntimeBoot.setup writes the argument into the config object and the plugin gate reads it straight back — the config was being used as a side channel. It becomes boot-scoped state on RuntimeHub with an accessor (the precedent is is_dry_run_forced) plus a build_registrar parameter.
[migration]
One field, migration_maps, whose only consumer annotated validation errors with renaming hints. Migrator’s own ledger supersedes it. The .mthds renaming hints are an accepted loss, recorded, until the language-surface project restores them.

The file itself

Two tables are interleaved today

The packaged defaults file is physically out of order: [pipelex] is split across three spans and [migration] across two, which is what makes both resolve to a tomlkit OutOfOrderTableProxy. Ruling R6 rewrites the file in order — a content edit of a reference document, not a schema change, since the transform comparator is path-based.

The ledger entry

37 ops, and the order is load-bearing

Children move out of [pipelex] before [pipelex] is renamed. [cogt] is renamed before anything moves into [inference]. A parent is renamed before the suffix renames inside it, so a root rename keeps every child in place in the user’s file. A delete_key whose source sits inside a table that later moves comes first, so its source is still a schema-1 path. Whole-table deletions go last.

The consequence nobody had written down

Because the ops chain, a nested rename under a moved parent always has an intermediate address at one end — whichever way you order it. Rename the child first and the destination is intermediate; move the parent first and the source is.

What catches a mistake

A 37-op entry written by hand needs more than review. Three checks read it from different ends, and each is red at authoring time on the branch — not at a user’s boot.

Coverage
Every removed path is the source of some op, and every destination is an added path of fingerprint@2. Catches an unaccounted removal and a misspelled destination with the same test — they are the same defect seen from either end.
Convergence
Replays the entry over the new packaged defaults and the new kit template. It must apply nothing. A migration that still finds work to do on an already-migrated file is not finished.
Transform golden
Applies the entry to defaults@1 and demands exactly the paths of defaults@2. Renaming pipelex before its runtime children moved out, or deleting boot_orchestrator after plugins moved, is red here.
The type checker
Field names equal TOML keys with no aliases, so every one of the ~145 package read sites that is missed is a pyright error. The two shapes it cannot see — raw-dict TOML reads and inline-TOML test fixtures — get a hand pass.

How it ships

The reshape cannot land alone

A user whose ~/.pipelex/pipelex.toml is in the old shape needs two things to exist before the new shape reaches PyPI: a boot that tolerates the old file with a warning instead of failing, and a pipelex migrate that rewrites it. Both are Migrator Phase 3. Releases have run every one to three days lately, so “it will not be cut into a release” is not a plan.

Enforcement is by ordering, plus two tripwires: this branch’s pull request is titled MERGE AFTER Migrator Phase 3 — …, and Phase 3 adds a step to /release that refuses a moved schema without its ledger entry.
