### What Phase 1 taught Phase 2

Read this before starting 2.1. **Moving code has consequences no compiler reports**, and Phase 1 hit four classes of them. Two failed a gate loudly; two are silent and only one of those is caught by CI at all.

**Caught by a gate (will fail your build):**

1. **Dead subject grants.** `subject_grants.toml` still granted positional subjects for defs the move deleted (`pipe_operators/llm/helpers.py::get_output_structure_prompt`) or relocated (the `LLMPromptBlueprint._extract_direct_*` methods). The convention's staleness check is *symmetric* — a grant whose def moved or vanished hard-fails until the registry is cleaned. Remove rather than re-grant: kernel replacements are fully keyword-only, the package's stated zero-grants doctrine. **Sweep the grants for every operator you move.**
2. **Dead paths in `.test_durations`.** Moved test modules leave the committed shard-balancing artifact pointing at their old home, and `tests/unit/repo/test_test_durations_paths.py` catches it. Rewrite the node ids' path prefix rather than regenerating: the tests moved verbatim, so their recorded durations are still accurate, and `make store-test-durations` would churn every timing in the file for no gain. New modules simply have no entry, which pytest-split treats as average duration.

**Silent (nothing tells you):**

3. **Under-the-hood docs naming moved files.** Phase 1 broke a file path in `docs/under-the-hood/image-handling-in-llm-prompts.md` and nothing noticed — no drift contract has a trigger glob over `pipelex/pipe_operators/**` or `pipelex/kernel/**`, and `mkdocs build --strict` does not validate inline code spans in a table. Grep `docs/` for every path you move. Already known for Phase 2: `docs/under-the-hood/dry-run-mock-generation.md` names `pipe_operators/compose/structured_content_composer.py`, a task-2.4 target, and `docs/under-the-hood/architecture-overview.md` still presents `pipe_operators/` as the sole home of operator behavior. Both settled in Phase 2: the composer did not move, so its reference is still accurate, and the architecture overview now states the split. The Phase-3 equivalent is task 3.4's kernel page, which should be written against these two rather than beside them.
4. **`docs/errors/` pages carry the defining module path.** The generator emits ``| Defined in | `<module>` |`` onto each page, so moving a `PipelexError` subclass makes its committed page stale — and `make generate-error-pages` runs in neither `make check` nor CI. Phase 1 escaped this only by luck: `LLMPromptBlueprintValueError` and its replacement `PromptContentError` are bare `ValueError`s, so `tests/data/errors/error_identity.txt` never moved. Phase 2 was predicted to move error classes that *are* `PipelexError`s (search, img-gen, compose, extract). **It moved none** — each operator's error family stayed with the interpreter-side code that raises it, because the kernel ops raise the same cogt-level errors the moved code raised and the operators rewrap as they always did. So the two chores this item names went unexercised and are still owed by whoever first moves a `PipelexError` into `pipelex/kernel/`: regenerate the pages, and note that the generator's `_SUBSYSTEM_SECTIONS` has no `kernel` key, so a moved error falls through to the `platform-and-tooling` fallback under a humanized "Kernel" heading instead of "Execution & runtime".

**Two traps that are not move-consequences:**

5. **The execution-data coverage test cannot see module-level functions.** `tests/unit/pipelex/pipe_machinery/test_execution_data_coverage.py` walks only `self.<method>(...)` call chains to find each pipe's `_register_execution_data` call. A kernel function is invisible to it. Phase 1 survived because that call stayed inline in `pipe_llm.py`; **every Phase-2 operator must keep `_register_execution_data` on its own `self.*` chain**, or the test fails for that pipe.
6. **Every operator has tracer intermediates, and Phase 2's task list does not mention result envelopes.** The typed result envelope (`LlmTextResult`/`LlmObjectResult`/`StructuringPath`) was Phase 1's real design work beyond the ops, and each remaining operator registers its own execution data with the same kind of intermediates. Decide per operator whether it gets an envelope or the interpreter keeps computing them — but decide deliberately, because "the tracer rides the same functions" is the property that stops the two callers drifting.

## Goal

Pull operator-execution semantics out of the interpreter's operator classes into shared, importable kernel functions under a new public `pipelex/kernel/` subpackage, and re-point the interpreter onto them — **zero behavior change**. Today, what a `PipeLLM` step actually *does* (deck resolution, templating-style derivation, prompt assembly, generation, memory write-back) is only reachable through a fully booted interpreter with a loaded library. After this refactor, operator semantics have **one implementation with multiple callers**: the interpreter's operators, and any programmatic caller — SDK-style embedding, hosts that boot only the runtime layer — invoking them directly on a `RuntimeBoot`-only process with zero `.mthds` loaded.

This completes the runtime/interpreter layering arc: the hub split (#1062/#1064), layer placement (#1071), concept purity (#1072), the boot split that created `RuntimeBoot` (#1073), the templating-style threading fix (#1074), and the concrete-class object path (#1076). It is a pure refactor, valuable on its own: single-sourced operator semantics are what prevent two callers from drifting apart.

## Doctrine

- **Layering.** The caller-facing kernel API is hub-free: an explicit `PipelexKernel` object and explicit arguments, never an ambient lookup. Kernel *internals* may use `pipelex.runtime_hub` — never `pipelex.interpreter_hub`. This is a mechanically enforced rule (the hub-layering guard plus the runtime-layer import-closure test), but #1071's history shows the guard does not hold the line "for free" — see the four sub-tasks under 0.1, which exist because each one closes a hole that episode demonstrated: an *undeclared* package is unpoliced rather than neutral (both guard rules filter through the layer declaration, so omission makes the guard quieter); a declaration with no test pinning it is a comment; a **cross-layer re-export aggregate defeats the guard entirely** (vendor adapters once pulled the interpreter into a declared-clean runtime package by importing from `pipelex.exceptions` instead of the definition site — a module that re-exports across layers is a layer boundary with the sign filed off; that hole is the one now closed mechanically tree-wide, and the kernel inherits the coverage by being declared); and a function-local import is invisible to the static graph and the closure test at once.
- **Calls are activity-shaped.** Explicit, serializable-leaning inputs and outputs; `WorkingMemory` threaded explicitly (taken and returned); no hidden shared state. This is a design constraint, not a deliverable: it keeps a future Temporal-activity wrapping a re-decoration rather than a rewrite. The memory contract, stated so both caller classes read the same thing: a kernel call may mutate the memory it is passed and returns it — callers must treat the returned memory as the result and must not rely on aliasing of the argument, because inline execution aliases the two today and a serialization boundary will not.
- **Functions carry the semantics; the class is a façade.** Module-level kernel functions hold the shared implementation. The `PipelexKernel` class is a thin ergonomic façade over them, holding the per-run state a caller would otherwise thread through every call. The interpreter's operators call the functions directly.
- **The kernel API is fully keyword-only — zero subject grants.** The governing bar, stricter than the general rubric in [`docs/contribute/keyword-only-arguments.md`](../../docs/contribute/keyword-only-arguments.md): only the first parameter may be positional, and strictly only when it is obviously the subject — named in the function, or as unmistakable. Nothing in the kernel clears that bar: `llm_text` and `llm_object` name what they *produce*, and `memory` is threaded state (taken and returned), not the operand. So `pipelex/kernel/` records no entries in `subject_grants.toml`, every call site names every argument, and `make fix-keyword-only` mechanically produces exactly this form — there is no ordering trap. Any future kernel def that wants a positional subject must clear the stated bar in review first, not in the registry.
- **Boot contract: `RuntimeBoot.make()`** ([`pipelex/runtime_boot.py`](../../pipelex/runtime_boot.py)). Every kernel call must be servable on the runtime-only composition root, with no interpreter constructed and no library loaded. The import-closure test guards this structurally; a live smoke run proves it dynamically.
- **Zero behavior change.** The full `make agent-test` suite is the gate at every checkpoint — no *behavioral* test rewrites. Import repoints, module moves and `mocker.patch` target updates are expected and are not a red flag: Phase 1 repointed several test modules' imports, moved two, and rewrote patch targets in `test_cogt_run_params_carrier.py` when the code they patch moved.

## Target caller experience

The sketch below is the API shape to preserve while the internals get extracted for real out of `pipe_llm.py` (which is where the deck chain, style derivation, and prompt assembly currently live). Every parameter is keyword-only, including `memory`. Two contracts the sketch elides for brevity, stated here because they are load-bearing: `user` and `system` are prompt *templates* rendered against `memory` inside the kernel — template references are how images and documents enter the prompt (task 1.3's assembly functions do the rendering) — and the return value is a small typed result carrying the updated memory plus the rendered prompts, the resolved model setting, and the structuring path taken, because the interpreter's execution-graph tracer consumes those intermediates after generation and recomputing them outside the kernel would mean a second assembly path. Expect the signatures to grow explicit keyword parameters for setting overrides and output multiplicity as tasks 1.1–1.4 extract the real thing; the shape that must survive is fully-named arguments over explicit state. One limit the sketch does not show, now that Phase 1 has landed: **the façade methods carry no image or document references at all** — both hardcode `LlmPromptContent.make_from_text(...)`, and a caller needing references drops to `run_llm_text` / `run_llm_object` with an `LlmPromptContent` it builds itself. Phase 2 brings image-bearing operators (2.1 `PipeExtract`, 2.2 `PipeImgGen`), so decide there whether `PipelexKernel` grows reference-carrying parameters or stays a deliberately text-only convenience. **Decided in Phase 2 — it stays LLM-only; see Decisions.** The sketch above already reflects one growth the plan did not anticipate: folding the parity-gaps track in widened `llm_text` to take an optional `concept` and `output_class`, and made `model` optional too, so the façade can express what the op beneath it always could — see the 2.1 entry in that track and the `llm_text` docstring for why each of the three has to be reachable.

```python
class PipelexKernel:
    """Façade over the module-level kernel ops; holds per-run state."""

    def __init__(self, *, job_metadata: JobMetadata, cogt_run_params: CogtRunParams): ...

    @classmethod
    def make(cls, *, run_mode: PipeRunMode = PipeRunMode.LIVE, user_id: str) -> "PipelexKernel": ...

    async def llm_text(
        self,
        *,
        memory: WorkingMemory,
        model: LLMModelChoice | None = None,
        user: str,
        system: str | None = None,
        concept: Concept | None = None,
        output_class: type[StuffContent] | None = None,
        result: str,
    ) -> LlmTextResult:
        """The semantics of a PipeLLM step with a Text output.

        `user`/`system` are templates rendered against `memory`; the result
        carries the returned memory plus the rendered prompts and resolved
        setting for the caller's tracing needs.
        """

    async def llm_object(
        self,
        *,
        memory: WorkingMemory,
        output_class: type[StuffContentT],
        concept: Concept,
        model: LLMModelChoice,
        user: str,
        system: str | None = None,
        structure_prompt: str | None = None,
        result: str,
        is_multiple_output: bool = False,
        fixed_nb_output: int | None = None,
    ) -> LlmObjectResult:
        """The semantics of a PipeLLM step with a structured output.

        The concrete pydantic class is handed over directly — no registry lookup,
        and no runtime schema-to-class reconstruction, because the class exists.
        The structure prompt is derived from `output_class` by default (same
        config template as today); pass `structure_prompt` to override it.
        """
```

- [x] 0.2 Kernel construction shape: `PipelexKernel.make()` mints `JobMetadata` + `CogtRunParams`; decide what the instance holds vs what stays per-call. Two constraints on that decision are settled now. First, the instance holds only identity and run-scoped state (the run-level `JobMetadata`, the `CogtRunParams`); anything derived from config or the model deck — resolved settings, prompting style — is computed per-call and never cached on the instance, exactly the deliberate per-run derivation `pipe_llm.py` documents today, because cached derived state is hidden shared state and breaks per-call `run_mode` variation. Second, the run-level metadata the instance holds is not what a step runs under: each call mints a per-step copy via `copy_with_update` (per-step `pipe_run_id`), matching the interpreter's pass-down-a-modified-copy pattern, so trace and usage attribution stay per-step.

  The original task text, kept because its analysis of the seam is what the deviation rests on: `PipeFunc` → kernel function-call op over the **`PipeFuncExecutorProtocol` seam**, not a bare registry lookup. The executor is pluggable — `run_pipe_func` (live objects) and `run_pipe_func_transported` (serialized request/response via `pipe_func_execution_dtos`) are its two arms — and the kernel op must carry **both arms**. But the kernel never reads `HubSlot.PIPE_FUNC_EXECUTOR`: that slot is applied in `Pipelex.setup`, so it does not exist on a runtime-only boot, and an ambient read would break the boot contract for this one op. Instead the executor enters as an explicit protocol-typed argument — the interpreter passes its hub-resolved one (selected by `pipe_func_config.execution_mode`, `direct` by default), a programmatic caller passes the direct executor or its own.

  ⚠ **This is the highest-risk task in Phase 2, and it is not a move.** An earlier draft of this plan said the protocol "needs a runtime-layer home, since it currently lives in `pipe_operators/func/`", framing it as placement. It is not: the protocol and its DTOs are *typed on interpreter-layer models*. `pipe_func_executor_protocol.py` imports `PipeRunParams`; `pipe_func_execution_dtos.py` imports `PipeRunParams` **and** `LibraryCrate`; `pipe_func_execution_transport.py` imports `get_current_library` / `get_library_manager` straight from `interpreter_hub`, which is a flat layering violation the instant it lands in `pipelex/kernel/`. Both `pipe_run` and `libraries` are interpreter packages. The kernel is clean today *because* it uses `CogtRunParams` and never `PipeRunParams`, and the kernel's own doctrine forbids the usual escape hatch ("if a function-local import seems necessary, the placement is wrong and the type should move instead"). So the real task is **re-typing the protocol off `PipeRunParams`/`LibraryCrate`, or keeping an interpreter-side adapter** — not relocating a file. Moving those two models is far outside Phase 2's scope.

  Three further hazards on this task, none of which any gate catches:

  - **`pipelex/config.py` imports the executor registry**, which defers the protocol under `TYPE_CHECKING` for exactly this reason. If you conclude the deferral is now unnecessary and un-defer it, `pipelex.config` starts loading `pipe_run` and `libraries` — failing every closure test at once, from a module almost everything imports.
  - **Two external plugin repos import these exact modules**: our Daytona sandbox plugin (executor, DTOs, transport) and our Temporal plugin (in-workflow executor and the PipeFunc activity). They are separate repos, so nothing in this tree's CI sees them.
  - **A module path is held as a bare string and run via `python -m`** in the Daytona plugin (`"pipelex.pipe_operators.func.pipe_func_transported_entrypoint"`, hardcoded in two clients and again in its Dockerfile). No import error, no type checker, no static gate catches a rename — it fails at runtime inside the sandbox. Grep sibling repos for string-held module paths before renaming anything under `pipe_operators/func/`.

  Also relevant: 2.5 must touch `pipelex/interpreter_hub.py`, which reopens the `hub-layering-convention` drift contract — and this time the review target is genuinely falsified, because `docs/contribute/hub-layering.md` states in several places that the pipe-func accessor is interpreter-layer *because* its protocol lives in `pipe_operators/func/`.

### What the cold review changed — the boot contract was claimed for six operators and tested for one

A cold `/code-review` of the whole Phase-2 diff returned one finding, and it was right: the boot contract was being *asserted* for every operator and *tested* for the LLM arms alone. Worth recording in full, because the gap was invisible from inside the phase and the same shape will recur in Phase 3.

`test_kernel_boot_contract.py` is the only gate that catches a **function-local interpreter import** inside a kernel function — the static hub-layering guard and the import-closure test both see module-level imports only, which the kernel's own doctrine says out loud. Phase 1 built that gate for `llm_object`/`llm_text` and Phase 2 added five operator ops without extending it. The blind spot is per-function: a function-local import inside `run_search` is caught only by calling `run_search`.

Worse, the *import-time* gate did not reach them either. `test_runtime_layer_import_closure.py` lists `pipelex.kernel.pipelex_kernel` as its kernel entry point on the strength of a comment claiming "the façade imports the ops modules … so one entry point covers the package". That was true in Phase 1 and Phase 2 silently falsified it: `PipelexKernel` is an LLM-era façade that imports `llm_ops` alone. So `extract_ops`, `img_gen_ops`, `search_ops`, `compose_ops` and `func_ops` were policed by **neither** test.

Fixed by extending the boot-contract subprocess to call all seven entry points on the same keyless `RuntimeBoot` and sweep afterwards. All five were drivable in DRY exactly as the LLM arms are — every cogt leaf mocks before a worker is looked up — so the settings are built literally rather than through the `resolve_*_setting` helpers, which read the deck and would be asking a different question. The stale closure-test comment is corrected to say what actually covers those modules and when adding one there would still be worth it. **Verified by mutation, not by assertion:** a function-local `pipe_operators` import planted in `run_search` makes the extended test fail with 72 offending modules, and passes without it.

Two things surfaced while writing it, both recorded where they belong rather than here:

- `ExtractResult.content` is the one kernel envelope field annotated below `StuffContent` (`ListContent[PageContent]`), so pydantic revalidates the plain `ListContent` that `run_extract` builds into a fresh container — making `result.content` a different object from the one the returned memory holds, uniquely among the ops. Nothing is lost (the `PageContent` items pass through by identity) and the interpreter is unaffected, since `PipeExtract` reads only `.memory`. The narrowing is worth keeping — a caller gets `.items` typed without a cast — so it is documented in `extract_results.py` instead of being flattened for uniformity.
- The per-op check in the boot-contract test is therefore by type, not by identity. Asserting identity would have been asserting a coincidence.

It is the only gate that sees a function-local interpreter import, it is per-function, and neither static guard will tell you when it has fallen behind — Phase 2 added five ops and both gates stayed green while covering none of them. - [x] 3.2 Result extraction helpers (main-stuff and named-slot, typed). `extract_main_content` / `extract_named_content` in `memory_ops.py`. Review added `extract_main_content_as_list` / `extract_named_content_as_list`: a multiple-output call stores one `ListContent`, the single-content read cannot narrow it (the bare item class raises, `ListContent[item_type]` is rejected by design), and the bare-`ListContent` workaround loses the item type — so without them the kernel produced one shape its own read half could not read.
- [x] 3.3 Per-step `JobMetadata` semantics (per-step `pipe_run_id` minted from the instance's run-level metadata via `copy_with_update`, per the 0.2 constraint) as a kernel duty; optional trace-context wiring so cost/usage reporting reaches parity when a caller provides one. This task must also answer the lifecycle-ownership question it implies: the interpreter's run machinery is what opens and closes usage reporting today, so state who owns that lifecycle for a kernel-driven run. **Parity bar, measured not asserted:** a test runs an equivalent step through the re-pointed interpreter and through direct kernel calls (mock usage) and asserts the two produced `TokensUsageRecord` lists ([`pipelex/reporting/usage_records.py`](../../pipelex/reporting/usage_records.py)) match in shape and count — the list `/execute` returns on `pipe_output.tokens_usages` and durable runs persist as `tokens_usages.json`.

  **Answered: the caller owns the lifecycle; the kernel owns the stamp.** `PipelexKernel.make` grew `trace_context` and `is_mock_usage`; the context rides the run-level `JobMetadata` and every `make_step_metadata()` copy inherits it, which is the whole of what the cogt leaf needs to emit a usage event. Opening the event log, registering it on the report delegate, reading the events back and clearing the registration stay outside — a kernel call has no run boundary to hang a `finally` on, because it is one step and a caller may make one or a thousand. `pipelex/tracing/` gives a caller both halves it needs (`make_event_log`, `UsageAggregator`) and is runtime-layer, so this costs the boot contract nothing. ## Decisions

- **Structure-prompt provenance — SETTLED: derived in-kernel, optional override.** The registry was only ever needed for the concept→class hop, and the kernel's object call already holds the class — so the kernel derives the structure prompt from `output_class` itself (same config template, same `StructurePrinter`, same `is_structure_prompt_enabled` gate as today), and an optional `structure_prompt` argument overrides it for callers who want to supply their own. The interpreter drops `get_output_structure_prompt`'s registry hop and rides the kernel derivation, so both callers produce the same prompt by default — the alternative (prompt as argument only) would have left the derivation outside the kernel and forked the two callers' default behavior, which is the drift this extraction exists to kill.
- **The deferred runtime-boot orchestrator question — SETTLED: recorded, not guarded.** `runtime_boot.py` deferred the external-interpreter-orchestrator half-application hole to "the first caller of a runtime-only boot", which is now the kernel's boot-contract test. That caller does not trigger it, and not by luck: the gate is only reached when `plugins.boot_orchestrator` is non-`None`, and the test names none — as no kernel caller will, since the kernel's doctrine forbids it from reading `HubSlot` at all and Phase 2's `PipeFunc` op takes its executor as an explicit argument for that reason. The remedy stays unbuilt: both candidates are real machinery (a `HubSlot.is_interpreter_slot` property plus a `honours_interpreter_slots` class attribute, or a widened `build_registrar` signature) bought for a path with still no production caller. Reassess when a runtime-only boot is offered to real callers — that is when naming an orchestrator becomes reachable. Written up in [`wip/boot-split/runtime-boot-external-interpreter-orchestrator.md`](../boot-split/runtime-boot-external-interpreter-orchestrator.md), and `runtime_boot.py`'s comment now points at the settlement rather than at an open question.
- **Kernel construction shape** (task 0.2) — **SETTLED as implemented.** `PipelexKernel` holds exactly `job_metadata` (run-level, fresh `uuid4` `pipeline_run_id`) and `cogt_run_params`. `make_step_metadata()` mints the per-step copy with a fresh `pipe_run_id` and an explicit `otel_context=None`. Nothing config- or deck-derived is cached.

### Deviations from the plan's letter, taken during Phase 3

- **`shape_inputs` requires `input_specs`; the bottom-up no-signature arm is not kernel business.** 3.1 said "over the existing `InputShaper`", and that is literally what landed — the kernel does not wrap `WorkingMemoryFactory.make_from_pipeline_inputs`, whose signature-driven arm *is* `InputShaper.shape` and whose other arm infers each value's concept from its own shape. Inference is exactly the ambient guess a kernel entry point must not make for a caller, so `input_specs` is required rather than optional. A caller with no declared specs builds its stuffs and hands over a `WorkingMemory` directly.
- **`WorkingMemoryFactory.make_from_pipeline_inputs` was re-pointed at, not moved.** The instinct — move the body into the kernel and delete the factory method, as 2.2 did with `resolve_default_size` — is wrong here, and checking is what showed it: the method is on the sanctioned transport surface, pinned by `docs/specs/pipelex-transport-boundary.md` — which lives at the **workspace root**, not in this repo, alongside the `conformance/` suite that enforces it — and is called from `pipelex-transport/pipelex_transport/bridge.py`, `pipelex-mistralai-workflows` and both demo repos. Deleting it is a cross-repo breaking change, which is not what a zero-behavior-change refactor gets to do. So the interpreter's one call site moved to the kernel op and the factory kept its surface.
- **`PipelexKernel.make` grew two parameters, and the ordering of one of them is load-bearing.** `trace_context` was the task's ask; `is_mock_usage` came with it, because the DRY-only sub-flag is what makes a measurable parity comparison possible at all (a plain dry run reports zero tokens on both sides, which would compare equal while proving nothing). It is validated against the **requested** mode, before `resolve_run_mode_for_boot`, mirroring `PipeRunParamsFactory` — otherwise the one illegal combination would raise on a keyed boot and pass silently on a keyless one, i.e. a contract violation whose visibility depended on whether the process held API keys. Pinned in `test_keyless_boot_forced_dry.py`.
- **A supplied `TraceContext` sets the run id rather than sitting beside one.** `PipelexKernel.make(trace_context=…)` adopts its `graph_id` as `pipeline_run_id`. The alternative (a separate optional `pipeline_run_id` parameter) lets the two diverge, and divergence is not cosmetic: the registered-context emit path stamps the event log's id while the runner fallback stamps the metadata's, so a run whose two ids differ scatters its usage events across both and a read-back keyed on either silently misses half. One identity, one parameter.
- **The parity test measures `pipe_code` as *absent on both sides*, not as the one honest difference.** The plan's expectation was that the interpreter fills it and a kernel call cannot. It does not: `pipe_code` is stamped in `live_run_pipe`, which a DRY run never reaches, so the measurement cannot observe the one field that would legitimately differ. Asserted as-is rather than excluded quietly, because that is the honest scope of what the comparison proves — and recorded as KF-13, since a `--dry-run --mock-usage` cost report having no pipe attribution is a real (pre-existing, interpreter-side) gap.
- **KF-6 was settled, KF-2 and KF-5 were closed out as needing nothing, KF-10/KF-12 were re-homed.** Four deferred items named a Phase-3 task as their trigger. Three resolved without code (see `deferred-follow-ups.md`); KF-6 resolved with a docstring, narrowing `StructuringPath` to say it names the *LLM* paths and why `PipeStructure`'s sibling literal has no member. KF-10 and KF-12 had been scheduled onto 3.1 as "the task that decides what a kernel entry point does with a malformed argument" — 3.1 answered that for the memory boundary (reject with a typed, locator-bearing error, which is what `InputShaper` already does), but `max_results` and `nb_images` are operator arguments that never cross it, so their conclusion is unchanged and their home is a standalone blueprint-constraint PR.

### Deviations from the plan's letter, taken during Phase 2

- **`PipeFunc`'s pluggable executor seam stays interpreter-side (task 2.5).** The task asked the kernel op to take the executor as an explicit protocol-typed argument, carrying both arms. Neither arm's type survives the layer boundary: `PipeFuncExecutorProtocol.run_pipe_func` declares `pipe_run_params: PipeRunParams` and `run_pipe_func_transported` is typed on `LibraryCrate`, both interpreter models the task itself rules out moving. That leaves two ways to satisfy the letter, and both were rejected on cost. *Re-typing the protocol* breaks two out-of-tree implementers (our Daytona and Temporal plugins) which thread `pipe_run_params` onto the transported request — for a parameter nothing in either repo actually reads, which makes it a wire-format question, not a cleanup. *A kernel-side protocol plus an interpreter adapter* buys a second protocol for one seam, a wrapper class, and a model conversion at the boundary — to compose two calls. So the composition (`run_func`) is the kernel's in-process path, and what is genuinely shared — the call itself and the write-back — is single-sourced in `call_registered_function` and `store_result`, which is what the interpreter's default executor and operator now ride. Consequence to hold onto: a programmatic caller cannot dispatch a kernel `run_func` to a sandbox, and `run_func` has no in-tree caller, which is why it is unit-tested directly. Recorded in [`deferred-follow-ups.md`](deferred-follow-ups.md) as KF-8.
- **`PipeCompose`'s construct mode stays interpreter-side (task 2.4).** Its semantics are `StructuredContentComposer` (840 lines) over a `ConstructBlueprint` (315 lines), and the kernel cannot import either: `pipe_operators` is an interpreter package by the closure test's own predicate. So covering construct mode means *relocating both into `pipelex/kernel/`* — an MTHDS field-composition blueprint, its composer, and the `PipeComposeError` family they raise (which drags the `docs/errors/` regeneration and the `error_identity.txt` snapshot). Phase 1's `LLMPromptBlueprint` precedent points the other way but does not apply: there the kernel needed a *small* input model (`LlmPromptContent`) and the blueprint mapped down; the equivalent here is a near-verbatim copy of a 315-line model. Weighed against that cost, the caller-side gain is close to nil — a programmatic caller holding real Python builds the object directly rather than describing it in a blueprint. The template path, which *is* pure rendering over memory, is fully extracted, and the one thing both paths share (the three-layer context ordering) is now single-sourced in `build_compose_context`. Recorded in [`deferred-follow-ups.md`](deferred-follow-ups.md) as KF-7.
- **`PipelexKernel` stays an LLM-only façade — the reference-carrying question the plan assigned to Phase 2 is answered "no".** The task at "Target caller experience" was to decide, once image-bearing operators landed, whether the façade grows reference-carrying parameters. It did not grow at all: the five Phase-2 ops are module-level functions with no façade method. Two reasons. The façade's job is holding *per-run state* a caller would otherwise thread through every call (`job_metadata`, `cogt_run_params`), and that state is identical for every op — a façade method per operator would add a naming surface without adding a service. And the ops' remaining arguments are the operator-specific ones (`ExtractInput`, `ImgGenPrompt`, `output_class`, a template and its category), which a façade would have to enumerate verbatim; wrapping them buys nothing and forks the signature the moment an op grows a parameter. So a programmatic caller mints a `PipelexKernel` for the run state and calls the module-level functions with it, which is what the boot-contract test does. **Consequence worth carrying into Phase 3:** `test_runtime_layer_import_closure.py`'s only kernel entry point is `pipelex.kernel.pipelex_kernel`, so an LLM-only façade means that test's closure does not reach the other ten kernel modules — the standing rule at the head of Phase 3 exists for exactly this reason.
- **The kernel ops modules gained a shared `memory_ops.store_result`.** Phase 1 put it in `llm_ops.py`; every Phase-2 operator ends the same way, and importing it *from `llm_ops`* would have implied an LLM dependency that does not exist. It moved to `pipelex/kernel/memory_ops.py`, which is also where Phase 3's boundary shaping (3.1) and result extraction (3.2) belong.
- **Not every operator earned a rich result envelope, and that was decided per operator** (the plan's trap #6). Each envelope carries exactly the intermediates the kernel *produces* and the caller cannot recompute: `SearchResult` carries the rendered query and the post-resolution `SearchSetting` (which is not the one passed in); `ComposeResult` the rendered text; `ExtractResult` the resolved `ExtractSetting`. `ImgGenResult` carries only memory + content, because everything the img-gen tracer records is either a caller input or something the caller resolved through an ops function before calling. The memory contract is why even the thin one exists.
- **The kernel gained an image-prompt constructor the plan never scheduled (`pipelex/kernel/img_gen_prompt.py`).** Folded in from the parity-gaps track (its gap 2.3), on the same reasoning as Phase 1's `llm_text` widening: it is a defect *this* PR would otherwise introduce. `run_img_gen` takes a *ready* `ImgGenPrompt` by deliberate analogy with `run_llm_text` taking a ready `LlmPromptContent`, but the kernel shipped the LLM prompt's constructor and no image counterpart — so a `RuntimeBoot`-only process could call every operator op except the image one, and `kernel/prompt_references.py` hosted `ImageReference` under a docstring asserting the kernel resolves them while the interpreter-layer blueprint did the resolving. A "callable without the interpreter" guarantee at less than 100% is worth nothing. `ImgGenPromptBlueprint` drops 296 → 82 lines and delegates, keeping parse-and-validate; `ImgGenPromptBlueprintValueError` becomes `PromptContentError`, the same swap Phase 1 made on the LLM side. **The predicted cost did not materialise:** the parity plan expected the move to drag `ImageRegistry`, `PromptImageFactory`, `substitute_nested_in_context` and `render_template` across a layer boundary and force a scoping decision — all four are already `cogt`/`tools` citizens, and the blueprint held exactly one interpreter-layer import. Nothing moved layers. `max_prompt_images` deliberately stayed with the blueprint: it is a property of the model the *pipe* chose, its breach is a pipe-level error, and it is a `len()` check rather than the subtlety the kernel module exists to centralise. Two now-dead subject grants were removed rather than re-granted, per this package's zero-grants rule — exactly the sweep this plan warns about for every operator moved.
- **The new entry point took the boot-contract arm the standing rule owes it, and the arm replaced a hand-built prompt.** `assemble_llm_prompt` never needed one — `run_llm_text` and `run_llm_object` both call it, so the LLM arms carry its closure. `run_img_gen` takes a ready prompt and calls nothing, so the img-gen arm had been *constructing* its `ImgGenPrompt` in the test, for the plain reason that nothing in the kernel could build one. That made the arm's coverage incomplete in precisely the way the kernel surface was. It now assembles from a memory holding a referenced image and generates from the result, asserting on the `[Image N]` token *and* on `input_images` — the two readings of one registry, whose disagreement would mislabel which image the prompt describes with nothing downstream able to notice.

### Deviations from the plan's letter, taken during Phase 1

- **The deck chain is two functions, not one `resolve_llm_settings`.** `resolve_llm_setting_for_text` and `resolve_llm_setting_for_object` (the latter taking the optional `llm_choice_for_text` that makes its chain one rung longer). A single function returning both settings would have made `PipeStructure` — which resolves only the object setting today — newly resolve the text one too, which is a behavior change on the one gate that matters. Two functions keep each caller resolving exactly what it resolved before, and the chain is still single-sourced.
- **`PipeStructure` rides the kernel's *pieces*, not `run_llm_object`.** It shares the object semantics — structure-prompt derivation, generation, memory write-back — and calls those four kernel functions. It does **not** share prompt assembly: it has no template of its own and no memory-borne references, it renders one configured `structuring_prompt` template over one input string, and forcing that through `assemble_llm_prompt` would have changed the render context from `{"text": …}` to the whole working memory. That is a real behavior change for a cosmetic gain.
- **`templating_style` is an explicit argument to `run_llm_text` / `run_llm_object`, not derived inside them.** `PipeLLM` derives it from its **text** setting and uses it on both paths; a kernel that derived from its own setting would silently change the object path's rendering style. The derivation itself (`derive_templating_style`) is single-sourced in the kernel; *which* setting governs is the caller's decision, and it has to be, because a caller can hold two.
- **One deliberate widening, worth watching in review:** `PipeLLM`'s text path used to wrap only `structure_class(text=…)` in `except ValidationError`. That construction is now inside the kernel call, so the handler wraps the whole call. A `ValidationError` raised elsewhere inside it (prompt assembly, result construction) would now surface as `PipeRunError("Error generating text content in PipeLLM …")` instead of propagating raw. Same error class, same wrap, slightly wider scope.
- **`assemble_llm_prompt` does not log the assembled user text**; `LLMPromptBlueprint.make_llm_prompt` still does, keeping its `output_concept_ref` parameter (whose only job was that log) so its test call sites are untouched. Moving the log into the kernel would have meant either duplicating it or carrying a log-only parameter across the layer boundary.
- **The no-class arm task 1.6 told the re-point to keep does not exist, and was correctly dropped.** 1.6's text says the interpreter must retain the arm where `get_output_structure_prompt` returns `None` because the concept's structure class is not in the registry, "rather than assume class resolution always succeeds". The re-point does assume it: both `pipe_llm.py` and `pipe_structure.py` now call `get_class_registry().get_required_subclass(...)` eagerly before dispatch, and the soft `get_class(...) -> None` path is gone with `helpers.py`. That is right, and the plan's premise was a half-reading of the old code: the pre-move object path called `get_required_subclass` unconditionally as the first statement of `_llm_gen_object_stuff_content`, so no run ever survived a missing class — the soft arm only ever suppressed the *structure prompt*, never the failure. The only real change is that the error now raises before prompt assembly instead of after. Recorded because a future reader of 1.6 would otherwise think a required arm was dropped silently.
- **`PipelexKernel.llm_text` ships as wide as the op beneath it** — `concept`, `output_class` and `model` are optional, defaulting to what the method previously hardcoded (native `Text`, `TextContent`, the deck's own choice). Folded in from the parity-gaps track (its gap 2.1) rather than landed as a follow-up PR, because the narrowness is a defect *this* PR would otherwise introduce: `run_llm_text` takes all three and the interpreter passes all three, so a façade hardcoding them stores `native.Text`/`TextContent` where an interpreted run stores the declared concept and its generated class — a silent memory divergence surfacing only later as `StuffContentTypeError` in whoever reads the result back. `llm_object` had all three from the start; the asymmetry was between the façade's own two methods. Purely additive (the only callers are tests), gated by `tests/unit/pipelex/kernel/test_llm_text_kernel.py`, which asserts on what lands in the returned memory rather than on the signature. No changelog entry: the package is new and unreleased, so there is no shipped behavior to note.
- **The prompting-style question that came with it is deferred, not fixed — see KF-16.** The same parity track listed a gap 2.2 claiming `llm_object` renders under the wrong model's style. Re-verified here as **overstated**: the single explicit `model` wins `resolve_llm_setting_for_object`'s first rung, so the style comes from that setting — which is what an interpreted run derives for a pipe naming only a text model. The two agree for every call the façade can express. What remains is narrowness (a pipe naming *both* models is inexpressible), and widening it would mean building the two-setting derivation the mechanism is slated to lose entirely — `wip/prompting-style/README.md`.
- **The concept-resolution routing rule (0.1e) is satisfied vacuously in Phase 1.** The LLM kernel ops answer no concept-compatibility question at all — the text-vs-object dispatch stays interpreter-side by construction, which is stronger than routing through the pure tiers. The rule is written into the kernel doctrine and applies to whatever Phase 2 adds; there is no `concept_resolver`-omitted arm to test yet, so task 1.7's third named arm does not exist and should not be invented.

## Non-goals (explicit)

- **Controllers stay interpreter-side.** This effort covers operator semantics only; `pipelex/pipe_controllers/` is untouched.
- **No standalone PyPI distribution yet.** A separately installable kernel dist is a later milestone, once the cogt hub/plugins coupling is unwound; for now the kernel is a subpackage of `pipelex`.
- **No behavior changes and no new operator features.** Extraction is behavior-preserving; the full test suite must pass, with only the mechanical churn the Doctrine section describes (import repoints, moved modules, patch-target updates).
- **No Temporal activity target.** Activity-shaped is a design constraint on call signatures, not a deliverable of this refactor.
