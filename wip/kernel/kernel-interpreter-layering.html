Kernel / Interpreter Layering

What we refactored, why the boundary exists, and what it measurably bought.

pipelex · PRs #1081 #1082 #1083 #1090, all merged to dev · written 2026-08-12

TL;DR

  • Pipelex now has two named layers and exactly one arrow between them. The interpreter reads a .mthds method and drives it. The kernel is the machinery present at execution time whatever is loaded — inference, models, memory, storage, tracing. The interpreter may import the kernel; the kernel may never import the interpreter, directly or transitively.
  • Operator semantics moved out of the operator classes into pipelex/kernel/. What a PipeLLM step actually does — deck resolution, style derivation, prompt assembly, generation, memory write-back — used to live inside PipeLLM._live_run_operator_pipe and be reachable only through a fully booted interpreter with a library loaded. It is now plain keyword-only functions with the operator class as one caller among others.
  • The point is single-sourcing, not reuse. Two callers with two copies of "what an LLM step means" drift, and nothing tells you when they have. There is now one implementation and a build that fails when a second one is smuggled in.
  • Four gates hold the boundary, and each sees something the others miss. The strongest one runs every kernel entry point on a keyless boot with zero .mthds loaded and sweeps sys.modules afterwards — it is the only gate that can see a function-local interpreter import. Each gate was mutation-tested, not just asserted.
  • Zero behavior change was the bar, and the full suite was the gate at every phase. One real bug surfaced on the way and was fixed: a keyless boot could reach a live inference provider through the new kernel factory.
  • Measured (2026-08-11): 560 of 981 modules are declared kernel-layer; a kernel-only boot loads 1511 modules / 91.7 MiB RSS against 1884 / 108.7 MiB for a full boot; a kernel-only install would shed 32 distributions and 32.4 MiB (~35%).
  • Not done, deliberately: the kernel is still a subpackage of pipelex, not its own distribution; two operator arms stayed interpreter-side on cost grounds (both recorded). See Honest limits.

1. The two problems this fixes

Problem A — the semantics were trapped inside the operator classes

Before this work, "what a PipeLLM step means" existed once, as a 100-line stretch inside PipeLLM._live_run_operator_pipe: walk the model-deck chain, derive the prompting style, assemble the prompt (text, images, documents), generate, coerce into the output class, write the result into working memory. That code was only reachable by constructing a PipeLLM, which requires a library, which requires an interpreter, which requires a full boot.

Any second caller therefore had two options, both bad: boot the entire interpreter to run one inference step, or reimplement the semantics. Reimplementation is the expensive one — not because writing it is hard, but because the copy and the original drift silently and nothing in CI can tell. This is not hypothetical for us: a distributed activity, an SDK-style embedding, and a host that only wants inference are all callers we either have or want.

Problem B — the layer was a claim, not a boundary

The layer split existed on paper before this arc (runtime_hub / interpreter_hub, #1062), but it was real for importing and vacuous for booting: the only composition root in the tree constructed an InterpreterHub, a PipelineManager, a PipeRouter and a PipeRun whether the caller would ever load a method or not. And it leaked in ways that were invisible to review:

  • Four modules in a declared-clean package reached interpreter_hub through a three-hop import chain while both gates stayed green (fixed by the transitive rule, #1064).
  • Five vendor adapters dragged interpreter modules in by importing from the pipelex.exceptions re-export aggregate rather than from definition sites — a cross-layer aggregate is a layer boundary with the sign filed off (fixed by a mechanical ban, #1080).
  • Merely installing our Temporal plugin pulled the whole interpreter into every pipelex process in the venv, because plugin discovery imports every installed plugin's module regardless of what the boot needs (fixed by the entry-point group split, #1090).

The pattern worth internalising: an undeclared package is not neutral, it is unpoliced. Both guard rules filter their candidates through the layer declaration, so omitting a package from it makes the guard quieter, not louder. Every one of the leaks above was green on every gate at the time.

2. The two layers

One arrow is the whole architecture. The property it buys is measurable, not rhetorical: importing or booting the kernel layer loads zero interpreter modules.

Pipelex subclasses RuntimeBoot and appends the interpreter constructions, so there is one composition root with two entry points rather than two roots that can drift. Module counts and RSS above are measured on a booted process, not estimated.

3. What moved, and where the cut line falls

The operator class did not shrink into a shell — it kept everything that genuinely needs a loaded method, and became a caller for the rest.

The cut line is the load-bearing design decision, and it is stated so nobody has to find it by trial:

ConcernOwnerWhy
Blueprint resolution, input validationinterpreterBlueprints are what .mthds parses into — language artifacts.
Text-vs-object dispatchinterpreterIt is a question about the declared output concept; answering it is what a loaded library is for. The kernel's two entry points are that fork made explicit.
Error context (PipeRunError + pipe stack)interpreterThe kernel raises the same cogt-level errors the moved code raised; it has no pipe to name.
Concept → concrete classinterpreterA registry read. Handing the class over is what spares the kernel one.
Deck chain, style derivation, prompt/job-params assembly, generation, write-backkernelThese are what a step does; they need no method and no library.
Structure-prompt derivationkernelOnly the concept→class hop needed a registry, and the kernel already holds the class. Leaving derivation outside would have forked the two callers' default behavior — exactly the drift this exists to kill.
Memory boundary (shape in, store, typed read-out)kernelBoth ends of one boundary belong together.
Usage/trace lifecyclecallerA kernel call has no run boundary to hang a finally on — it is one step and a caller may make one or a thousand. The kernel owns the stamp (a TraceContext onto every step's metadata); opening and closing the event log stays outside.

The resulting package is 19 modules / ~2 200 lines under pipelex/kernel/: the six operator families (llm, extract, img_gen, search, compose, func) as *_ops.py + *_results.py pairs, the memory boundary, the prompt-content models, and a thin PipelexKernel façade holding per-run state.

B. The op shape — activity-shaped, keyword-only, memory in and out

Every kernel entry point has the same shape, and each property is a deliberate constraint rather than a style choice.

async def run_llm_text(
    *,                                        # fully keyword-only: zero subject grants in this package
    memory: WorkingMemory,                    # threaded state, taken and returned
    prompt_content: LlmPromptContent,         # a kernel-layer model, not the language-layer blueprint
    llm_setting: LLMSetting,
    concept: Concept,
    output_class: type[StuffContent],         # handed over, so the kernel needs no registry
    job_metadata: JobMetadata,
    cogt_run_params: CogtRunParams,
    templating_style: TemplatingStyle | None = None,
    result_name: str | None = None,
) -> LlmTextResult: ...                       # typed envelope: memory + the intermediates a tracer needs


def store_result(*, memory: WorkingMemory, concept: Concept, content: StuffContent, ...) -> WorkingMemory:
    """Write a produced content into memory as the new main stuff, and return the memory.

    Returning it is the contract, not a convenience: the argument is mutated today because inline
    execution aliases the two, and a caller that relies on that aliasing breaks the moment a
    serialization boundary sits between them.
    """
  • Keyword-only, no exceptions. pipelex/kernel/ records zero entries in subject_grants.toml — a bar stricter than the repo-wide rubric, and one the auto-fixer produces mechanically, so there is no ordering trap.
  • Explicit, serializable-leaning arguments; no ambient lookups in the caller-facing API. This is a design constraint, not a shipped feature: it keeps a future distributed-activity wrapping a re-decoration rather than a rewrite.
  • The memory contract is stated once, in the package doctrine, so both classes of caller read the same sentence. Today inline execution aliases argument and return; a serialization boundary will not, and a test that pinned result.memory is memory would have made the very change the contract permits look like a regression. The tests deliberately assert the returned memory carries the result, and nothing about identity.
C. The plugin layer split — a plugin declares its layer through its entry-point group

Measurement showed that merely installing an interpreter-side plugin dragged the whole interpreter into every pipelex process in the venv: discovery imports each installed plugin's module before anything can inspect it. Making that plugin well-behaved fixes our own plugins and nothing else. The mechanism (#1090) makes a kernel-only boot never query the interpreter group at all:

class PluginGroup(StrEnum):
    KERNEL = "pipelex.plugins.kernel"
    INTERPRETER = "pipelex.plugins.interpreter"

# providers/builtins.py            — what a kernel-only boot asks for
KERNEL_ENTRY_POINT_GROUPS = (PluginGroup.KERNEL,)

# interpreter_plugins/builtins.py  — what a full boot asks for
ENTRY_POINT_GROUPS = (PluginGroup.KERNEL, PluginGroup.INTERPRETER)

     def make(
         *,

+        entry_point_groups: "Sequence[PluginGroup] | None" = None,   # symmetric with builtin_plugins

Three further properties came with it, each closing a specific silent-failure mode:

  • A tier cross-check at register time. A kernel-group plugin calling an interpreter-tier menu method (add_orchestrator, add_bundle_validator, add_pipe_func_executor) fails loud. The rule is deliberately one-directional — an interpreter-group plugin may contribute kernel-tier capabilities freely, because a kernel-only boot never loads that group anyway. Our own Temporal plugin is what settles it: it is interpreter-side and also contributes an HTTP error mapper.
  • Slot tiering is a property of the slot, via an exhaustive match, so a newly added hub slot cannot be merged without being classified.
  • A fail-loud probe on the retired pipelex.plugins group. Without it, a plugin left behind is simply absent — no error, a capability that quietly does not exist. That is the expensive failure to diagnose.
D. The one real bug the refactor found — and what it teaches

Review caught it before merge; it was the PR's only behavior change. PipelexKernel.make minted a LIVE CogtRunParams on a keyless boot, bypassing the forced-DRY coercion the pipe tier applies. Reachable, not theoretical: run_mode alone gates mocking, so the call reached a real provider, and needs_inference=False loads backends leniently rather than credential-free. The hazard was the default — PipelexKernel.make(user_id=…) names no mode.

The root cause is the refactor's own doing: PipeRunParamsFactory's docstring called itself "the single writer" of run_mode, and that stopped being true the moment the kernel became a second run-params factory.

+        log.warning("LIVE run requested under a keyless boot (needs_inference=False): forcing DRY ...")

@@ pipelex/kernel/pipelex_kernel.py

The generalisable lesson, and it applies to any layering work: a new lower-tier factory of run-scoped state silently skips every process-wide invariant the upper tier applied. When you add one, ask explicitly which invariants the tier above enforces that yours now bypasses. Note also the ordering: the requested mode is validated before the coercion, otherwise the one illegal combination would raise on a keyed boot and pass silently on a keyless one — a contract whose visibility depended on whether the process held API keys.

5. What holds the boundary

A layering rule that is only in a doc decays. Four gates enforce this one, and the honest framing is that each covers something the others structurally cannot see — the reason there are four is that we found each blind spot the hard way.

GateProvesBlind to
pipelex-dev check-hub-layering No kernel module imports the interpreter hub — per-file, plus a transitive pass over the whole module-level import graph, plus a dead-module rule matching bare string literals. Function-local imports. Runtime-assembled module paths.
test_kernel_layer_import_closure.py A kernel entry point imports clean, in a subprocess. Anything outside the listed entry points' closure — the façade is LLM-only, so most of the package sits outside it. Function-local imports.
test_kernel_layer_exceptions_aggregate_gate.py No kernel module reaches the pipelex.exceptions re-export aggregate — imports and bare strings, module-level or function-local. Aggregates other than the declared one.
test_kernel_boot_contract.py Every kernel entry point runs on a keyless RuntimeBoot with zero .mthds loaded, then sys.modules is swept. The only gate that sees a function-local interpreter import. It is per-function: a breach inside run_search is caught only by calling run_search. Nothing tells you when it has fallen behind.

That last blind spot is not hypothetical either — it is exactly what happened mid-refactor. Phase 2 added five operator ops; the boot contract was asserted for all of them and tested for the LLM pair alone, and both static gates stayed green while covering none of the five. A cold review found it. The standing rule now reads: every new kernel entry point owes an arm in that subprocess, and it is written into the package docstring rather than into a plan nobody will re-read.

Every gate above was mutation-tested rather than asserted: a function-local pipe_operators import planted in run_search leaves the static guard at exit 0 and the closure test at all-passed, and turns only the boot-contract test red. The usage-parity test was checked the same way — dropping the trace-context stamp turns 1 record into 0. A test that is green on its first run has proven nothing yet.

The honest reading of the size numbers. A kernel install is roughly two-thirds of a full one, and the ~61 MiB floor is dominated by four dependencies with nothing to do with the interpreter (pillow, faker via polyfactory, pypdfium2, portkey-ai). "Look how little you need" is not a claim this refactor earns — a small footprint would have to be bought by extras design, not by the layer split. The layering's value is elsewhere.

Where the value actually is

  • Drift becomes a build failure instead of a discovery. The specific risk this removes: an SDK-shaped caller and the interpreter computing the model-deck chain, the structure prompt, or the memory write-back slightly differently, with no test capable of noticing. Before, that outcome was prevented by discipline. Now the second copy has nowhere to live.
  • "Where does this change go?" has a mechanical answer. Language rule → blueprint, interpreter-side. Authoring convenience → spec. What a step does → kernel. Reviewers apply it rather than negotiate it, and a wrong answer trips a gate rather than a reviewer's memory.
  • The layering property became testable at all. "The kernel does not depend on the interpreter" used to be an import-time claim about a process that could not actually be booted that way. It is now a property of a process that boots, runs every kernel entry point, and is swept afterwards.
  • A whole class of silent failure got a loud failure mode. Cross-layer re-export aggregates, transitive leaks, plugins that lie about their layer, plugins left under a retired entry-point group — each of these used to manifest as a mystery import or an absent capability. Each now names itself at build or boot time.
  • Refactoring pressure now points the right way. The remaining coupling is 11 modules and a static leak census with a named disposition each, instead of an unbounded "the interpreter is entangled with everything" feeling. That is what makes a later distribution split a decision rather than a project.
  • Cost/usage reporting reaches parity for a kernel-driven run, measured rather than argued: an equivalent step run through the interpreter and through direct kernel calls produces matching TokensUsageRecord lists.

7. Honest limits

What this refactor did not do, stated plainly so nobody reads more into it than it earns:

  • The kernel is still a subpackage of pipelex, not a separate distribution. The trust-base story ("this process contains only the kernel") is a per-venue claim today, holding for plugins we author and vet. A separate pipelex_kernel/ top-level package (Part B, same repo and same wheel) is planned and measured but not started; a published pipelex-kernel distribution (Part C) is explicitly hypothetical and requires its own decision.
  • Two operator arms stayed interpreter-side, on cost grounds, both recorded. PipeCompose's construct mode would require relocating an 840-line composer, a 315-line MTHDS blueprint and its error family into the kernel — for a caller-side gain near nil, since a programmatic caller holding real Python builds the object directly. PipeFunc's pluggable executor seam is typed on interpreter models (PipeRunParams, LibraryCrate); re-typing it breaks two out-of-tree plugin repos over a parameter neither reads. Consequence to hold onto: a programmatic caller cannot dispatch a kernel run_func to a sandbox. The template path and the function call itself are single-sourced.
  • Controllers were out of scope. pipelex/pipe_controllers/ is untouched — this covers operator semantics only.
  • The three external plugin repos are migrated but unpushed. Local commits on refactor/plugin-layer-groups in pipelex-temporal, pipelex-mistralai-workflows and pipelex-daytona-sandbox. Each repo's venv is currently red on that branch, and correctly so: the working tree declares the new entry-point group while the pinned pipelex reads only the retired one. That is the release gate showing through, not breakage — they land once a pipelex release carries the new discovery.
  • The remaining kernel→non-kernel couplings are catalogued, not fixed. The structural one is that MthdsConfig — an interpreter-layer submodel — is a field of the kernel-layer main config model. That is a config-composition decision, not a file move.
  • One live finding is still open (KF-18): core/memory/working_memory_factory.py — kernel-layer — imports two pipelex.builder.pipe modules inside a dry-run mocking helper, under a "avoid circular imports" comment, pulling 6 interpreter modules. Both static gates are green and each is answering its own question correctly; the boot-contract sweep does not reach it because no op calls that helper. It is a real instance of the blind spot documented above, and the reason Part B's package-level ban (nothing under pipelex_kernel/ may import pipelex) is worth more than the instance fix.

9. The rules worth carrying into your next change

  1. An undeclared package is unpoliced, not neutral. If you add a top-level package, place it on one side of the line in KERNEL_LAYER_PACKAGES and pin the declaration with a test. Omitting it makes every gate quieter.
  2. Every new kernel entry point owes an arm in test_kernel_boot_contract.py. It is a few lines; noticing it was never added took a cold review, twice.
  3. Import from definition sites. A module that re-exports across layers is a layer boundary with the sign filed off.
  4. No function-local imports in kernel code. They are invisible to the static graph and to the closure test at the same time. If one seems necessary, the placement is wrong and the type should move.
  5. A new factory of run-scoped state skips the tier above's invariants. Enumerate them explicitly before shipping it.
  6. Moving code has consequences no compiler reports. Sweep subject_grants.toml, .test_durations node IDs, docs/ for file paths you moved, and docs/errors/ pages when a PipelexError subclass changes module. Two of those four fail a build; the other two fail silently.
  7. Mutate your own test before believing it. Green on the first run proves nothing about what a test guards.
