pipelex-temporal · branch refactor/Topology

Flat topology & dynamic names

One workflow per run instead of one per sub-pipe, and names that say which method is running. What changed, why, and what it buys us.

Audience
Anyone working on pipelex-temporal, or on pipelex code that dispatches through the pipe router.
Status
Implemented, both PRs open, suite green. Docs, skills and the release remain.
Why it is safe to do now
Temporal has never carried production traffic. These are wire-visible surfaces — this will never be cheaper.

TL;DR

  • One workflow per run, not one per sub-pipe. Sequences, parallels and conditions now execute inline as workflow code. Child workflows survive in exactly one place: batch fan-out branches, where per-item isolation and history partitioning are genuinely earned.
  • Names carry meaning. A run's workflow type is the pipe ref it runs — legal_docs.summarize_contract, not another wf_pipe_router row. Each leaf activity is <operation>::<pipe_code> — llm_text::draft_overview, not another act_llm_gen_text bar.
  • The two halves are one decision. Dynamic naming is what replaces the structural readability per-sub-pipe children used to provide. Flattening without renaming would trade a legible tree for an illegible flat list.
  • What we stop paying, per sub-pipe dispatch: a full library/registry setup + crate load + teardown, a double WorkingMemory serialization round trip, and a workflow's worth of history events and worker round-trips. It compounded with tree depth.
  • Deliberately unchanged: queue routing (still keyed on the canonical act_* name), the structured error contract, the replay-determinism surface, and worker-scope vocabulary.
  • Two PRs, landing in order: pipelex#1088 (core seam) then pipelex-temporal#18 (the reshape).

What a run used to look like

Every sub-pipe dispatch in the interpreter — batch, condition, ordinary sequencing alike — went through get_pipe_router().run(...). Under Temporal that router auto-detected its context: outside a workflow it started a top-level wf_pipe_router; inside one it dispatched the sub-pipe as a child workflow of the same type.

So a sequence of leaf steps became a parent workflow plus one child per step, and a leaf child was a workflow whose entire body was setup ceremony wrapped around a single activity.

The tax, paid per child, compounding with depth

Cost of a workflow boundary that buys no isolation
CostWhat it actually was
Library ceremony, repeatedEach child seeded a class registry from the global one, opened a fresh per-workflow library, loaded the crate, and tore it all down in a finally block choreographed for eviction safety — re-establishing state its parent already held.
Double serialization per hopThe full WorkingMemory was dehydrated on the way into each child and again on the way out, on top of the per-activity payload serialization that does the actual work.
Error machinery_carries_temporal_failure and its chain-walking exist to rescue leaf error classifications out of ChildWorkflowError cause chains across workflow boundaries.
History, latency, schedulingOwn start/complete events, own worker round-trips, own workflow-task scheduling — pure overhead when the child adds no isolation the parent lacked.
…for benefits bought elsewherePer-pipe visibility rides on ids, summaries, details and search attributes — none of which need a workflow boundary. Per-sub-pipe workflow-level retry was explicitly disavowed in our own comments (retry belongs at the activity boundary). Per-pipe queue routing was never exploited; activity_queues already routes at the operation level.

The determinism surface did not change

Controller code already executed inline as workflow code — in whichever child happened to own it — and the sandbox handoff already treats the whole pipe.run_pipe() tree as workflow-reachable. Flattening moves the same code into the parent. Nothing new became replay-sensitive.

Three things start working that never worked before:

  • The workflow type column, type filters and per-type metrics become first-class visibility over the method catalog — “how many summarize_contract runs failed today” is a stock Temporal query now.
  • Per-activity-type metrics answer which step of which method is slow or retrying, without opening a payload.
  • A flat history reads in method order, so “where did this run stall” is one glance rather than a tree walk through boilerplate children.

The reshape, in five moves

Each move was a phase, gated on a green suite and a code review before the next started. The numbering is the real dependency order — they read cleanly in that order in the branch history.

01

Core seam

Core needed one thing it did not have: a way for the interpreter to say “this dispatch is a per-item fan-out branch” as semantics rather than as a data shape. A batch branch job is otherwise indistinguishable from any other dispatch — it just carries the branch pipe and the per-item memory.

+    async def run_batch_branch(self, pipe_job: PipeJob) -> PipeOutput:
+        """Run ``pipe_job`` as one fan-out branch of a ``PipeBatch``.
+
+        A distributed router MAY use that signal to isolate the branch (own retry, own
+        history partition); every other dispatch it receives runs inline.
+
+        The default body IS the behavior for in-process routers: a branch is just a run.
+        """
+        return await self.run(pipe_job)

Deliberately no override in core's own PipeRouter — the default is the behavior, and the delegation target is part of the contract (observers still see branches go through run), not an implementation detail.

The same PR freezes the batch fan-out bound into the payload. PipeBatch used to read max_concurrency from live config inside workflow code — a pre-existing replay hazard, since config drift between original execution and replay would change the fan-out shape. It is now a frozen PipeRunParams.batch_max_concurrency field, written once by the params factory.

Proven against history, not against code

test_wf_flat_topology.py counts StartChildWorkflowExecution events in recorded histories: a sequence-wrapping-parallel-and-condition bundle records zero; the batch bundle records exactly one per item. That is the structural claim of the whole reshape, asserted where it is observable.

Behavior deltas the flip produced
  • with_conditional_worker no longer wraps the in-workflow branch dispatch. It decorated _run_pipe_job, which used to own both arms. Strictly safer: the wrapper's INTERNAL arm would have tried to start a worker from inside a workflow. Latent, never hit, now unreachable.
  • PipeParallel combine no longer crosses a boundary, so the class-identity bug family that produced the scoped_library_for_crate fingerprint-reuse fix cannot occur on non-batch paths — the boundary that invited it is gone.
  • Two tests had to change bundle, not assertions. One proved cross-child usage aggregation with a PipeParallel; parallel branches run inline now, so it proved nothing there. Both migrated to a batch — the only construct that still produces children. Neither contract was weakened; each moved to the shape that can still exercise it.
  • The error machinery narrowed, it did not weaken. _carries_temporal_failure's reachable case went from “any sub-pipe child anywhere in the tree” to “a batch branch”, and chain depth now tracks batch nesting instead of tree depth. A dedicated test pins the surviving child path end to end: leaf ApplicationError.details → branch child → wrap → the parent's propagate-don't-flatten decision → recover_error_report at the submitter, with the full classification intact.
03

Merge the two workflow definitions into one

With the tree flat, WfPipeRun (the run root: scoping, tail, delivery) and WfPipeRouter (the per-dispatch body) were two definitions doing overlapping work. They merged behind a plugin-owned envelope:

class WorkflowRole(StrEnum):
    RUN_ROOT = "run_root"
    BATCH_BRANCH = "batch_branch"

class PipeWorkflowArg(BaseModel):
    pipe_job: PipeJob
    role: WorkflowRole
    delivery_assignment: DeliveryAssignment | None = None

The role is an explicit field, not workflow.info().parent inference — parent-ness identifies a batch branch today only because batch branches are the only children we create, and a future child kind would silently inherit the wrong role. Match/case on the role, no default arm. RUN_ROOT runs tracing assembly, delivery and the deferred re-raise; BATCH_BRANCH returns straight after the flush.

A real bug the merge introduced — and the lesson

The old topology had a catch ladder of ActivityError/PipelexError in the router and ChildWorkflowError/PipelexError in the parent. A TemporalError — what the content generator mints at its own activity boundary — is neither, so it escaped the router child entirely and the parent caught the resulting ChildWorkflowError. That is what fired delivery.

With one workflow there is no parent to catch it, so the first merged version let a leaf inference failure skip the run's whole tail: no tracing assembly, no FAILED webhook. Fixed with an except ApplicationError arm that captures it as-is — converting would flatten the leaf's packed ErrorReport.

Keep this: merging two catch ladders is not the union of their clauses. The outer one was also catching what the inner one deliberately let escape.

04

Dynamic workflow naming

make_workflow_type_name(pipe) returns the pipe ref (domain.pipe_code), used for both roles: a run root by its entry pipe, a batch branch by the branch pipe actually fanned out. It delegates to core's own PipeAbstract.pipe_ref, so the wire-visible type stays in lockstep with the notation an author writes.

The run workflow became @workflow.defn(dynamic=True). That trades a typed signature for a name-matched catch-all, which moves the boundary contract into the decode:

def _decode_workflow_arg(args: Sequence[RawValue]) -> PipeWorkflowArg:
    if len(args) != 1:
        raise ApplicationError(..., non_retryable=True)

    # Deliberately annotated ``Any``, not ``PipeWorkflowArg``: the type hint tells the payload
    # converter which deserialization *strategy* to use, it does not enforce the result.
    decoded: Any = workflow.payload_converter().from_payload(args[0].payload, PipeWorkflowArg)

    if not isinstance(decoded, PipeWorkflowArg):
        raise ApplicationError(..., non_retryable=True)      # <- load-bearing, see below

    expected = make_workflow_type_name(decoded.pipe_job.pipe)
    if workflow.info().workflow_type != expected:
        raise ApplicationError(..., non_retryable=True)      # started under a lying type
    return decoded

Every rejection is non-retryable, and that is the point: a mis-dispatched start must fail at the boundary rather than enter a retry-forever loop — the silent-hang failure mode this backend works hardest to avoid, because it looks exactly like “still running”.

The trap in that snippet

I originally wrote the isinstance check, then deleted it because pyright called it unnecessary — from_payload's declared return type is PipeWorkflowArg. But it returns Any at runtime and uses the hint only to pick a deserialization strategy: Kajson then reconstructs whatever class the payload actually names. A foreign payload therefore decodes successfully into some other model, and the next attribute access raises a bare AttributeError — which is neither a Temporal FailureError nor in the worker's workflow_failure_exception_types, so the workflow task retried forever.

The dynamic definition is what made it reachable rather than theoretical: before, an unregistered type got the SDK's own NotFoundError; now the catch-all claims every unregistered type on the queue. Lesson: a type checker's “redundant” verdict is only as good as the annotation it trusts. At a deserialization boundary, verify what the converter does at runtime.

05

Dynamic activity naming, and the collapse

Leaf steps are scheduled as <operation>::<pipe_code>. The :: separator is chosen because no act_* name can contain it — the two namespaces are disjoint by construction, not by convention, so a derived name can never shadow a static registration. Infra activities (act_deliver, act_flush_trace_events, act_assemble_tracing, act_dry_validate) stay static on purpose: they are plumbing, not method steps.

Worker-side, Temporal allows exactly one @activity.defn(dynamic=True) per worker. It recovers the operation token from activity.info().activity_type, decodes the payload into that operation's assignment type, and calls the existing act_* coroutine — unchanged. Each keeps its own @convert_pipelex_errors boundary, so the error contract is identical whether an operation is reached statically or through the catch-all. This is a routing layer, not a rewrite.

The plan's own answer here was wrong — the correction is the interesting part

The plan said: cut the crafting task pack over to the dynamic catch-all in one move. Doing that deletes the only handle anything has on an individual content-generation activity, and three separate mechanisms fell over at once:

  • Worker scopes (required_activities / excluded_activities) name activities that no longer exist — a runner-llm worker hard-fails at startup.
  • The split-worker test helper excludes content-gen activities by name to build a router-only worker — same hard failure.
  • substitute_activities={act_llm_gen_text: stub} silently becomes a no-op, because the substitution keys on a function object no longer in the registration set. That is how the suite runs leaf steps without calling a real provider — so the quiet version of this failure is a test suite that starts making live inference calls.

Three independent mechanisms needing the same granularity is a design signal, not three bugs.

The resolution: the task catalog stays canonical — one entry per act_*, addressed by its own name — and the collapse into one dynamic registration happens at worker construction, closed over that worker's own operations.

Scopes, exclusions and substitutions all keep working unchanged in canonical terms — and the specialized runner-* scopes came out stronger than before: a worker given only the LLM operations now refuses an image-gen activity that mis-routes to it, non-retryably, instead of quietly running it on the wrong pool.

A worker with no operations in scope gets no catch-all

A dynamic definition claims every unregistered type landing on the queue. Registering an empty one would turn a workflow-side worker into something that fails leaf activities meant for an activity worker beside it.

    OperationToken.IMG_GEN:       OperationImpl(ImgGenAssignment, act_img_gen_images),
    OperationToken.EXTRACT_PAGES: OperationImpl(ExtractAssignment, act_extract_gen_extract_pages),
    OperationToken.FUNC:          OperationImpl(PipeFuncExecutionRequest, act_pipe_func),
    ...
}

def make_dynamic_activity(*, operation_impls: Mapping[OperationToken, OperationImpl]) -> ActivityType:
    @activity.defn(dynamic=True)
    async def act_dynamic(args: Sequence[RawValue]) -> Any:
        activity_type = activity.info().activity_type
        operation = parse_operation_token(activity_type)
        if operation is None:
            raise ApplicationError(..., non_retryable=True)   # not a name we mint
        impl = operation_impls.get(operation)
        if impl is None:
            raise ApplicationError(..., non_retryable=True)   # wrong worker — routing bug
        if len(args) != 1:
            raise ApplicationError(..., non_retryable=True)
        try:
            assignment = activity.payload_converter().from_payload(args[0].payload, impl.assignment_type)
        except Exception as exc:
            raise ApplicationError(..., non_retryable=True) from exc
        return await impl.run(assignment)   # the unchanged act_*, with its own error boundary
    return act_dynamic

Everything above is non-retryable, the decode included: an unrecognized token, an operation this worker does not serve, a wrong-shaped argument list and an undecodable payload are all dispatch or deployment bugs. None becomes valid by trying again, and a worker that merely stalled on work it cannot do reproduces the silent-hang failure mode this backend exists to avoid.

Why the method split is not decoration

The first version had one method returning the canonical set. The replay-determinism test builds its Worker by hand (for two knobs make_worker does not expose), fed it straight to Worker(...), and got NotFoundError: Activity function llm_text::step_one is not registered. A function whose output looks like Worker input but isn't is a trap. Now the only method named for worker registration returns the registerable form (workflows_and_activities), and the canonical one is named for what it actually is (scope_selection).

Substitutions need the mapping passed through, not just the substituted list: a stub is an arbitrary function with no way back to the operation it stands for — but the mapping's key is always the canonical coroutine, which names it.

pipelex/pipe_machinery/pipe_abstract.py — a genuine core bug that dynamic naming surfaced.

     log.verbose(f"Dry run of {self.type}: '{self.code}'")

live_run_pipe stamped pipe_code=self.code onto the metadata it handed down; dry_run_pipe passed the caller's straight through. So for a whole dry run job_metadata.pipe_code stayed unset, every leaf named itself with the bare token, and every step in a dry run got the same activity name — the exact problem this phase exists to fix, unfixed for the mode the entire test suite and pipelex validate run in. It had also been silently degrading the pre-existing build_activity_summary, whose docstring rationalized the gap as “tests / fixtures with no pipe context”.

What we lose, honestly

  • The parent→child tree view in the Temporal UI for non-batch runs. A flat, well-named history recovers most of the readability, but the tree rendering is genuinely gone where the children are gone.
  • Per-sub-pipe reset granularity. Temporal reset operates per workflow; without a child per sub-pipe, resetting mid-run means resetting the run's single workflow to an earlier point rather than replaying one child.
  • Renaming an operation token is now a breaking change to what operators and dashboards see — the tokens are wire-visible.

The first two are operational niceties. Neither justifies the per-hop tax.

If you run the temporal-e2e-validate skill before phase 6

It will lie to you in two directions. Its Tier 3 asks “do parallel branches execute as separate child workflows?” and will report a false FAIL — they run inline now, by design. And its routing harness matches scheduled activity types against canonical act_* names, which no longer reach the wire, so a correctly-routed run reports was never scheduled → RESULT: FAIL. The fix is to match on the operation token instead.

Five things worth carrying forward

  1. Merging two catch ladders is not the union of their clauses. The outer one was also catching what the inner one deliberately let escape.
  2. A type checker's “redundant” verdict is only as good as the annotation it trusts. At a deserialization boundary, verify what the converter does at runtime — from_payload uses its type hint to pick a strategy, not to enforce a result.
  3. Three independent mechanisms needing the same granularity is a design signal, not three bugs. That is what turned the activity-registry cutover from “delete the per-activity registrations” into “collapse at worker construction”.
  4. Once you schedule by string name, result_type= is mandatory — for activities and for workflow starts alike. There is no signature for the payload converter to read.
  5. Run pkill -9 -f temporal-sdk-python first. Zombie test servers from earlier killed runs compound contention and look exactly like a fixture-teardown hang. It is in CLAUDE.md for a reason; skipping it cost a full diagnostic cycle.
