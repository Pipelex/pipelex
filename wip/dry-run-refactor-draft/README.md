# Dry-Run Refactor — Notes Index

Branch: `feature/Validate-with-signatures-4-fix-dry-run`. Goal: consolidate all dry-run code paths through `PipelexRunner` so dry and live runs share one entry point — **now layered on top of the signature-validation feature**, which already re-wired these paths.

> **Read this first — the situation changed since the draft was written.**
> The original draft (a few days old) documented this refactor as *already shipped* on a branch called `fix/dry-run`. That branch was **never merged**. It forked at v0.29.1 and the live branch then moved ~55 commits past it independently — landing the **signature-validation** feature (`PipeSignature`, `--allow-signatures`, strict pre-check) which **re-touched the exact dry-run code this refactor wants to delete**. So: none of the deletions/migrations the draft claimed are in the tree, and the refactor's original motivation (a "silent dry-run regression" in `validate_bundle`) **has since been fixed** — through the very path the plan wanted to remove. Everything here was re-grounded on the current code.

## Current state of the world (what's actually true today)

- The four parallel dry-run modules **all still exist**: `pipelex/pipe_run/dry_run.py`, `dry_run_pipeline.py`, `dry_run_with_graph.py`, `dry_pipe_router.py`.
- `DryPipeRouter` is **still dead code** (never instantiated outside its own definition) — the draft's central finding holds.
- `validate_bundle` **already dry-runs on load** (`validate_bundle.py`) — the three `# TODO: wip - restore or refactor dry run` are gone. The regression the plan targeted is closed.
- That fix arrived via the **old** `dry_run_pipes` path, which signature-validation then extended. `dry_run.py` is now **load-bearing for signatures**: it hosts the strict signature pre-check (`collect_signature_refs` / `collect_signature_paths` → `SignaturesNotAllowedError`), threads `allow_signatures`, and exports `convert_stuff_spec_to_typed_named` that **`pipe_signature.py` itself imports**.
- `allowed_to_fail_pipes` is **still** in `configs.py` + `pipelex.toml`. `convert_to_working_memory_format` is **still** in `dry_run.py` (imported by `pipeline_run_setup.py` and `dry_run_with_graph.py`).

So the consolidation is still desirable, but it is now a **bigger** operation than the draft assumed: any "route dry-run through a single execution path" design must find a new home for the signature strict-check and preserve the single-aggregated-error UX. See [`D-plan.md`](./D-plan.md).

> **Second expansion (2026-06-01) — the backend dimension.** Beyond the in-process consolidation, three user requirements added an orthogonal axis: DRY must (1) be testable through the **real Temporal distributed path** (workers, no shortcuts, mock at the operation/activity leaf), (2) run production validation as a **single standalone Temporal activity** dispatched by the API, while (3) direct in-process execution keeps working. The key principle: **run mode (LIVE/DRY) is orthogonal to execution backend (direct vs Temporal)**. This *retires* the "DRY → local" shortcut the parity gate was written to justify, and splits the work into three parts — **A** in-process consolidation (D1–D3), **B** run-mode/backend orthogonality at the cogt leaf (D4), **C** distributed validation as a Temporal activity (D5). See `D-plan.md` §3.5, §4.8, §4.9 and decisions D4–D5.

> **Eng review + split (2026-06-01, `/plan-eng-review`).** The review scoped **this branch to Part A only** (the in-process consolidation) and reviewed it in depth (decisions D1–D8; an outside-voice pass caught a `validate_bundle` teardown-on-success blind spot → the two-lifecycle model). ## TL;DR

**Problem (still real).** Dry-run has four parallel code paths that bypass the `PipelexRunner → PipeRun → DeliveryExecutor` orchestration, plus a confirmed dead `DryPipeRouter`. Under the principle *"a run is a run"*, dry and live should share one entry point.

**What changed since the draft.** The "silent regression" motivation is gone — `validate_bundle` dry-runs again. But the path that fixes it (`dry_run.py` / `dry_run_pipes`) is now the home of the signature-validation strict-check and is imported by `pipe_signature.py`. The consolidation therefore has to carry the whole signature surface, not just delete it.

**The design (see [`D-plan.md`](./D-plan.md)).** "Dry-run" is really two operations: **execution-dry-run** (a single pipe through `PipelexRunner`, raises on failure — already exists and *is* the north-star) and the **validation-sweep** (batch, tolerant, over pre-loaded pipes — the bespoke `dry_run.py` path). The consolidation keeps the runner as a pure single-pipe execution primitive and rebuilds the sweep as a first-class `BundleValidator` service that *composes a shared execution seam* with the runner. Decisions: **D1** `BundleValidator` service (not a batch method on the runner); **D2** extract `acquire_library` / `prepare_pipe_job` seams from `pipeline_run_setup` that both compose (no `borrowed_library` method, no suppression flags on the runner); **D3** keep the tolerant `SUCCESS/FAILURE/SKIPPED` sweep, with `allowed_to_fail_pipes` fixed to namespaced refs. Key simplification: `allow_signatures` is a validation gate, **not** a runner parameter.

**The backend dimension (D4–D5).** Run mode is orthogonal to execution backend. **D4** moves the LIVE/DRY decision **down to the cogt leaf** (`llm_gen_*`/extract/img-gen), so the content generator is run-mode-agnostic and DRY honors the backend — DRY-on-Temporal runs on the real workers and mocks *inside* `act_llm_gen_*` (req 1), retiring the "DRY → local" shortcut. **D5** makes `BundleValidator` a self-contained in-process DRY executor (direct router + inline generator, never the hub's Temporal components) that runs identically in-process (CLI/local/direct API, req 3) or inside **one standalone Temporal activity** dispatched by the API (req 2; needs a `temporalio` bump). Migration is phased across three parts — **A** (in-process: seam → validator → callers → delete), **B** (leaf run-mode mock + Temporal-DRY e2e gate), **C** (SDK bump → `act_validate_bundle` → API dispatch) — with checkpoints A–F.
