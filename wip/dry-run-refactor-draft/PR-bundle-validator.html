Dry-Run Consolidation

Four parallel dry-run code paths (plus a confirmed dead router) collapse into one first-class BundleValidator service composed over a shared acquire_library / prepare_pipe_job execution seam. Validation stops forking the runner — it now composes the same execution core a real run uses.

branch · feature/Validate-with-signatures-4-fix-dry-run base · feature/Validate-with-signatures-3 (stacked) Part A of 3 · in-process consolidation ~4.9k +/− · 70 files

TL;DR

THE PROBLEM

Four doors to one room

DRY mode had grown dry_run.py, dry_run_with_graph.py, dry_pipe_router.py and a pile of bespoke setup — each bypassing the real PipelexRunner orchestration. DryPipeRouter was dead code.

THE INSIGHT

It's two operations, not one

"Dry-run" was secretly two things wearing one name: a single-pipe execution (already the runner's job) and a tolerant batch validation sweep (a quality gate that uses runs).

THE FIX

Compose, don't fork

A new BundleValidator owns the sweep and composes the shared execution seam — the exact same core the runner reaches. The runner stays a pure single-pipe primitive with zero validation flags bolted on.

Scope

This PR is Part A — the in-process consolidation. The design (wip/dry-run-refactor-draft/D-plan.md) also defines Part B (move the LIVE/DRY mock down to the cogt leaf so DRY honors the Temporal backend) and Part C (run the whole sweep as one standalone Temporal activity). Both are deferred to their own branches — see What's deferred.

The north-star: "a run is a run"

The whole refactor is anchored on a user-stated principle:

“A run is a run, whether it's dry or live — it's the same thing. The delivery, the preparation, should go through the same thing. Everything should go through the PipelexRunner. Just drop those dry-run functions.”

Taken literally that says "delete the dry-run functions and route everything through the runner." But a validation sweep is tolerant (collect SUCCESS/FAILURE/SKIPPED, honor allowed_to_fail, skip cross-package gaps) and the runner is strict (raise on first failure). You can't make one method be both without turning the runner into a god-object. The reframe below is what made the north-star achievable without that compromise.

The reframe that drives the design

A · EXECUTION-DRY-RUN

Already through the runner

PipelexRunner.execute_pipeline(pipe_run_mode=DRY) — one pipe, loads from scratch, raises on first failure, owns its library teardown. This is the north-star and it already existed. We don't touch its public behavior.

B · VALIDATION-SWEEP

The bespoke dry_run.py path

Takes already-loaded pipes, shares one library, runs each DRY tolerantly, does a single aggregated signature pre-check. This is a quality gate, not a run — it needs its own explicit home.

The honest conclusion: a validation sweep is not a run — it's a batch policy that uses runs. So "route everything through the runner" is exactly right for the execution primitive (A), while the batch semantics (B) need a clean home that composes the runner instead of forking it. That home is BundleValidator.

The shared execution seam (D2)

The reusable middle of pipeline_run_setup was factored into two building blocks in pipelex/pipeline/execution_seams.py. The key discipline: prepare_pipe_job is pure — it builds a job and nothing else (no pipeline-manager registration, no report-registry open, no telemetry, no library mutation). Those side effects are properties of the single-run wrapper, not of building-and-running a job — which is exactly why the sweep can skip them with nothing to "suppress."

acquire_library(...)

Set current → open → load

Loads dirs + blueprints into a fresh library. Owns its own load-failure teardown (restore the caller's outer current-library, then tear the just-opened one down) so a failed load never leaks a Library. Returns (library_id, qualified_main_pipe).

prepare_pipe_job(...)

Build a PipeJob, purely

Working memory (user inputs + mock inputs when is_mock_inputs), run params, job metadata, library crate. Mock-input generation now lives here, so callers stop building working memory themselves.

BundleValidator — the batch validation service (D1)

A first-class domain service in pipelex/pipeline/bundle_validator.py. It owns the sweep semantics and runs every pipe through a locally-constructed, direct in-process PipeRun — explicitly not the hub's get_pipe_run(), which under a Temporal hub would spawn a workflow per pipe (and is illegal from inside an activity). Keeping it direct is what lets the whole sweep later be hosted in one Temporal activity (Part C).

pipelex/pipeline/bundle_validator.py — the direct primitive
class BundleValidator:
    def __init__(self) -> None:
        # Locally-constructed, direct execution primitive — NOT get_pipe_run().
        # ObserverNoOp keeps the sweep observation-silent; validation surfaces its own report.
        self._pipe_run: PipeRunProtocol = PipeRun(pipe_router=PipeRouter(observer=ObserverNoOp()))

Two lifecycles (D6)

The subtlety that an outside-voice review pass caught: validate --all wants the library torn down afterward, but validate_bundle and the build CLIs depend on the library staying loaded so they can keep using it. One method couldn't satisfy both — so there are two:

The standalone validate --all lifecycle. Opens a fresh library, loads dirs + contents, sweeps all loaded pipes, and always tears the library down in a finally — restoring the caller's outer current-library first so the guarantee survives a teardown raise.

The public inner sweep. Classifies a caller-supplied list of pipes against the caller's already-open library and never tears it down — preserving the loaded-on-success contract (pinned by test_validate_bundle_loaded_on_success). This is what validate_bundle, validate_pipe and build_runner_code_for_pipe call.

Order matters (D7): the static validate_with_libraries wiring check runs before the signature pre-pass, so a wiring error keeps its precedence over a signature error — exactly as before.

Subtle bug avoided · SKIPPED classification

Routing each pipe through PipeRun.run means a cross-package unresolved dependency no longer arrives as a bare PipeNotFoundError — the run layer re-raises the original and the router may add __cause__ links. If BundleValidator only checked the top-level exception, partial-bundle validation would regress from SKIPPED to a hard FAILURE. So _root_cause_is walks the entire __cause__ / __context__ chain (with a seen-set guard against cyclic contexts).

Minimal diff — _classify_pipe and the recursive cause walk
pipelex/pipeline/bundle_validator.py
try:
    pipe_job = await prepare_pipe_job(pipe=pipe, library_id=library_id,
        execution_config=execution_config, pipe_run_mode=PipeRunMode.DRY,
        pipeline_run_id=SpecialPipelineId.DRY_RUN_UNTITLED, ...)
    await self._pipe_run.run(pipe_job)
except (PipelexError, ValidationError, FactoryException) as exc:
    # broad DOMAIN surface — never `except Exception`
    if self._root_cause_is(exc=exc, exc_type=PipeNotFoundError):
        return DryRunOutput(..., status=DryRunStatus.SKIPPED, ...)   # cross-package gap
    return DryRunOutput(..., status=DryRunStatus.FAILURE, ...)
return DryRunOutput(..., status=DryRunStatus.SUCCESS)
 
@classmethod
def _root_cause_is(cls, *, exc, exc_type) -> bool:
    seen: set[int] = set(); stack = [exc]
    while stack:
        current = stack.pop()
        if id(current) in seen: continue        # cyclic __context__ guard
        seen.add(id(current))
        if isinstance(current, exc_type): return True
        for linked in (current.__cause__, current.__context__):
            if linked is not None: stack.append(linked)
    return False

Library lifecycle hardening

A recurring, easy-to-get-wrong pattern shows up across every code path that opens a temporary library: the current-library binding is a ContextVar, and naive teardown clobbers the caller's outer binding. The fix is one disciplined idiom, applied everywhere.

sequenceDiagram participant C as Caller (has outer library X) participant H as hub _library_id ContextVar participant V as validate path C->>H: outer current = X C->>V: enter V->>H: prev = get_current_library_id_or_none() (= X) V->>H: set_current = Y (the temp/run library) Note over V: ...do the work (may raise)... rect rgb(42,26,31) Note over V,H: finally / teardown V->>H: restore prev FIRST → set_current = X V->>H: teardown(Y) end V->>C: return (outer current still = X)
Restore the outer binding before teardown, so the safety guarantee holds even if teardown itself raises. set_current_library can't take None, so the "no outer was set" case routes through the renamed clear_current_library().
Rename · teardown_current_library → clear_current_library

The old name implied it freed the Library. It doesn't — it only resets the _library_id pointer to None. Releasing the library is a separate library_manager.teardown(library_id=...) call. The rename makes the two distinct operations honest at every call site.

Minimal diff — runner restores the outer binding, with a collision guard

The recent review fix in PipelexRunner.execute_pipeline: capture the outer binding up front, and on teardown restore it — unless the caller's outer library is this run's library (in which case "restoring" would leave the ContextVar pointing at the library we're about to tear down, so we clear instead).

Signature validation fixes

CLASSIFICATION

SignaturesNotAllowedError → INPUT domain

An unimplemented placeholder in a submitted bundle is a caller mistake, not a server fault. Now marked error_domain = ErrorDomain.INPUT + _authors_caller_facing_message = True → the API renders it 422 (not 500), and the CLI logs it as a caller error. Matches the agent-CLI's existing classification.

IDENTITY

validated_pipes unified on namespaced pipe_ref

Previously validate all reported domain.code while validate pipe reported the bare code — the same pipe under two identities depending on the command. Now every surface emits the qualified ref, which can't collide across domains.

What's deferred (and why the design looks the way it does)

The whole conceptual frame is run mode (LIVE/DRY) is orthogonal to execution backend (direct vs Temporal). Four cells, all must eventually work — and that's why BundleValidator is built as a self-contained in-process executor that never touches the hub's Temporal components.

PART B · own branch

Leaf-level run-mode mock (req 1)

Today the DRY mock is minted above the activity boundary (operators hardcode ContentGeneratorDry()), so DRY on a Temporal hub never dispatches act_llm_gen_*. Part B moves the LIVE/DRY decision down to the cogt leaf (llm_gen_* / extract / img-gen, carried on JobMetadata.run_mode) so DRY honors the backend and mocks inside the activity. Retires the "DRY → local" shortcut.

PART C · own branch, gated

Validation as a Temporal activity (req 2)

The API dispatches the whole sweep as one standalone act_validate_bundle activity. Needs a scoped_content_generator ContextVar (mirroring scoped_current_library) to force the inline generator, a temporalio bump beyond 1.23.0 for standalone activities, and the cross-repo pipelex-api route migration.
