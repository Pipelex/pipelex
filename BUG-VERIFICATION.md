## Real — act on these

### Cross-worker cost report assembly never wired into runtime (medium, M)

`UsageAggregator.aggregate` (`pipelex/tracing/usage_aggregator.py:13`) and `ReportingManager.inject_tokens_usages` (`pipelex/reporting/reporting_manager.py:227`) both exist but have zero production callers — grep across `pipelex/` + `tests/` finds `aggregate` referenced only by its own definition, a pass-through comment (`graphspec_assembler.py:186` `pass # Handled by UsageAggregator`), and `tests/unit/.../test_usage_aggregator.py`; `inject_tokens_usages` is referenced only by docstrings (`reporting_manager.py:133,148`) and its unit tests. The runtime cost path at `pipelex/cli/commands/run/_run_core.py:224` calls `generate_report(pipeline_run_id=...)`, which (`reporting_manager.py:369-394`) reports only from local `_usage_registries` — populated via `_try_add_to_registry` (`:141-154`), which silently skips on runner processes where `open_registry` was never called. The two event-log readback paths — `graph_assembly.py:53` (direct mode, wired via `pipe_run.py:71`) and `temporal/tprl_pipe/act_assemble_graph.py:39` (wired via `wf_pipe_run.py:81`) — feed `read_events` only into `GraphSpecAssembler.assemble` to build the GraphSpec; neither calls the aggregator or `inject_tokens_usages`. So distributed `UsageReportEvent`s emitted by `_emit_usage_event_runner_fallback` (`reporting_manager.py:289-352`) land in the backend partition and are never assembled into a cost report. `CHANGELOG.md:266-270` documents the emission + aggregator machinery but no readback-into-cost-report wiring.

Recommended action: wire the cost readback parallel to the existing graph readback — after run completion (in the `graph_assembly` path for direct mode, and `act_assemble_graph` / post-workflow for Temporal) call `UsageAggregator.aggregate(events)` then `ReportingManager.inject_tokens_usages(pipeline_run_id, usages)` before `generate_report`, so distributed `UsageReportEvent`s become a complete cost report. Re-file with corrected code ref `pipe_run/pipe_run.py:71` (the cited `pipe_run/runner.py` was renamed; substance holds). Effort: M.

### get_config() reads inside Temporal workflow code — replay nondeterminism (medium, M, known-deferred)

The `get_config()` reads inside workflow code all still exist. `observability.py:104` does `config = get_config().temporal.search_attributes` inside `build_search_attributes()`, called from workflow-side code at `wf_pipe_run.py:63` (inside `@workflow.run async def run`) and `temporal_pipe_router.py:85` (inside the `if is_in_temporal_workflow():` child-dispatch branch). The `content_generator_in_workflow.py` `make_*` methods read live config at workflow runtime and feed it into the recorded activity-start command: e.g. `make_llm_text` reads `get_config().temporal.worker_config` (`l.73`), `.queue_options` (`l.83`), `...is_dispatch_resolution_traced` (`l.84`), then `resolve_dispatch(...).to_execute_kwargs()` (`l.80-85`) supplies `task_queue`/`start_to_close_timeout`/`retry_policy` to `workflow.execute_activity(...)` (`l.87-92`). The same pattern repeats across `make_object`, `make_object_list`, `make_single_image`, `make_image_list`, `make_templated_text`, `make_render_page_views`, `make_extract_pages`. `resolve_dispatch` (`config_temporal.py:498-632`) derives task_queue/timeout/retry from config, so a config edit between original run and replay emits a different `ScheduleActivityTask` command -> `NondeterminismError`. None of the proposed fixes have shipped (no `WorkerDeploymentConfig`/`VersioningBehavior`/`TemporalDispatchSnapshot`/`search_attributes_enabled` in `pipelex/`, no Replayer regression test).

Recommended action: keep in backlog as a known-deferred item, not a fresh fix. The code is intentionally in this state — the "submitter snapshot" approach was attempted and reverted for sound reasons (operator config shouldn't ride workflow input; payload bloat; defeats central config). The chosen path is operational mitigation (drain in-flight workflows before editing `[temporal.worker_config]`/`[temporal.queue_options]`/`[temporal.search_attributes]`) plus future Worker Versioning, and `wip/temporal-next/01-deferred-items.md:9-37` already tracks it as deliberately deferred. Cheap, file-able next steps: (1) add a `docs/distributed-execution` note on the config-edit-while-in-flight constraint; (2) add a Replayer regression test over a saved history. The full fix (Worker Versioning) is large. Effort: M.

### GraphSpecAssembler event ordering wrong for parent/child topologies (medium, M)

The bug is live and the TODO is present verbatim. `pipelex/tracing/ndjson_event_log.py:157-161` — TODO states "causal ordering — sorting by (workflow_id, sequence) groups by lexicographic workflow ID, not execution order. In parent/child workflow topologies this can cause incorrect producer map overwrites in GraphSpecAssembler." — followed by `events.sort(key=lambda evt: (evt.workflow_id, evt.sequence, evt.writer_id))`. The producer map is last-writer-wins and order-sensitive: `graphspec_assembler.py:273` (`_handle_pipe_end_success`) and `:311` (`_handle_controller_output`) both unconditionally do `self._stuff_producer_map[digest] = node_id`. DATA edge sources are resolved purely from this map at `graphspec_assembler.py:388` (`producer_node_id = self._stuff_producer_map.get(input_spec.digest)`), so cross-workflow lexicographic ordering can yield a wrong DATA edge source. This path is exercised cross-worker in `pipelex/temporal/tprl_pipe/act_assemble_graph.py:39-50` and offline in `pipelex/pipe_run/graph_assembly.py:53-55`. No CHANGELOG entry resolves it. (Targeted mitigations exist for a *different* race — parallel-combine snapshots branch producers at emit time, `trace_events.py:143-144` / `graphspec_assembler.py:333-337`; batch edges use an explicit `batch_controller_node_id`, `:405-407` — but those do not cover the general DATA edge path the TODO describes.)

Recommended action: replace the lexicographic `(workflow_id, sequence)` sort in `read_events` with causal/topology-aware ordering (timestamp-based, or a topological order over parent/child workflow relationships), as the TODO itself proposes. Real-world severity is gated by digest collisions across distinct workflows — only then is a wrong DATA edge produced — and it only affects observability graph output (the assemble activity is best-effort and swallows failures), so medium is appropriate. Effort: M.

### JobMetadata.started_at naive vs aware datetime TypeError (low, S, partially-real)

Root cause confirmed unfixed: `pipelex/pipeline/job_metadata.py:79` still uses `started_at: datetime | None = Field(default_factory=datetime.now)` (naive). The `duration` property at `:84-85` does `(self.completed_at - self.started_at).total_seconds()`, which raises `TypeError` on naive/aware mismatch. The hazard is real and documented in-repo: `pipe_abstract.py:456` constructs `datetime.now(timezone.utc)` (aware), and `content_generator_dry.py:48-52` carries a comment stating the field "can arrive either offset-naive ... or offset-aware ... mixing aware/naive raises TypeError when JobMetadata.duration subtracts," with a defensive workaround at `:54-59`. But the realized crash surface is narrower than medium: in all live inference paths the field is reset to naive on both ends — `started_at` via `*_before_start` (`llm_job.py:30`, `search_job.py:34`, `img_gen_job.py:24`, `extract_job.py:24`) and `completed_at` via `*_after_complete` (`llm_job.py:45` etc.) — so the subtraction is self-consistent there. The aware value in `pipe_abstract.py:456` is a local var for graph tracing, never assigned to the field. The only path where the naive default reaches the subtraction (dry-run reporting via `report_inference_job`, `reporting_manager.py:356`) is the one already guarded. No CHANGELOG entry fixes the root cause.

Recommended action: fix at the source rather than relying on the per-callsite workaround — change `job_metadata.py:79` default_factory to a tz-aware lambda (`lambda: datetime.now(timezone.utc)`) and normalize the live job paths (`llm`/`search`/`img_gen`/`extract` `*_before_start`/`*_after_complete`) to also use aware datetimes, so duration subtraction is uniformly aware-vs-aware. Then the `content_generator_dry.py` tzinfo-matching dance can be simplified. Re-file with corrected severity (low, latent) — not the reported medium active crash. Effort: S.

### Protocol-violating make_extract_pages signature in ContentGenerator (low, S, partially-real)

The signature divergence still exists: `content_generator.py:257-258` declares `extract_job_params: ExtractJobParams | None = None` and `extract_job_config: ExtractJobConfig | None = None`, while the Protocol at `content_generator_protocol.py:125-126` requires non-None types. So the factual divergence is real — but the "contract violation / type-check or runtime error" framing is wrong. No type-check error: widening a required `T` to optional `T | None = None` is the LSP-contravariant-safe direction; the class subclasses the Protocol with `@override` (`content_generator.py:37,250-252`) and there is no `type: ignore`/`pyright: ignore` anywhere, so pyright+mypy (run by `make agent-check`, gated in CI) accept it. No runtime error: None is immediately defaulted at `:260-261` (`... or ExtractJobParams.make_default_extract_job_params()`, `... or ExtractJobConfig()`); the only real caller (`pipe_extract.py:158-164`) always passes non-None. The item originates from the deferred/nice-to-have list of the source plan (`wip/archive/collapse-content-generation-workflow-layer-v2-plan.md:393`), explicitly tagged a "pre-existing divergence."

Recommended action: tighten the two direct/dry impl signatures to the non-None Protocol shape and default-construct at the operator boundary (`pipe_extract.py` already passes both). This is a trivial consistency cleanup, not a correctness fix — safe to drop from a bug backlog and re-file as low-priority tidy. Re-file with corrected detail: it is NOT a type-check or runtime error source. Effort: S.

## Stale or already-shipped — correct the backlog

- **Bare except Exception in wf_pipe_router.py (already-shipped, was high):** Backlog claims bare `except Exception` on workflow-critical paths; the code shows every cited catch now carries `# noqa: BLE001` plus a one-line justifying comment, satisfying `.claude/rules/python-standards.md` (`wf_pipe_router.py:111-113,119-121,147-149,163-165`; `act_assemble_graph.py:55-57`). `git blame` ties this to commit `11a10ed7` (PR #943, error-handling overhaul), and CHANGELOG `:95` documents it. - **PipeLLM wrapping defeats the PipeRouter transient-retry loop (stale, was high):** Backlog claims an app-level transient-retry loop in direct mode that PipeLLM's wrapping defeats; the code shows direct mode is a single pipeline-level attempt with no retry by design (`pipe_router_protocol.py:54-72` — "This handler is error propagation, not retry... Resilience is the Temporal track's job"), so there is no retry branch to defeat. PipeLLM preserves the cause chain (`pipe_llm.py:247/251,262/266,356/360,373/377` all `raise PipeRunError(...) from exc`), and Temporal-mode retryability is correctly derived from `__cause__` via `find_inference_error_category_in_chain` (`exceptions.py:112-136`, `temporal_error.py:264-279`). CHANGELOG `:95,99,113,159,175` documents this design. **Drop from backlog.**
- **Graph tracer misaligns when a failed batch branch has no item_stuff_code (stale, was medium):** Backlog claims partial-failure collection in PipeBatch keyed by `item_index + item_stuff_code` where a failed branch has neither; the code shows `gather_bounded` re-raises the first exception rather than returning partial results (`async_utils.py:56-59`), so the harvest/aggregation only runs when all branches succeeded (`pipe_batch.py:207,212-215,232-239`), keyed by a contiguous `enumerate` `agg_index` plus a real `item_stuff_code` — no sparse-gap/None path exists. The premise lives in an unbuilt design doc (`wip/concurrency/batch-partial-failure.md:3` "Status: design scoping, not yet a plan"; the graph-tracer item is listed at `:53` as future blast-radius); CHANGELOG `:91` confirms current behavior. **Drop from backlog; track under that design doc.**
- **gather_bounded first-error-by-index ordering would regress under a semaphore (stale, was low):** Backlog claims a semaphore-based window; the code shows `gather_bounded` is chunk-based with no `asyncio.Semaphore` anywhere (`async_utils.py:51-61`), and first-error-by-input-index is intact and pinned by tests (`tests/unit/pipelex/tools/misc/test_async_utils.py:68,81-117`). The regression only arises *if* the chunk barrier is replaced by a naive gather — a hypothetical called out in a design-scoping doc (`wip/concurrency/fan-out-scheduling.md:3,7,55-61`). **Drop from backlog; the open question already lives in the design doc.**
